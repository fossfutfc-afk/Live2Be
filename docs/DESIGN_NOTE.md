# DESIGN_NOTE.md — **note 的真正定位**

> 建立 2026-09-27。用户原话：
> *"思考一下 note 的真正定位，LLM 为什么要有 note？人为什么要有 note？
> 一个 note 应该是轻便易携带的，它是否应该是指向某些群的指针？
> 就像人类的海马体，存储关键记忆在大脑皮层中的位置，或者多次被召回的记忆，会直接进入 note？"*
>
> **本文只回答定位问题** —— 施工规格见 `docs/DESIGN_DIGEST_LAYERS.md`，背景与真机证据见 `PROCEED.md`。
> **当前状态：代码一行未动。**

---

## 0. 一句话结论

> **note = 引擎无法替她保证"必然在场"、而她又必须知道的那几件事的常驻投影。**
>
> 三类，各有各的**存在理由**（不是"想要什么就放什么"）：
>
> | 槽 | 存在理由 | 判据 |
> |---|---|---|
> | **约定**（promise） | **前瞻**：不写就必然失约，且**没有任何别的面看得见它** | 不可检索 + 她不会主动查 |
> | **心境**（on_mind） | **当下**：给一个"此刻我在意什么"的注意力锚 | 不属于任何群，是**此刻** |
> | **索引**（index）⭐ 新 | **指针**：一行换掉一整个群的全部正文 | 每轮成本：**30 字换 1000 字** |

## 1. 人为什么要有 note —— 三个**不同**的东西被同一个词盖住了

这是本节最关键的发现：**"note"在人类实践里是三种东西，触发条件、生命周期、功能都不同。**

| # | 人类用途 | 触发条件 | 生命周期 | 认知学对应 |
|---|---|---|---|---|
| **①** | **外置记忆** | *"我会忘，而且忘了有代价"* | 到事情办完为止 | **前瞻记忆**（prospective memory）· **意向卸载**（intention offloading） |
| **②** | **外置思考** | *"我现在正在想这个"* | 想到别处就换 | 草稿纸 · 工作记忆的外挂 |
| **③** | **索引** | *"我知道它在哪，但一下想不起来"* | 长期，随知识增长 | **海马体索引** · Memex 的 associative trail · 卡片盒的 hub note |

**①的证据**：意向卸载的综述（[Intention Offloading review, UCL](https://discovery.ucl.ac.uk/id/eprint/10151884/)）指出，
人**是否**写外部提醒，取决于**元记忆判断**——*她觉得会忘，才会去写*；而写了**确实提升**前瞻记忆表现。
⭐ 所以"人写 note"的判据是 **"已知会忘 ∧ 忘了有代价"** —— 不是"这件事重要"。

**③的证据**（本轮联网查到的，都是现成的先例）：
- ⭐ **Zettelkasten 的官方笔记类型**（[zettelkasten-mcp](https://github.com/entanglr/zettelkasten-mcp)）里有专门的两种**指针式笔记**：
  `structure` = *"Index or outline notes that **organize other notes**"* ·
  `hub` = *"**Entry points** to the Zettelkasten on key topics"* —— **不装内容，只指向别处**
- **Memex（Vannevar Bush, 1945）** 的 *"associative trails"*：他把 **trail 本身**当作一等公民
  （原话大意：*"the trail is the thing"*），**内容可以散落各处**
- **海马体索引理论**（Teyler & DiScenna 1986；[Rolls 2024 回顾](https://oxcns.org/papers/692%20Rolls%202024%20Hippocampal%20Discoveries.pdf)）：
  海马**不存内容**，它存**指向新皮层表征的索引**；回忆 = 一个线索激活索引 → 索引把新皮层的多个片段**绑到一起**重放
  （另有 2024 年的工作把它当作框架，见 [Nat Commun PMC11387663](https://pmc.ncbi.nlm.nih.gov/articles/PMC11387663/)）
- **Luhmann 的查号表**：他自己称之为 *"query into the database"* —— 索引，不是内容

⇒ ⭐⭐ **所以"note 应该是指向某些群的指针"这个猜想，在人类实践里有三个独立的先例（卡片盒 hub / Memex trail / 海马索引）。它不是新发明，是被我们漏掉的那一类。**

### 我们今天的 note 落在哪

| 人类的三类 | 我们今天有吗 |
|---|---|
| ① 外置记忆（前瞻） | ✅ **有** = `promise`（真机 2 条 / `close` 0 次） |
| ② 外置思考（当下） | ✅ **有** = `on_mind`（真机 1 条） |
| ③ **索引**（指针） | ❌ **完全没有** |

而今天的 `habits`（真机 3 条）**三个都不是** —— 它想当"规律"，规格却是"≤20 字标签 + refs 无走法"
⇒ 既不是约定、也不是心境、也不是索引。**它是我们缺③之后找的替身。**

## 2. LLM 为什么要有 note —— 与人的三条**关键差别**

| # | 人 | LLM | ⇒ 设计后果 |
|---|---|---|---|
| **1** | **会遗忘**（痕迹衰减） | **不会遗忘** —— 它的"记不住"是**上下文窗口** | ⭐ 判据不同：人问"**我会不会忘**"；LLM 要问"**它会不会进入我的上下文**" |
| **2** | **能被线索触发回忆**（海马索引自动激活） | ⚠️ **不能** —— 它**只能读到已经放进上下文的**东西，或**主动调用一次检索** | ⭐⭐ 对 LLM，**索引必须显式化**：要么引擎替她检索好塞进去，要么给她一个"查"的动作。**这正是我们今天卡住的地方**（`note.refs` 没有走法 / `recall` 零产品调用者） |
| **3** | note 是**免费**的外挂 | note **每轮都在花 token 与注意力**（Anthropic *context rot*） | ⭐ note 的价值不能只是"提醒"，必须"**用最少 token 换最大确定性**" ⇒ **它必须轻** |

**⇒ 汇总：LLM 需要 note，是为了三件人不需要它做的事：**

| 目的 | 为什么 LLM 更需要 |
|---|---|
| **① 让某件事必然在场** | 人可以被突然想起；LLM **不在上下文就是不存在** |
| **② 给当下的注意力锚** | 她的上下文里有几百条历史与 4293 字的记忆视图，需要一个"**此刻我在意什么**"的指针 |
| **③ 用短指针换长正文** | **每轮都付费** ⇒ 30 字换掉 800 字是净赚 |

**外部对照（本轮查到的最强锚点）**：Letta / MemGPT 的 **core memory**
（[Letta memory 文档](https://docs.letta.com/advanced/memory-management/)）：
> *"always-in-context structured blocks (user facts, agent persona). **Character-limited, agent-editable** via API calls."*

⭐ **"常驻 + 字符上限 + 她自己可编辑"** —— 与我们 note 的形态**完全一致**，而它把这件事做成了**一等架构**。
另外 Letta 的 **sleep-time compute**（后台异步 agent 共享记忆块、重组织与合并）**正是我们 L3 的形状**。

## 3. "多次被召回的记忆会进入 note" —— 直觉对，但信号要换一个

用户的类比：人的记忆**反复提取会变强**（testing effect / retrieval strength）。
Bjork 的"新失用理论"把**存储强度**与**提取强度**分开，**成功提取提升提取强度**（[Bjork 2001](https://sanlab.psych.ucla.edu/wp-content/uploads/sites/13/2016/07/RBjork_2001.pdf)）。

⚠️ **但对 LLM 必须拆成两问**：

| 谁在召回？ | "被召回次数"实际是什么 | 能不能当信号 |
|---|---|---|
| **引擎自动召回**（每轮注入） | = 它**被注入**的次数 | ❌ **不能用** —— 它**本来就已经在场**了，note 里再加一份是重复 |
| ⭐ **她自己主动查**（未来的 `mmt_recall`） | = **她关心什么** | ✅ **这才是我们要的信号** |

⇒ ⭐ **正确的形状不是"召回次数"，是"被主动查询的次数"** —— 它衡量的是**她自己的关注**，不是引擎的相关性分数。

⚠️ **但有一个陷阱必须防**：如果"查得多就常驻"，会形成**正反馈**
（常驻 → 更容易被看到 → 更容易被查 → 更常驻）⇒ **少数条目垄断**，与"只增不减"是同一类病。

⇒ **建议**：这个信号只当**排序提示**（同 `render._count_of` 的定位），**不当准入**；
而且必须**有退役**（查得少了自然沉底 —— ChatGPT"Dreaming"的**频率分层**就是这个机制）。

## 4. ⭐ 三条合一的存在判据（这是"什么该进 note"的唯一标准）

一个东西要进 note，必须**同时**满足：**不可检索 ∧ 她不会主动查 ∧ 不在任何别的可见面上**。

| 判据 | 问法 | 约定 | 规律 | 某条 episode 的细节 |
|---|---|---|---|---|
| **可检索性** | 它能被检索到吗？ | ❌ 不在任何面（§ 陷阱 43） | ✅ **写下来就可检索** | ✅ 原文在 `events.jsonl` |
| **她会不会主动查** | 她会在**需要之前**想到要查吗？ | ❌ **不会** —— 意识到需要时已经失约 | ✅ 会（聊到花时能想起来） | ✅ 会 |
| **每轮成本** | 值多少 token？ | 一行 ~20 字 | 一行索引 ~30 字 · **正文** ~100 字 × N | 全文 ~150 字 |
| ⇒ 结论 | | **必须常驻** | **常驻"索引"· 正文按需** | **不进 note** |

⭐ 顺带把 nacre 判据的作用域说清楚了（`PROCEED §4.4`）：
**"不可检索 ⇒ 必须常驻"只对"从未被写下来的东西"成立。规律一旦写下来（节点或边），它立刻变成可检索之物。**

## 5. 我们缺的那一类：③索引 —— 它的形状

### 5.1 一行索引装什么

```
主题（aspect 归一化后的名字） + 次数 + 时间范围 + 指针
```

**真机对照**（`n2`「瓦片缝那盆苔藓，总想带他去看」refs = m0014/m0015/m0017）：

| 项 | 今天 | 索引应该给 |
|---|---|---|
| 主题 | 正文里的"苔藓" | `aspect = 苔藓`（**群的身份**） |
| **次数** | ❌ **没有**（"频次绝不印"） | **5** |
| **时间范围** | ❌ 只有"记于 N 天前"（卡写下的时间） | **09-20 ~ 09-27** |
| **指针** | refs 印了，但**没有走法** | refs **可被引擎展开** |
| 完整性 | ⚠️ **抽样**（漏了 m0016 / m0020） | 群成员 = **完备**（边一条不丢） |

### 5.2 ⭐ 索引成立的前提只有一条：**它有走法**（2026-09-27 用户已裁）

**今天 `refs` 是一条"没有走法的边"**（陷阱 43）：印给 LLM 看了，但引擎**不会因为它去取物** ——
细节仍然靠 `_bucket_view` 把 18 条 episode 全文（**2644 字**）全量灌。

✅ **用户裁决（2026-09-27）：两条都要，分工写死**：

| # | 走法 | 谁发起 | 说明 |
|---|---|---|---|
| **①** | **引擎按 refs 展开** | 引擎（**注入时预取**） | ⚠️ **必须在注入时**：writer 一次调用中途**不能去查** ⇒ 引擎要**提前取好**放进上下文 |
| **②** | **给她一个特定动作** | 她（主动） | ⚠️ **动作本身待设计**（用户：*"动作到时候再设计即可"*）⇒ 与 `docs/DESIGN_RECALL.md` 的 `mmt_recall` 是同一族，将来**统一**，不许造两套 |
| **③** | **展开可选 link 连环** | 引擎 | 沿边继续走。⚠️ **默认 1 跳 + 带预算**（连环会爆炸；真机 18 节点 / 39 边，1 跳可控）。适合走的 rel：`same_kind` / `supports` / `about` |

⭐⭐ **连带发现（本轮）：`index` 因此有第二个用途** ——
它**不只是给她看的提示，同时是引擎的"取数路由表"**：`topic → refs` 让引擎知道
"这轮聊到苔藓 ⇒ 该预取哪几条正文"。**没有它，引擎不知道取什么**（今天只能全量灌）。

### 5.3 注入形态（保持 `render_note_block` 的纪律：自然语言小节、零结构化痕迹）

```
【你自己记的备忘录】（你自己随手记下的, 不是别人给你的任务; 括号里是编号, 指回你记忆里的那件事）
  · 你自己记下的约定
    n1 带老师看瓦片缝的苔藓 (m0014)  ← 记于 1 天前
  · 最近在想
    我给瓦片留了缝让它见光——也想给自己留一道
  · 你留意到的                              ← ⭐ 新增的一节
    苔藓那件事, 前后有五回 (09-20 ~ 09-27)
```

⭐ **注意最后一行**：**"有五回"是索引的唯一价值** —— 它**不描述内容**，它说"**这里有一类事，而且不止一次**"。
而"苔藓"这个名字来自 `aspect`（**群的身份**，见 `DESIGN_DIGEST_LAYERS.md §5.2`）。

⚠️ **它和 L2 的 belief 是两件事**：
- **belief** = 她的**态度/命题**（"我这样的杂草，第一次找到了自己的太阳"）—— 创作，按需取
- **索引** = **"这里有一类事"** —— 常驻的一行指针，**不含判断**

## 6. note v2 的形状（落成代码）

```json
{
  "up_to_seq": 314,
  "promise": [
    {"id": "n1", "text": "带老师看瓦片缝的苔藓", "refs": ["m0014"],
     "since": "2026-09-26T23:05:57+08:00", "due": ""}
  ],
  "on_mind": {"text": "我给瓦片留了缝让它见光——也想给自己留一道", "since": "…"},
  "index": [
    {"topic": "苔藓", "n": 5, "span": ["2026-09-20", "2026-09-27"],
     "refs": ["m0014", "m0015", "m0016", "m0017", "m0020"],
     "from": "group:苔藓"}
  ]
}
```

| 槽 | 谁写 | 真源 | 备注 |
|---|---|---|---|
| `promise` | **L1**（当场 + 收口）· 主 LLM 可选顺手字段 | `note/*` 事件 | 两段式 `close → retire` 不变 |
| `on_mind` | **L1** | `note/rewrite` 事件 | 一句散文，不印编号不印 refs |
| **`index`** ⭐ | **引擎派生**（从 `same_kind` 边 + `aspect` 分组算出来）· **LLM 只命名 topic** | ⭐ ✅ **已裁（2026-09-27）：纯派生缓存，不落真源**（从边表重建）⇒ 与 `notes.json` 同级 | 只给"过 promotion 阈值的群"（`DESIGN_DIGEST_LAYERS.md §3.3`：成员 ≥3 · 跨 ≥2 段） |
| ~~`habits`~~ | ✅ **已落地 2026-09-29（N4a）: 退役**（全链删干净, 旧档的键读时忽略）· 原裁决 ❌ **取消** | —— | 内容→L2 的 belief · 指针→`index` · 文字→不预写 |

⚠️ **`index` 由引擎派生**这一点很重要 —— 它意味着：
**索引不会膨胀**（群的数量有上限）· **不会漂**（topic 名归一化）· **可重建**（删掉重跑一致）。

## 7. 三个可测判据

| 判据 | 目标 | 今天 |
|---|---|---|
| **note 的 token 占比** | 百字级（≤200 字） | note **96 字** · episode 全文 **2644 字** ⇒ 索引加进来仍在百字级 |
| ⭐ **每条 note 的"走法"** | `promise` / `index` 的 `refs` **必须能被引擎展开** | ❌ 今天 refs 零消费者 |
| **存在判据** | 一条 note 若**既不能检索、又不会被主动查、又不在任何别的面** ⇒ 必须常驻（这是它的存在理由）；否则**不许进 note** | 今天 `habits` 三条都不满足 |

## 8. 与三层重排的接口

| 层 | 与 note 的关系 |
|---|---|
| **L1** | ⭐ **note 的唯一写者**（`promise` + `on_mind`）—— 约定是"当场说定的"、心境是"此刻"，**本段视野就够** |
| **L2** | 产出群与 belief ⇒ ⭐ **`index` 的原料**（`aspect` 分组 + 计数 + 时间范围 + refs）；但 **L2 不写 note**（保持 L1 是唯一写者） |
| **L3** | entity 摘要 = **动态人设基线** ⇒ ⭐ **它和 `on_mind` 是一对**：L3 说"**他们现在是什么样**"，`on_mind` 说"**我此刻在意什么**" |

## 9. 未定 / 明确不做

### 未定

| # | 项 |
|---|---|
| 1 | ⭐ **L3 的注入位置**（见 `DESIGN_DIGEST_LAYERS.md §4.1` 的详解与建议 —— **待点头**） |
| 2 | **"被主动查询次数"要不要记**（§3）—— 它是 `mmt_recall` / 那个"特定动作"接通后才有意义的信号 |
| 3 | **索引条的容量闸**：Nomi 是"每类 ≤50、合计 ≤150、每次只给最相关 2–5 条"—— 我们要不要一个硬上限？我倾向**按 token 预算**（同 L2 的候选装填） |
| 4 | **`refs` 展开的预取命中率**：引擎凭什么知道"这轮该取哪几条"？（§5.2 的连带发现：靠 `index` 的 topic 路由 + 当前上下文。**需要真机标定**） |

### ✅ 已裁（2026-09-27）

| # | 裁决 |
|---|---|
| 1 | **`refs` 要有走法：引擎按 refs 展开（注入时预取）+ 给她一个特定动作**（动作待设计）· **展开可选 link 连环**（默认 1 跳 + 预算） |
| 2 | **`index` = 纯派生缓存**（从边表重建，不落真源） |

### 明确不做

| 项 | 为什么 |
|---|---|
| ❌ **`habits` 槽** | 三个存在理由都不满足（§4） |
| ❌ **把规律正文放进 note** | 规律写下来就可检索 ⇒ 按需取；note 只放**指针** |
| ❌ **拿"被引擎注入的次数"当重要性信号** | 它本来就已经在场（§3） |
| ❌ **note 里预写她的台词** | 那是创作 ⇒ 必须由 writer 在**高潮那一刻现写**（Kindroid 红灯：概括活得比证据长 ⇒ 模型编造具体场景） |
