| 轴 | v2 现状 | v3 目标 |
|---|---|---|

## 1. 为什么 v3 必须换节点层

### 1.1 ⚠️ `experience` 一词在代码里承担四套语义

| 出现位置 | 实际含义 | 归属层 |
|---|---|---|
| `nodes.KINDS` 的 `kind="experience"` | 重复模式 / 口癖 | **图节点** |
| `nodes.is_seed()` 判据 `source="experience"`（挂在 **episode** 上） | 出厂预设经历 | **图节点的来源字段** |
| `render_background_experience(ch.experience)` | `experience.yml` 角色档案 | **配置文件**（不进 wiki） |
| `mmt_inspect_character` 的 L3 `+experience` | 故知层人设资料 | **检视深度** |

同一拼写横跨四层。**后果不是"难读"，而是规则写不对**：`accrue`（同类事件并入 experience）、
`_ensure_cognition` 的目标校验、`render` 的分桶、`recall` 的 kind 过滤——每一处的"experience"
指的是哪一套，只能靠上下文猜。

### 1.2 ⚠️ 线上真实数据证明 `experience` 节点名不副实（决定性证据）

线上全库 **13 个节点**（haruka 8 / mutsuki 5 / kayoko 0）。其中唯一的 experience 节点：

```json
{"id": "e0001", "kind": "experience", "subject": "player", "significance": 0.5,
 "epistemic": "observed_fact", "links": null, "event_seq": [60], "segment_id": "seg-60",
 "pattern": "老师总靠喝浓缩咖啡硬撑工作, 自称到了需要它才有精力的程度",
 "verbatim": "我已经到了需要喝浓缩咖啡才能有精力工作的程度了呢",
 "tags": ["浓缩咖啡", "工作", "老师"]}
```

它有**三处自相矛盾**，每一处都指向同一个诊断：

1. **`subject="player"` 但 kind 叫 experience** —— 它记的是**关于玩家（老师）的知识**，
   不是角色的经历。它是"对老师的认知"，语义上就是 belief。
2. **`epistemic="observed_fact"` 但内容是一句转述** —— "自称到了……的程度"是**老师说的**。
   按 v2 自己的护栏，这该是 `reported_fact`（episode 才有此取值），而 belief 又强制
   `inferred_belief`。**它落在一个两种 kind 都不认的语义夹缝里**。
3. **`links=null`** —— 而 v2 的规则是"belief 必须 links ≥1 支撑（无支撑升华拒绝）"。
   它作为 cognition 参与 Round B 组织（`render_cognition_list` 只挑 belief/experience），
   却**没有任何支撑证据**。规则在 kind 之间不一致。

**结论**：`experience` 作为一个 **kind** 没有独立语义载荷。它实际想表达的是
"**反复出现的规律**"，而"反复"是**证据条数**的属性，不是节点的类型属性。

### 1.3 另一条被记错的节点（同一批数据）

```json
{"id": "m0002", "kind": "episode", "epistemic": "reported_fact", "observer": "老师",
 "narration": "聊天时老师说起阿露酱居然认真跑去问他怎么帅气地喝苦咖啡……",
 "verbatim": "库呼呼～老师你可千万别告诉她哦", "subject": "阿露", "tags": ["阿露","苦咖啡","牛奶","恶作剧"]}
```

`observer="老师"` 意味着"这是老师说的事"，但 `narration` 写的是**阿露的行为**，
`verbatim` 是**睦月自己**说的话。**"谁经历的 / 谁说的 / 关于谁"三个轴被压进了一条记录**，
而渲染时（`render.py` 的 `_reported_line`）只会加一句"（听老师说的）"——**主体是谁读不出来**。

这是 `subject`（关于谁）与 `observer`（谁说的）在 v2 里**职责重叠**的直接后果。

### 1.4 为什么"打补丁"会来回抵消（四个诉求改的是同一片）

你要的四件事，落点文件**完全重叠**：

| 诉求 | 要动的地方 |
|---|---|
| 澄清 `experience` | `nodes.KINDS/_REQUIRED/validate/normalize` · `store._PREFIX` · `render` 五个分桶 · `recall` 的 kind 过滤 · `digest_registry` 决策表与 parse · `revise` 目标校验 |
| **实体中心化 + 物品/地点/知识** | **同上全部**（新 kind 要过每一道闸）+ `recall` 两级结构 + `render` 分组 + Round B 组织视图 + **新增 Step 1.8** |
| 组合重组 | `revise` 规则引擎 · `store` 不变量 · 新增阶段编排 · `digest_registry` 新动作 · **合并策略按 `nature` 分派** |
| 时间架构 | 每个节点的字段 · `render` 文案 · `recall` 衰减 · `store` 需要时间游标 |

打四次补丁 = 把同一片代码动四遍，且中间态是"半新半旧 schema"（新旧 kind 共存、
时间字段半有无）。**重构一次 = 动一遍 + 带 `schema_version` 迁移**。

**代价现在最低**：全库 13 个节点，迁移脚本几十行；等真跑几百条就不是这个量级。

**而且这四件事互为前提**（不是四件独立的事）：
- 没有实体层，"组合重组"就只能在**自由字符串 subject** 上做比较 → 判不出该不该合并
- 没有 `nature`，"合并策略"就没有判据 → 会把角色内核（`self_image`）当重复项合并掉
- 没有时间，`relationship`（约定）就无法过期 → 只能一直堆着
- 没有实体层，物品/地点的"状态"就要各自造一套 → 就是 v3 初稿那个 `possession` kind

### 1.5 v3 明确**不**重写的东西（保住已建成的资产）

| 保留 | 理由 |
|---|---|
| `events.jsonl` append-only 真源 | 事实主线，v3 不碰 |
| `digested_seq` 水位 / 原子提交 / 快照回滚 | 增量与幂等已正确 |
| `history` 版本化字段 ✅ | 正是 A-Mem 那条"必须版本化"纪律的落地物——v3 要**用它**，不是重塑它 |
| `apply_revision_package` 规则引擎与测试 ✅ | merge/contradict/accrue 逻辑与校验已写好，v3 只补**入口 + 溯源** |
| 上两轮加的观测/降级埋点 | 不动 |

## 2. 节点新概念（实体层 + 经验层 + 四条轴）

### 2.0 为什么引入实体层（诊断 + 用户裁决 2026-09-13）

**v2 的图是"以非 belief 节点为中心"的**：`episode` 是绝对主体，belief 挂在它下面，
彼此之间没有任何边。作为 agent-memory 这没问题；**但对 RP 不对** —— 角色扮演里
最有价值的查询是"老师在她心里是什么样"，而 v2 的结构回答不了。

真实数据（线上 13 节点）给出三条证据：

**(1) `subject` 是自由字符串 → 同一实体裂成多种写法**

```
igusa_haruka  [belief] subject='被老师求助时的反应'
              [belief] subject='向老师敞开秘密基地'
              [belief] subject='对老师肯定的感受'
              [belief] subject='对老师的承诺方式'
asagi_mutsuki [belief] subject='我对老师的心意'
              [belief] subject='我对阿露的看法'
```
同一个"老师"，haruka 用 4 种**侧面描述**当 subject，mutsuki 用"我对X的看法"当 subject。
不是 LLM 不听话——**是引擎没给它一个稳定引用点**，每次都是现场编。
后果：这 4 条 belief 语义上属于同一个实体，结构上却彼此无关，召回时无法一起捞。

**(2) 实体信息其实已经在图里，只是散在 `tags`**

真机 episode 的 tags：`阿露 / 春余×2 / 杂草屋 / 咖啡厅 / 俄罗斯轮盘巧克力 / 联邦理事会 / …`
——**人名、地点、物品全在，但没有节点承载**。换场翻译、物品查表都只能靠字符串匹配。

**(3) `interperson.json` 已经是一张角色实体表**（8 条，带权重 1/2/3）
——实体中心化不是引入新概念，是**把已有的表接进图**。

**(4) 顺带**：线上 `source=experience` 的节点 **0 条** —— 出厂 episode 从未进过 wiki。
所以"出厂基座"目前纯属设计概念，迁移几乎没有历史包袱。

**用户裁决（2026-09-13）**：需要 `self`（自我认知）/ `item`（物品）/
`place`（地点）/ `knowledge`（特定知识）四类实体；**belief 保持多条并存**
（不做"合成一条总结"——理由见 §2.5）。

### 2.1 两层，不是三种东西

```
┌─ 实体层（entity）── 世界里的"持久参照物"：谁 / 什么 / 哪里 / 哪条知识
│     稳定 · 引擎管身份 · 可被引用 · 不承载情感内容
│
└─ 经验层 ────────── 角色视角的"我经历过/我认为"
      episode（发生的事，亲历/听说）
      belief （持久认知，含自我认知/对他人/关系/模式）
```

**关键澄清（用户问题的直接回答）**：

> 引入实体层解决的是**归属与召回**，**不是**内容粒度。

`entity` 节点**不是"把对它的看法装进它"**，而是"给它一个家"——
entity 只存身份与索引（名字/别名/类型/关系阶段），**关于它的看法仍是多个 belief 节点**。

所以**不做**方案 B（把"对老师的看法"合成一条）：
- "对老师的看法"会变成一段**单调增长**的长文本，而 `content ≤200 字`——
  第 20 条经历时要么丢细节、要么写不下
- 每次 update 都要**重生成整段** → 成本高 + **漂移**（A-Mem 的警告正是针对这个：
  "rewriting older notes … without hard versioning is hard to debug and can be unsafe"）
- **矛盾无法表达**：一个人对另一个人的看法**本来就是矛盾的**
  （"依赖他" + "怕成为负担"）——合成一条会把张力抹平，而 **RP 里张力就是戏**

### 2.2 实体层：`entity`

```jsonc
{
  "id": "x0001",
  "kind": "entity",
  "name": "老师",                        // 显示名（中文主名）
  "etype": ["person"],                   // ★ 数组，不是单值（见 §2.4 改进①）
  "aliases": ["sensei", "老师", "他"],    // 归一化用（每角色视角不同）
  "ref": "player",                       // 关联既有 id：interperson / registry / 角色 id（可空）
  "stage": "",                           // 关系阶段词（未来 relationship_view 接这里；引擎裁决）
  "origin": "digest",                    // digest | seed | author
  "story_time": { ... }                  // 首次确立时间（§4）
}
```

**`etype` 取值（用户定，4 + 1）**：

| etype | 指什么 | 真机例子 | 特殊之处 |
|---|---|---|---|
| `self` | **角色本人**（自我认知的归属点） | 唯一一个，id 固定 `x0000` | 必存在：开局自动建，别名 = 角色名 + 自称 |
| `person` | 他人（学生/老师/其他） | 老师、阿露、春余 | 可与 `interperson.json` 对齐 |
| `place` | 地点 | 杂草屋、咖啡厅、联邦理事会 | 与 §10 背景词表/换场翻译天然对接 |
| `item` | 物品 | 俄罗斯轮盘巧克力、写满杂草名字的卡片 | 有生命周期 → 见 §2.6 边状态 |
| `knowledge` | 特定知识（事实/秘密/规则） | "联邦理事会让他做环境调研报告" | **与 `knowledge.yml`（世界观知识库）刻意同名**——把"我知道的事"接进图 |

**为什么 `self` 必须有**：真实 belief 里 **最多的是关于自己的**——
"我这种人配不上老师的帮助"、"对老师肯定的感受"。若只建"他人"实体，
**角色内核将无家可归**（现在它们的 subject 是"被老师求助时的反应"，挂在老师名下，
语义上是错的）。

### 2.3 经验层：`episode` / `belief`

**episode**（形状同 §2.2 旧版，仅新增/改名两个字段）：
```jsonc
{ "id": "m0001", "kind": "episode",
  "title": "老师拜托我调查杂草", "narration": "……", "verbatim": "……",
  "place": "",                     // ★ v3 新增（来源 = place 标注; 见 §2.3.2）
  "tags": ["杂草调查", "报告"], "significance": 0.7,
  "epistemic": "observed_fact", "observer": "",
  "about": ["x0001"],              // ★ v2 的单一 subject → 实体引用列表（可多人同场）
  "story_time": { ... }, "origin": "digest", "event_seq": [30], "links": ["m0005"] }
```

**belief**（⚠️ 相对 v3 初稿有实质变化——`subject` 拆成 `about` + `aspect`）：
```jsonc
{ "id": "m0005", "kind": "belief",
  "about": "x0000",                // ★ 归堆键：指向实体（引擎保证存在、唯一）
  "aspect": "被求助时的反应",        // ★ v2 的 subject 语义降到这里（LLM 自由写）
  "nature": "self_image",          // ★ 第四轴，见 §2.5
  "content": "老师一开口请我帮忙，我会先……",   // ≤200 字，结论式
  "growth": "……", "pattern": "", "keywords": ["老师", "自我怀疑"],
  "occurrences": 3,                // 引擎数（= 支撑 episode 条数）
  "significance": 0.6, "epistemic": "inferred_belief",
  "history": [ { "episode_id": "m0001", "content": "…", "ts": "…" } ],
  "superseded_by": "", "story_time": { ... }, "origin": "digest",
  "links": ["m0001"] }
```

**`about` + `aspect` 的拆分是这一版的核心**：

| 字段 | 谁管 | 作用 |
|---|---|---|
| `about` | **引擎**（LLM 只能从已渲染的实体列表里选，或显式提议新建） | **保证归堆**——同一实体下的 belief 天然成为一组，"四种写法"从根上消失，**不靠提示词劝** |
| `aspect` | LLM | **保留区分度**——每条看法讲的是哪个侧面，自由命名 |

这两者缺一不可：只有 `about` → 丢侧面（"对老师的看法"含糊）；只有 `aspect` → 就是现在这样裂开。

**替换 `player` 特例**：v2 用硬编码 `subject == "player"` 表达"玩家画像"
（`is_player_experience`/`PLAYER_SUBJECT`，7 处消费）。v3 改为
`about == 玩家实体 id` + `nature == "pattern"` —— **同一套词汇，取消特例**。

#### 2.3.1 episode 的**粒度与字段规格**（2026-09-13 对标 AgentGal 实测）

**对标来源**：`D:\MYCODE\github\AgentGal`（本地源码）的 `EpisodeMemory`
（`models/memory.py`）与其**索引文本构造**（`repository/vector_store.py:482-496`）。

|---|---|---|---|

| 日期/时间 | `date` / `time` | `ts`（壁钟，**不进 embed**） | 🔧 **计划内**（`story_time`，§4） |

| 归属者 | `memory_owner` | 隐含（每角色一份） | ✅ 无需 |

**① `narration` 再长一点**（用户裁决 2026-09-13）

现状 51~191 字，实测 **embed 文本 87~238 字**。用户判断**可以再长**——采纳。
两条支撑：

- **AgentGal 的 `content` 比我们长**（它把整段对话摘要下来），而它的检索效果是标杆
  → **更长的正文没有害处**
- **长度本身就是检索质量**：更长的正文 = 更多可匹配的语义面
  → 对"排序取 top-k"（无阈值，Q31）的范式来说，**长文本只会让排序更准**

⚠️ **但这与 Q24 有一个必须说清的边界**：Q24 定了 **episode 注入 writer 时只给标题**。
所以"narration 变长"**不影响 writer 的注入体积**（见到的仍是标题）；
它影响的是 ① **embed 文本长度** ② **digest Round B 的素材量**。**两者都是好事。**

**② `title` 加长到 12~20 字**（v3 新增职责导致）

v2 的 title 只当"回放标题 / 决策表引用"，8~10 字够用。但 **Q24 定了 episode 注入
writer 只给标题** → title 要**独立承担"这事讲过了，别重复"**的职责。
8~10 字很可能不足以让 LLM 判断"这条和我现在要写的是不是同一件事"。

**验收标准（可测）**：只给 title，看 LLM 能否正确判断"这段剧情与既有 episode 是否重复"。

**③ embed 文本改成"分段带标签"（学 AgentGal 的"高密度字段拼装"）

AgentGal 的 `_embed_text` 是**四段带标签拼装**（注释原话：*"决定拿哪些高密度字段去索引，
避免只靠正文丢失检索锚点"*）：

```
title
keywords（、连接）
日期：…；时间：…；地点：…；在场：…      ← 元数据段（空则跳过）
content
```

Live2Be 现状是 `narration + verbatim + tags` **平铺**（`recall.py:_embed_text`）。
**建议改为**（照抄这个形态）：

```
{title}
{keywords}
地点：{place}；日期：{story_time}；在场：{about 的实体名}；参与者：{…}
{narration}
{verbatim}
```

**为什么带标签更好**："那天在杂草屋"这类 query 能**直接命中** `地点：杂草屋`，
而平铺文本里"杂草屋"只是一段话里的一个词。**标签本身就是检索锚点。**

> ### ⚠️ 撤回一条：**情绪行不进 embed 文本**（2026-09-13 实测后）
>
> 本节初稿曾把 `情绪：{...}` 也列为一段。**撤回**——那是我顺着 AgentGal 的
> "高密度字段拼装"外推的，而 **AgentGal 拼的是 `日期/时间/地点/在场`，没有情绪**。

> 三个结果：

> | 变体 | 两两余弦 mean / max | 情绪型 query top1 |
> |---|---|---|
> | A baseline（`narration+verbatim+tags`） | **0.5595 / 0.6747** | 1/4 |
> | B `+情绪键串`（标注层直接产物） | 0.6853 / 0.7446 | 2/4 |
> | C `+键串+强度` | 0.7214 / 0.7836 | 2/4 |
> | D `+手写情绪叙述`（**照着 query 写的**，上界） | 0.5964 / 0.7207 | 3/4 |

>    "情绪"在向量空间里是一个**话题簇**，不是可微分量。四条 episode 盖上同类情绪戳
>    就互相靠近，**判别力被系统性吃掉**。
> 2. **极性在向量空间里是错的**：`A(她终于笑了，开心的笑)·B(她哭了，最难过的哭)
>    = 0.4986`，**高于**二者各自与中性文本（0.4603 / 0.3864）——抓的是"这段在讲情绪"。
> 3. **最反直觉**：`[情绪] 她失控的那一瞬间` 的 rank，B(`+键串`) = **4**（比 baseline 的 3 更差），
>    而板里真的躺着 `outburst` 这个键。D 之所以赢，是因为我**照着 query 的字面写了"真正的笑"**
>    ——**那是词面命中，不是情绪理解**。
>
> **外部印证**：调研的干净结论是**九套主流 agent 记忆系统中零套有显式 `emotion` 字段**；
> 唯一成体系的两套（**Emotional RAG** arXiv:2410.23041 / **Sentipolis**）**都把情绪放进
> 独立的向量空间或离散标签，从不混进语义 embedding 文本**。Emotional RAG 用
> `score_emotional = 1 − cosine(emotion_q, emotion_m)`，且论文实测**相加融合是唯一会变差的
> 那一种**。
>
> **落法**：embed 文本 = **内容 + 元数据锚点**；情绪走**独立结构化通道**（§3.3 的
> `emo_span`/`emo_int` + 情感召回的 family 匹配）。

### 2.4 四条轴（v2 只有两条，且被压在一起）

```
轴一 kind      —— 节点的"形状"      : entity | episode | belief
轴二 epistemic —— "我怎么知道的"    : observed_fact | reported_fact | inferred_belief | speculation
轴三 etype     —— 实体是"哪种东西"  : self | person | place | item | knowledge   （仅 entity）
轴四 nature    —— 认知"是哪一类"    : self_image | other | relationship | pattern （仅 belief）
```

### 2.5 改进②：第四轴 `nature`（为什么必须加）

真实那 4 条 belief 混着**四种性质不同的知识**，而它们的**合并规则完全不同**：

| nature | 例子 | 合并规则 | 为什么 |
|---|---|---|---|
| `self_image` | "我这种人配不上老师的帮助" | **不合并**——允许长期并存甚至互相矛盾 | 这是**角色内核**；合并等于抹掉人设张力 |
| `other` | "老师总靠浓缩咖啡硬撑" | **同类合并**（同一 about+aspect 的多条经历 → update/accrue） | 关于他人的判断会被反复观察到，该收敛 |
| `relationship` | "约定一起去看杂草" | **有时效，过期退场** | 约定会履行或失效；现在没有这个机制（§4 时间架构支撑） |
| `pattern` | "老师总说摸鱼"（= v2 的 experience 本义） | **计数聚合**（`occurrences`） | "反复出现"是证据条数的属性 |

**只按 `about` 归堆的缺陷**：会把 `self_image`（自我认知）与 `pattern`（他人习惯）
放进同一个桶里，而前者**不该被计数合并**、后者**应该**。
所以 `nature` 是**合并策略的判据**，不是标签——它决定这条 belief 在 V3-6
深度重组阶段**能不能被 merge**。

**默认值**：LLM 未填 → 按 `about` 推断（`about == self` → `self_image`；
有关键词线索"约定/答应/一起" → `relationship`；`pattern` 非空 → `pattern`；
否则 `other`）。引擎可覆盖，且**判错不致命**（最坏是合并策略取默认）。

### 2.6 改进③：边状态 —— 通用化 v3 初稿的 `possession`

v3 初稿给 `possession` 设计了独立 kind + `state`/`holder` 字段。**引入实体层后
这套变得多余，而且不通用**：

| 情况 | 用 possession kind | 用边状态 |
|---|---|---|
| 物品转手 | `state=given_away` | ✅ 同 |
| 地点变得不可去（毕业了/封锁） | ❌ 无表达 | ✅ `state=lost` |
| 知道了某个秘密 | ❌ 无表达 | ✅ `state=held`（knowledge 也"持有"） |
| 忘记了 | ❌ 无表达 | ✅ `state=forgotten` |

**推荐形态（待确认，但必须现在定形状）**：把"角色与实体的当前关系"表达为
**角色 → 实体的边状态**，而不是物品专属字段：

```jsonc
// 每角色一份（与 wiki.jsonl 并列，不改 entity 节点本身）
// soul/bonds.jsonl 或 wiki.meta.json 的 relations 段
{ "entity": "x0003", "state": "held",       // held | lost | given_away | consumed | forgotten
  "obtained": { "episode": "m0001", "story_time": {...} },
  "lost":     null,                          // 同构
  "updated_at": "壁钟（审计）" }
```

**为什么不能把状态放 entity 节点上**：entity 是**世界级**的（一个物品只有一件），
而"持有"是**角色级**的（换角色视角完全不同）。放错层会让多角色共享世界时互相污染。

**与 §2.2 初稿的 `possession` kind 的取舍**：v3 初稿把 `possession` 立为 kind 的
四条理由（有身份/有状态机/有时间区间/有资产锚点）**全部由
`entity(etype=item)` + 边状态满足**，且少一个 kind。资产锚点
（`assets/illustration/{char}/{outfit}/possession/`）改为与 `entity.id` 对应。

#### 2.6.1 ⚠️ 边状态与 `links[]` / `contradictions[]` **不是一回事**（2026-09-13 澄清）

用户疑问："我们不是有 `links[]` 和 `contradictions[]` 列表吗？"——**三者回答三个不同问题**：

| | 存在哪 | 回答什么 | 形态 |
|---|---|---|---|
| `links[]` | **节点上** | 这两条**记忆**有关系 | 节点 ↔ 节点 |
| `contradictions[]` | **节点上** | 这两条**记忆**互相矛盾 | 节点 ↔ 节点 |
| **边状态**（本节的） | **角色 ↔ 实体** | 这个**东西/地点/知识**现在在她这儿是什么状态 | **不是节点间关系** |

**为什么 `links` 永远替代不了它**：

> **遗忘不产生节点，它抹掉一个节点**——而"忘了"这个**状态**必须存在某处，
> 否则系统不知道"她曾经知道"。

**为什么也不能存在 entity 节点上**（本节已述）：entity 是**世界级**的（一件物品只有
一件），而"持有/失去"是**角色级**的——"她以为扔了、其实还在"在多角色共享世界时
必须能表达，放错层会互相污染。

**存储形态（Q9 裁决 2026-09-13：暂缓，但定下判断原则）**：

> **它本该是派生数据**——从事件流推"每个实体对该角色的最新状态"。
> 落文件只是**物化**（缓存），不是第二真源。
> 所以 Q9 的真问题从「放 `soul/bonds.jsonl` 还是 `wiki.meta.json`」变成
> 「**要不要物化、物化在哪**」——留给 V3-5，与"实体层落地形态"一起定。

**为何仍倾向物化**：① 召回要用它做过滤/加权，每轮现推要扫全事件流
② 它是"当前状态"，突变语义，与 append-only 的节点层不同构
③ 物化失败可重算（因为是派生的）——所以物化没有"双真源"风险。

### 2.7 改进①+④：`etype` 用数组 + 别名软合并

**改进①：`etype: list[str]` 而非单值。** 一个实体天然可属多类，
单值会强制 LLM 二选一：`白守`既是 person 又是 group；`圣园未花`是 person，
但作为学生会长出现在 belief 里也带 group 语义。而 `etype` 是**滤镜**不是**身份**——
`["person", "group"]` 同时满足两种检索。渲染取首元素当主标签。

**改进④：实体合并用"别名软合并"，不做硬删。**
v3 初稿让 merge 保留源节点（I7）。实体合并同理且更严格：

```
LLM 提议 merge(x0007 → x0001)
  → 只做两件事: ① x0001.aliases ∪= x0007.aliases ∪ {x0007.name}
                ② x0007.merged_into = "x0001"（**节点保留**）
  → 此后 LLM 看到的是 x0001（含全部别名, 归一命中率上升）
  → 旧的 about=x0007 的 belief **不改写**（append-only 精神）;
    召回时经 merged_into 一跳重定向到 x0001
```

**为什么硬删是坑**：实体是**被引用的**——删掉它，指向它的 belief 全变悬空
（`store.audit` 能查出来，但已经丢了解释信息）。而软合并**只增不改**，
可回滚、可审计，与项目既有哲学一致。

### 2.10 改进⑤：实体携带"总体看法"（`overview`）—— 修订 §2.1 的裁决

§2.1 曾裁决"**不做**对 X 的单条总结"。**用户 2026-09-13 细化后修订**：
把总结放在 **entity 节点的一个受限字段**里，与"多条 belief 并存"**不矛盾**——
因为它是**受限的、可版本化的一个视角**，而不是 belief 的替代品。

```jsonc
{ "id": "x0001", "kind": "entity", "name": "老师", "etype": ["person"],
  "overview": "依赖他，却又怕自己成为他的负担——所以我总在答应之后才敢后悔。",
  "overview_history": [ { "content": "…", "ts": "…", "episode_id": "m0005" } ],
  "overview_updated_by": "m0008" }
```

**为什么这次可以（上一轮我反对的三条理由都被化解了）**：

| 上一轮的反对理由 | 用受限字段后 |
|---|---|
| 会变成无限增长的长文本（`content ≤200` 写不下） | **`overview` 同样 ≤200 字**，是有界总结，不是累积 |
| 每次 update 重生成整段 → 成本 + 漂移 | `overview_history` 版本化（**复用已有 `history` 模式**）；漂移可审计、可回滚 |
| 矛盾无法表达，会把张力抹平 | **张力恰恰属于 overview**（"依赖他 + 怕成为负担"正是总体感觉该有的样子）；具体侧面仍由多条 belief 承载——**两者是"总"与"分"的关系** |

**它是第 7 个视角**（在 §2.2 的 6 个字段之外）：`name`/`etype`/`aliases`/`ref`/`stage`/`overview`。

**渲染顺序随之变成人回忆的自然顺序**：
```
【总体感觉】 entity.overview            ← 先给判断（1 行）
【具体认知】 该 entity 下的 belief 按相关度排序   ← 再给侧面（n 条）
【具体事件】 支撑它们的 episode                ← 最后给证据（按需展开）
```
所以 `overview` **不只是省了一个节点，它让召回有了"入口摘要"**——
BFS 第一层就有内容可给，而不是"先展开才看到东西"。

**更新时机**（不是每轮都改）：`nature=other` 的认知被 update/accrue 时顺带重写；
`self_image` 变更时也重写（自我整体感觉会变）。**限定 ≤1 次/次 digest**。

### 2.11 改进⑥：**废弃人称字符串替换**（`_me`）

**用户裁决（2026-09-13）**：不要依赖 engine 切第一人称，会丢重要信息。

**实测（真机数据 + 构造用例）**，`_me` 是**无差别 `str.replace`**：

```
「遥香，你过来一下。」老师朝我招手。  →  「我，你过来一下。」老师朝我招手。   ← 呼格被吞
阿露说「遥香那家伙又在擦地了」。     →  阿露说「我那家伙又在擦地了」。    ← 指代污染
遥远的天空下，遥香抬头看着云。（别名含单字"遥"时）→ 我远的天空下，我香抬头看着云。 ← 子串误伤
```
`_me`（`render.py:323`）把 `char_name + 全部 aliases` 一次性替换成"我"，
**只声明了"她/他"不替换，没有任何子串保护**。而 docstring 自述"yml 原文多用简称"
——正说明这个函数的用武之地是**第三人称的出厂 yml**。

**关键事实：v2 运行期根本不需要它。** 真机 4 条 episode 的 `narration`
**本来就是第一人称**（"想拜托**我**帮忙"），`_me` 对它们**是空操作**。
引擎转换只在出厂 yml 那条路上真正干活。

**v3 的做法**：

| 来源 | 人称 | 处理 |
|---|---|---|
| 运行期 episode/belief | **第一人称**（Step 1 的提示词已要求"用角色的视角写"） | **原样注入，不做任何替换** |
| 出厂 yml（`experience.yml`） | 第三人称（作者写的档案） | ① 走**已有的** seed 改编管线（`llm/prompts/seed_digest.md` 的"第一人称转换"是 LLM 任务，不是字符串操作，已归档但可复用）② 未改编的原文注入时**加视角声明**（见下） |

**视角声明（替代替换）**：注入段头加一行

```
【角色记忆】（下列均为她自己的记忆；"她"= 我，文中出现的人名按当前视角理解）
```
——**让 LLM 做视角解释**（它本来就擅长），而不是让引擎做字符串手术。

### 3.2 v3 召回管线（实体为"车道"）

引入实体层后，召回从"在一个扁平池子里打分"变成**两级 + 车道配额**：

```
query（本轮情境文本）
  │
  ├─ ① 实体级召回（先决定"这轮关于谁/什么"）
  │     通道E1 具名线索：query 里出现的实体名/别名（含 merged_into 重定向）★ 最强信号
  │     通道E2 语义：embedding(query) × **实体**向量（name+aliases 合成的代表向量）
  │     通道E3 在场保底：本场 episode 的 about 里的实体（剧情正在讲谁，必进）
  │        ▼  合并去重 → 实体打分 = w_cue·线索 + w_sem·cos + w_imp·该实体下最高 sig
  │        ▼  取 top-k_entity（建议 3~5）——**这就是"召回车道"**
  │
  ├─ ② 车道内召回（在每个实体内部取具体的认知/经历）
  │     通道B1 语义：embedding(query) × 该实体下 belief/episode 向量 → top-k
  │     通道B2 词面：BM25 / tags∩ / aspect 命中
  │     通道B3 珍贵保底：该实体下 significance ≥ 0.8 且未命中 → 补 n_precious  ✅ 设计已有
  │     通道B4 随机摘段：30% 珍贵加权 / 70% 对数正态(剧情年龄)加权              ✅ 设计已有
  │        ▼  融合打分 = w_rel·relevance + w_time·recency + w_imp·importance
  │             relevance = w_vec·cos + w_lex·bm25_norm            （AgentGal 同构）
  │             recency   = 双信号：剧情年龄衰减 × 上次被想起的年龄衰减
  │        ▼  **每实体配额**（每车道最多 n_per_entity，防一个实体洪泛）
  │
  ├─ ③ 跨实体补充（保证"没被 query 提到但对角色重要"的东西不饿死）
  │     通道C1 珍贵保底：全库 significance ≥ 0.8 的 belief（跨实体，补 n_precious）
  │     通道C2 时间锚：最近的 episode（保持"最近发生了什么"的连续性）
  │
  ▼
  ④ **BFS 逐层展开**（§3.5）: entity → belief → episode, 每层配额, 深度上限 2
  ▼
  按 kind 配额截断（防 episode 洪泛把 belief 挤出去）→ 渲染（§3.6 顺序）
  ▼
  写召回台账（§3.9, 增记 entity 命中）+ 回写 last_recalled（剧情时间）
```

**为什么"实体为车道"是这一版的关键**：v2 是在**扁平池**里按 significance 取前 N，
于是"关于老师的 4 条 belief"里只有排前面的进得来，其余永久读不出（§3.1）。
实体车道把"该给谁"和"给多少"解耦：**先按 query 选人，再在这个人内部按 query 选事**。
`COGNITION_CAP=12` 那个全局漏斗随之退役（见 §8-5）。

**防扇出（必须做，否则新结构会比旧的更糟）**：
若"老师"下挂 20 条 belief，无配额的展开会把它们全拉进上下文。
三道闸：① `k_entity` 限制车道数 ② `n_per_entity` 限制单车道条数
③ 全库上限 `cap`。三个值都进 `settings.toml [recall]`（V3-0 已建好旋钮面）。

**关键改动 vs v2 设计**：
1. **两级结构**（实体级 → 车道内）+ 车道配额（v3 新增）
2. **`recency` 用剧情时间，不用壁钟**（§4 落地后才有意义）
3. **`last_recalled_at`（剧情时间）** —— 刚念过的自然下沉，解掉"每轮重复念同一件事"
4. **双信号 recency**（事件年龄 + 上次被想起的年龄）—— 对齐 AgentGal
5. **kind 配额** —— 防 episode 洪泛（v2 靠固定 cap，v3 靠配额）
6. **打分是混合表达式矩阵，不是单阈值**（§3.3，用户裁决）
7. **随机旁路 + 死记忆回捞**（§3.4）
8. **BFS 逐层 + 层内 `entity→belief→episode` 顺序**（§3.5）
9. **链接展开有向且有类型**（§3.3 末）——回应用户 c/d

### 3.3 打分矩阵：**2×2 行列式**（用户裁决 2026-09-13，**上位替代线性加权和**）

**用户 2026-09-13**：*"我正在构思一个二维矩阵 A：A[0][0]=SIG、A[0][1]=-emo、
A[1][0]=emo-intense、A[1][1]=time；这样这个矩阵的行列式就是一个天然权重。"*

**采纳，且它替掉了本节初稿的线性加权和。** 记法收敛为（`emo` **无符号**，见下）：

```
A = [[SIG,      emo_span],          ← 行一：重要性 × 年龄
     [emo_int,  TIME    ]]          ← 行二：情绪量级 × 峰值强度

det(A) = SIG·TIME + emo_span·emo_int          ← 恒 ≥ 0（四格全部归一化到 [0,1]）
```

#### 为什么它**不是**任何加权和（这是它唯一真正特别的地方）

`score = Σ wᵢ·signalᵢ` 里**每个信号独立贡献**；`det` 是**两个乘积之和**——
**乘积里一个因子为零则整项清零**。于是行列式表达的是**两组合取条件**：

| 项 | 含义 | 什么时候最大 |
|---|---|---|
| `SIG·TIME` | 重要性 **且** 还新 | 正是用户指出的 **"SIG 与 time 天然冲突"** 的调和 |
| `emo_span·emo_int` | 情绪**既跌宕又猛烈** | 一个只猛不跌宕的板（全 `tease`）拿不到高分 |

**"行列式天生是权重"成立的机制**：反对角只贡献**符号**，对角两项就是全部。
所以这个 2×2 **只能装两对信号**——

> ⚠️ **`relevance` 装不进去。** 它走另一条路：**先按语义/实体取 top-k 做闸门**，
> 再在闸门内按 `det` 排序。与调研中 PsychoAgent 的"语义预选防住强烈但无关的
> 记忆"（CRR 0.933 vs 消融 0.500）同形。RAG 不是矩阵的一个格子，是**矩阵的前置闸门**。

#### ★ 四格各自是什么（含两处口径修正）

| 格 | 值 | 谁产 | 口径 |
|---|---|---|---|
| `SIG` | `significance` | **LLM（Round A，已有）** | 行为锚点——"改不改变认知"。**不是情绪强度** |
| `TIME` | `exp(-age/half_life)` | **引擎**（§4 剧情时间） | 年龄衰减 |
| `emo_span` | 板内 valence 的**极差** | **引擎查表** | ★ **不是均值** |
| `emo_int` | 板内**峰值**强度 | **引擎查表** | 作者注释分档（1~5 → 归一） |

**`emo_span` 用极差不用均值——这一条是实测逼出来的，不是偏好**（2026-09-13 真机探针）：

| episode | `emo` = 均值 | → `det` | `emo` = 极差 | → `det` |
|---|---|---|---|---|
| haruka **m0003**（含 `outburst→smile`） | −0.07 | **0.567（第三）** | **+1.80** | **9.900（第一）** |
| haruka m0002 | −0.03 | 0.750 | +0.70 | 2.950 |
| haruka m0001 | −0.38 | **−0.425（垫底）** | +0.70 | 2.800 |

**均值把弧抹平了**——全章最重要的一条被排到第三、另一条拿负分。
**而极差字面就是"这一刻情绪有多跌宕"，且天然非负**，不需要额外符号约定。
矩阵在这里起的作用是**强制口径清晰**：`emo` 必须是一个"能与峰值强度相乘"的量，
而"均值 × 峰值"没有意义。

#### ★ `emo` 必须**无符号** —— 这是裁决，不是偏好

若 `emo` 带极性（负 = 负面情绪），`emo·emo_int` 会**减分**：

```
emo=−0.38, int=3  →  det = SIG·TIME − 1.125 = −0.425        （haruka m0001 垫底）
SIG=0.9, emo=−0.8, int=5  →  det 恒为负, 且随年龄越来越负
```

**后果**：负面情绪的记忆被系统性埋掉（"遥香被老师交代了重要任务"垫底）。
**两种语义给出相反排序，不能两全**。裁决：

> **`emo` = 非负的情绪量级（极差）；极性（valence 的符号）属于情感召回链路的
> "同频"判据，不属于权重判据。** 同一条数据在两个位置承担两种角色，不混用。

**修法连带**：四格**必须全部归一化到 [0,1]**，否则量纲失衡。未归一化时实测
情绪项占比 **89%~93%**——`SIG`/`TIME` 沦为舍入误差，行列式退化成"情绪分 + 一点 SIG"。
归一化后（`emo_span/2`、`(emo_int−1)/4`）：haruka m0003 `det=1.800`（情绪项 50%）、
m0001 `det=0.875`（20%）、mutsuki m0001 `det=1.470`（44%）——**排序不变，四个信号
全部真正生效**。这是矩阵能用的**前提**，不是优化。

#### ★★ `emo` / `emo_span` 由**引擎派生，LLM 一个都不输出**

**问题**（用户 2026-09-13）：*"LLM 如何输出 emo && emo-span？"*
**答案：不输出。** 两者都是**板级统计量**，而板的情绪标签**已经在真源里**。

```
板（事件流里的 bond 事件）
 └─ payload.paragraphs[i].emotion   ← 标注层已产的键序列（真机 69 条记录实测可用）
      │
      ├─(作者分级表: 键 → valence, intensity)─→ emo_span = max(v) − min(v)
      │                                          emo_int  = max(intensity)
      └─ 而 Round A 的输入时间线**本来就带这些键**（renderer.py:297-299）
```

**外部依据**：调研的干净结论是**九套主流 agent 记忆系统里零套有显式 `emotion` 字段**；
唯一成体系的两套（Emotional RAG / Sentipolis）**都把情绪放进独立的向量空间或离散标签，
从不交给摘要 LLM 自由打分**。我们自己上一轮的实测也印证同一件事——把情绪串塞进
embed 会使 episode 两两相似度从 **0.5595 → 0.6853**（空间塌陷），
且"最开心"与"最难过"的余弦 **0.4986 高于**它们各自与中性文本的距离（0.4603/0.3864）。

**所以 LLM 在这场戏里只有一个职责：指位置，不打分。**

| 谁 | 做什么 | 为什么是它 |
|---|---|---|
| **引擎** | `emo_span`/`emo_int` 查表聚合 | 纯算术，零幻觉面，**完全可重放** |
| **引擎** | 板级 affect **物化缓存**（一次算，索引表里存） | §3.9 索引表的正当用途（可从真源重建） |
| **Round A** | 只产**板指针**（`event_seq` = 板 seq 列表） | 见下 §3.3.1 |

**退化路径是安全的**（这是结构自带的性质）：板指针缺失 → `emo_span = emo_int = 0`
→ 第二行整行为零 → `det = SIG·TIME`。**矩阵自动退化为一维，不报错、不污染。**

**`nomal` 的已知污染**（§6.4.1）：三处代码把它当失败回落值
（`emotion_annotate.py:41` / `emo_text.py:41` / `webgui/bond.py:2410`），
真机实测 mutsuki **0/53**、haruka **3/40**——**它不是"平静"的度量**。
分级表里 `nomal` 计入 valence=0/intensity=1（中性），但**必须与真 `nomal` 区分不出**
这一点要在台账里可见，否则"情绪平淡"与"标注失败"会混成同一个信号。

#### 3.3.1 板指针：LLM 唯一的情绪相关输出（**一个字段**）

```
Round A 输出（在现有 schema 上加一个字段，不是两个）:
  "event_seq": [19, 21, 23, 25]     ← 本条 episode 吃哪几板（抄时间线的 [seq N]）
```

- **LLM 只做选择**："这一段里哪几板属于这件事"——时间是 `[seq N]` 前缀，
  **这是抄行号，不是评分**
- **引擎做校验**：`event_seq ⊆ 本段 bond 事件的 seq 集`（与 `evidence.quote`
  的"逐字来自时间线"同一套防幻觉思路，`digest_registry.py:264` 已有先例）
- ⚠️ **当前状态：这个字段被禁收**——`_clean_episode`（`digest_registry.py:411-414`）
  把 `event_seq` 列为引擎字段直接丢弃，而 `digest.py:166` 把全部 episode 覆写成
  **常量 `[interact_max]`**。实测 `event_seq=[30]` 而 haruka 的板最大是 25——
  **它指向一条 MMT 消息，不指向任何一板**。见 §2.3.1 与 Q34。
- **归属歧义**（板↔episode 是**多对多**：一个板可被两条 episode 引用，一条 episode

**多板聚合用 `max` 不用 `mean`**——同 `emo_span` 的理由：一条 episode 吃多板时，
**取最跌宕的那一板**，平均会把弧抹平。

| `TIME` | 0~1 | 引擎 | `exp(-age/half_life)` |

**`emo_valence`（−1~+1）与 `arc`（−1~+1）不进矩阵**，只服务情感召回的同频匹配
与叙事形状（见下"未采纳方案"）。

##### ⚠️ 未采纳方案记录：**「约定 `emo` 与 `emo_span` 同号」等价于没做**

用户曾提议：*"维持 `emo` 的负号，但约定 `emo && emo_span` 同号"*。
**代数验证后不采纳**——在反对角带负号的形态下，两者效果**逐位相同**：

| `emo` | `span` | 同号? | `emo·span` | `det` |
|---|---|---|---|---|
| +0.8 | +0.6 | ✅ | **+0.48** | **1.38** |
| −0.8 | −0.6 | ✅ | **+0.48** | **1.38** ← 一模一样 |
| +0.8 | −0.6 | ❌ | −0.48 | 0.42 |
| −0.8 | +0.6 | ❌ | −0.48 | 0.42 |

**负 × 负 = 正**，符号在乘法里被吃掉。所以"同号约定"**就是"`span ≥ 0`"的另一种写法**，
且更脆：前者是**一个字段一个边界**（单测一行），后者是**跨两个 LLM 输出字段的耦合约束**
（模型给异号就得丢弃或夹紧）——**多一条失败路径，换零收益**。故直接**声明 `emo_span` 非负**。

> ★ **同时确认一件承重的事**：那个负号**必须待在 `A[0][1]`**。若写成
> `A = [[SIG, +emo], [emo_span, TIME]]`（反对角不带负号），同号会让 `det` **变小**
> ——`emo=+0.8, span=+0.6 → det = 0.9 − 0.48 = 0.42`，**情绪越强分数越低，正好反了**。
> **行列式展开时，反对角是唯一决定第二项符号的位置。** 用户最初把 `-emo` 放在
> `A[0][1]` 是**对的**。

**动机**：现有全部信号都是**单调累积量**——`significance` 0~1、`TIME` 0~1、
`span`/`int` 非负。**没有一个能表达"关系变坏"。**

**现状（实测，四处硬闸门，比预想多一处）**：

`digest_registry.py:267` 的 schema 注释）——**告诉 LLM 负值何时给、给多少**，
并明写"别为剧情起伏随手给负分"（防剧作本能污染数值）。

**要推翻的口头契约**：`affection_calc.py:12` 的注释 *"经验只增不减（好感不降——
BA 无降好感机制）"*。

**边界**：**bond 链完全不产 `affection` 事件**（实测只有 momotalk 的 digest 产）——
所以好感的真源目前只覆盖 MMT 线。

**⚠️ 用法：不进矩阵。** 塞进去会与 `arc` 同型翻车——好感为负 → 第二项为负 →
**"她讨厌我的那段日子"被压制**，而那段恰恰最该记住。

**用法 = 同频召回的第二个轴**（调研里唯一有生产实现的那套，
[`emotional-memory`](https://github.com/gianlucamazza/emotional-memory)）：

```
mood_congruence = 1 − |aff_now − aff_at_encoding| / 量程        ← 用绝对差, 不用有符号乘积
```

**用绝对差而非有符号乘积的理由**："关系回到原点"也算同频，符合直觉；
且有符号乘积会重现同一个负分坑。

```
她讨厌你时（exp 低）形成的记忆
  → 现在 exp 高  → congruence 低 → 不易想起
  → 又跌回去    → congruence 高 → 那段记忆浮上来
```

**"关系变坏时，坏日子的记忆会回来"——现在完全做不到，带符号一句话就给。**

##### 归一化：`aff01 = tanh(exp / 5000)`

- **`tanh` 保号、单调、饱和**，一条式子；`exp=0 → 0.0`（中性）
- **尺度不敏感**：同频只关心**差值**，不关心绝对量级；5000 exp ≈ level 5~6（可调旋钮）
- ⚠️ **不追求与 mood 同精度**：好感是**慢变量**，`|aff_now − aff_enc|` 本来就小。
  **真正需要细分辨率的"心情"是另一个量，本设计不假装它能顶替。**

##### 语义冲突（必须写下来）

**好感 ≠ 心情**：好感是关系状态（累积、慢变、单向为主）；心情是当下情绪
（流动、快变、可正可负）——"今天很糟"可以发生在好感很高的时候。
**所以"好感负数"给的是"关系变坏"（真实且值得做），不是"心情不好"。**

##### `aff_at_encoding` 落位：**episode 节点**

- **是快照，不是新信息**——真源仍在 append-only 的 `affection` 事件
  （`load_affection_from_events(events, up_to_seq=…)` 已经能按 seq 算出来）
- **落节点的理由**：① 写入时定、之后不变（与 `event_seq` 同性质，非突变态）
  ② 省掉每次召回重放事件流 ③ 与 Q9 的"突变态才进物化层"一致
- ⚠️ **与"节点是 append-only"不冲突**：它是创建时确定的值，**永不改**
- ✅ **已落地（提交见 §9.4）**：`BrainNode.aff_at_encoding: float | None`；
  `digest_segment(..., aff_at_encoding=)` → `_create_a_nodes` 写入；
  调用方 `momotalk._inject_brain` 按 **`up_to_seq=store.digested_seq`** 算
  （只算**已消化**的部分 = "写这些记忆那一刻的好感"）
- ★ **`None`（未采集）与 `0.0`（中性）必须可区分**——`to_dict()` 的
  "空值省略"规则里 `0` 会被省掉，故该字段**单独用 `None` 做哨兵**：
  落库条件是 `is not None`，而坏值/越界走 `_opt_clamp01` → `None`
  （**坏值不等于"中性"**）。否则旧档会在召回里冒充"当时关系中性"，
  同频匹配直接捞出一堆假阳性。

#### 链接展开：有向 + 有类型（回应用户 c/d）

`links` 现在是**无类型字符串列表** → 必须先加类型。而**方向比类型更关键**：

| 边 | 方向 | 展开规则 | 风险与对策 |
|---|---|---|---|
| **合同/支撑**（`links`） | **有向：belief → 其支撑 episode** | 被召回时**直接**支撑也召回；**不再往下**（用户 c） | ⚠️ **反向绝不能展开**：一条 episode 常被多条 belief 引用，反展开会让"1 条召回变 6 条"。**规则：`links` 只向下**（I15） |
| **矛盾**（`contradictions`） | 无向 | 直接矛盾 + 矛盾的矛盾（**两级**，用户 d） | ⚠️ A⟂B、B⟂C 时 **C 未必 ⟂ A**（可能 C≈A）。对策：边带 `kind`（`direct`/`transitive`），遍历时带"已反向走过"标记 |
| **归属**（`about`） | 有向：node → entity | 不靠展开（车道已由实体层决定） | — |

**为什么矛盾比合同展开更深**：矛盾是**低冗余**高价值信息（"同一个人的两个相反侧面"），
而支撑同一 belief 的 episode 之间高度冗余（往往在讲同一件事）。
**深矛盾、浅合同** —— 这个不对称成立，采纳用户 c/d。

### 3.4 随机旁路与死记忆回捞（回应用户 b 的"随机性旁路"）

**问题**：任何"按相关性取 top-k"都会**固化**——热门条目越召回越容易被再召回
（accessibility 上升），冷门条目永无出头之日。而人的记忆不是这样：
**人会突然想起八竿子打不着的事**。这正是 `recall_subgraph` 里"随机摘段"通道的本意，
但它**零生产调用**。

| 机制 | 做什么 | 参数（进 `[recall]`） |
|---|---|---|
| **随机旁路** | 每轮抽 `n_random` 条**不看 relevance**（只在 sig/年龄加权下抽） | `n_random`（建议 1） |
| **死记忆回捞** | 长期未召回（`story_age − last_recalled > 阈值`）的条目**强制进候选** | `revive_after_days`（建议 30 剧情日）、`revive_k`（1~2） |
| **探索扰动 ε** | 打分末尾加小噪声，让边际条目有机会 | `explore_eps`（0.02~0.05） |

**死记忆 ≠ 低分记忆**：前者是"**曾经重要但很久没被想起**"（`significance` 高、
`last_recalled` 很旧），后者是"本来就无关"。**只回捞前者**——否则是捞噪声。

### 3.5 遍历策略：**BFS + 层内 kind 顺序**（回应用户 e）

**用户 2026-09-13**：*"DFS 可以看到 belief-episode 链路，而 BFS 可以逐层展开，
先看 belief 再看 episode"*。

**采纳 BFS**：
- **与"每层配额"天然契合**（DFS 一头钻到底，配额会变成"先到先得"）
- **层内顺序 `entity → belief → episode` 就是"先结论后证据"**，也正是 §3.6 的渲染顺序
- DFS 的价值（顺一条链路走通）由**合同链接的定向展开**局部实现 ——
  "belief + 其支撑"本来就是一条两跳链，不需要全图 DFS

```

depth 1 : 这些 entity 下的 belief（§3.3 打分, 每实体配额）

```
**为什么上限是 2**：`entity → belief → episode` 已覆盖"总-分-证"三层，

## 4. 时间架构（v3 新增的第二条主线）

> 本节 2026-09-13 重写。触发问题：玩家在现实 12/24 当天和角色玩了多轮、游戏内
> 走了三天"拯救猫咪大作战"，现实只过去半小时 → **游戏内圣诞被错过**。
> 用户结论："这是无法调和的矛盾"——对。下面的架构不是"调和"它，而是**承认它、
> 分别记账、并对撞车点给出确定行为**（Q14–Q19）。

### 4.1 **三层**时间，各有唯一职权（v3 初稿写了两层，不够）

| 层 | 唯一职权 | 载体 | 谁写 |
|---|---|---|---|
| ① **剧情时间** `story_time` 🔧 新增 | **一切面向角色的时间表达**：记忆措辞、季节、日夜、角色作息 | `world_clock.json` 的 slot 游标 + 节点 `story_time` | 引擎累加（LLM 只给粒度） |
| ② **现实日历** `real_clock` 🔧 新增 | **触发器**：生日 / 节日 / 玩家设置的特殊日 | `data/worlds/{world}/real_clock.json` | 工程侧（本机日期），单调不可回退 |
| ③ **壁钟** `ts` ✅ 已有 | 审计 / 排序 / 调试 | ISO 字符串（实测格式正常：`2026-09-07T03:37:20.037943`） | 系统时钟 |

**红线（三条，都是硬约束）**

1. 任何进 LLM 上下文、任何影响召回排序的时间，**必须用 ①**。壁钟只回答"这段是几点跑出来的"。
2. **② 不是真源，是触发器**：它只回答"今天该不该触发某件事"，**绝不**用来计算记忆年龄、季节或日夜。
   旧设计想用现实日期推季节 → 必然与 ① 打架 → 删除该用法。
3. **① 与 ② 永远不试图同步**。它们是两个独立时钟，唯一交汇点是"目标日吸附"（§4.6）。

### 4.2 游标模型：**离散槽位**，不是天数（v3 初稿的"elapsed_days"被否）

理由：LLM 对"第 59 天"毫无时间感，只会把它当数字复读；而"春·第 2 周·傍晚"是它
能直接演的东西。**引擎负责算，LLM 只负责选粒度。**

```jsonc
// data/worlds/{world}/world_clock.json —— 剧情时间唯一真源
{
  "schema_version": 3,
  "anchor": { "year": 1, "month": 4 },          // 作者锚点（开学 = 四月，BA 口径）
  "cursor": { "year": 1, "month": 4, "week": 2, "phase": "昼" },   // 当前游标
  "sim_days": 9,                                 // 引擎累加（工程用途：算吸附距离/衰减）
  "updated_at": "…壁钟…"                          // 审计
}

// 节点级（记忆的年龄由它算）
"story_time": { "year": 1, "month": 4, "week": 2, "phase": "昼", "sim_day": 9 }
```

**粒度定义**（全部由引擎定义，绝不让 LLM 自由发挥）

| 单位 | 取值 | 引擎如何推进 |
|---|---|---|
| `phase`（时相） | `晨` / `昼` / `夕` / `夜` / `凌晨` | 每场互动默认 **+1** 时相（"这场戏之后天黑了"） |
| `week` | 1~4（`month` = 4 周） | LLM 选"过了一周"→ +1 week，溢出进位到 month |
| `month` | 1~12 | 溢出进位到 year |
| `year` | 1 起 | — |

**凌晨归属（用户点名的崩溃点）**：时相**以起点划界，不以 0 点划界**——
`凌晨` 跨月/跨年时**整段归属前一天**（4/30 凌晨 = 4 月第 4 周，不是 5 月第 1 周）。
这样"故事演过凌晨"不会把周/月/年算错，也不会让"昨天说好今天见"变成月份跳动。
`sim_day` 照实数累加（凌晨 +1 天），**只用于工程计算**，不进渲染文案。

### 4.3 谁决定什么（**引擎承担全部时间算术**，LLM 只选粒度）

| 主体 | 决定 |
|---|---|
| **引擎** | ① 累加、进位、**单调性校验**（I6：只增不减）② 夹取（单次跨度 ≤ 30 `sim_day`，非法值 → 走默认 +1 时相）③ 写入游标与节点 ④ **时相的具体含义**（由场景上下文决定"昼"是上午课还是午后） |
| **LLM** | 只输出**离散粒度枚举**：`same`（紧接着）/ `phase`（半日）/ `day` / `days:3`（本段剧情跨了 N 天）/ `week` / `weeks:2` / `month` / `months:N`。**不允许**输出日期、天数或"十年后" |
| **作者/玩家** | 世界创建时填 `anchor`（默认 `{year:1, month:4}` = 开学）；可覆盖 |

**为什么不再让 LLM 给"间隔天数"**（v3 初稿错了）：LLM 给的数字既不准也无法验证，
而**粒度枚举是可枚举、可校验、可兜底的**。"跨了三天"这种叙事事实由 LLM 给
（`days:3`），"这三天落在哪一周"由引擎算——正是项目"LLM 演、引擎判"的老分工。

### 4.4 现实日历（②）与节日表

```jsonc
// data/worlds/{world}/real_clock.json —— 触发器台账（不是剧情真源）
{
  "schema_version": 3,
  "last_seen_date": "2026-12-25",          // 上次跑引擎时的本机日期
  "fired": {                                // 已触发过的键 —— 幂等闸门
    "festival:1225:2026": "2026-12-25T09:12:03",   // 每个节日/生日每年只触发一次
    "birthday:igusa_haruka:2026": "2026-07-29T08:01:44"
  },
  "pending": [],                            // 已触发但玩家当天没上线 → 补发队列（T+2 天窗口）
  "rewind_count": 0                         // 回退/回档次数（§4.8 给第四面墙用）
}
```

**节日表**（暂定三行 —— 用户裁决：动态节日未来再扩展）

| 键 | 日期 | 语义 | 默认表现 |
|---|---|---|---|
| `christmas` | `12-25` | 圣诞节 | 强节日：可触发 MMT 主动消息 + 剧情片段 |
| `new_year` | `01-01` | 元旦 | 强节日：同上 |
| `teachers_day` | `09-10` | 教师节 | 轻节日：**只做风味**（对话里可提），不强推剧情 |

```yaml
# 扩展位（worlds/{world}/festivals.yml，v3-4 只落三行）
festivals:
  - key: christmas
    date: "12-25"
    tier: strong      # strong | soft
    hint: "圣诞"
```

- **动态节日（农历/第 N 个周几）明确推迟**，但表结构预留 `rule:` 形态（未来加 `nth_weekday` / `lunar`），
  免得日后翻表。
- 结构按 `month-day` 规范化，**不带年份** → 天然避免年边界问题；年份只出现在 `fired` 的键里。

**生日（表外，两个来源，均为现实日历 —— 用户裁决 Q16）**

| 来源 | 位置 | 用途 |
|---|---|---|
| 角色生日 | `config/characters/{char}/profile.yml` 的 `SIG~birthday` | 角色生日触发 |
| 玩家生日 | `settings.toml [player].birthday`（新增） | 玩家生日 → 角色主动祝福 |

- 真实 BA 数据格式 = `"11/3"`（`LocalizeCharProfileDBSchema.json` 实测）；
  `profile.yml` 现为**两种格式混用**：`7/29`（3 人）与 `12月22日`（5 人）→
  读入时归一为 `MM-DD` 后入 `fired` 键。
- ⚠️ **双源实测（2026-09-13，非臆测）**：

  | 事实 | 数据 |
  |---|---|
  | `mmt_registry.toml` 顶部注释自称"**显示真源在这里**" | 但只登记了 **4 个角色**（`active`/`experiment` 白名单里的那 4 个） |
  | 两处都有的 4 人 | **数值完全一致**（haruka 5/13 · aru 3/12 · kayoko 3/17 · mutsuki 7/29）——**无矛盾** |
  | 只在 `profile.yml` 的 | **5 人**（ako 12/22 · iori 11/8 · chinatsu 8/22 · kokoro 4/1 · hina 2/19） |
  | 结论 | 不是"两处打架"，是**registry 覆盖不全**。而节日触发器**需要全部角色**的生日 → **真源只能是 `profile.yml`** |

  **V3-4 动作**：`profile.yml` 定为唯一真源；`mmt_registry.birthday` **要么删、要么改为读 profile**
  （保留"显示口径"的注释语义，但不再存第二份数据）。
- **密集月份是常态不是异常**：BA 真实数据 **256 人有生日、只有 129 个不同日期**
  （95 个日期撞车，1月2日 = 7 人）。所以"一周五个生日"是**设计内**；引擎必须能一天
  触发多条（`pending` 是队列，不是单值）。

### 4.5 触发器怎么跑（幂等 + 补发 + 只发一次）

```
每次 MMT 轮开始（引擎侧，零 LLM）:
  today = 本机日期
  for key in (节日表 ∪ 角色生日) where month-day matches today:
      if fired 无 "{key}:{year}" → 触发
  for key in pending where 未超过 T+2 天 → 补发（玩家那天没上线）
```

- **幂等**：`fired[{key}:{year}]` 存在即永不重复触发。同一天多个生日 → 依次触发。
- **补发窗口 T+2 天**：玩家 12/25 没上线，12/27 上线时仍会收到圣诞消息；再晚就作废
  （不产生"迟到的圣诞祝福"这种怪异体感）。
- **触发形态**：写一条 `festival` / `birthday` 事件进 `events.jsonl`（**不直接注入文案**）
  → 由 `P18`（随机 `want_to_speak`）的同类机制转成"角色主动发 MMT"的注记 → LLM 演。
  **引擎不懂节日内容**，只懂"今天有这个由头"。

### 4.6 冲突处理：**目标日吸附**（Q17 用户裁决 = 需要）

② 触发了节日，而 ① 还没走到那个日期（12/25 到了，剧情还在 8 月）——这是**必然**
发生的主路径，不是边角情况。行为：

```
on_trigger(festival | birthday) where tier == strong:
    if story_time.month-day == target.month-day      → 直接演（自然）
    elif story_time 早于 target（同年）               → 吸附：把 ① 的 cursor 直接推到 target
    elif story_time 已过 target（同年）              → 吸附 + 标记"迟到"（角色口径："今年…都过了呢"）
    sim_days 增量一并记账 → 召回时间衰减也随之后移（一致，不产生"平行时间"）
```

- **吸附写一条 `time_jump`** 进事件流（`from` / `to` / `reason=festival:1225`），**可审计可回放**。
- **吸附是单向的**：只向前，绝不把剧情时间往回拨（I6 单调性）。
- **bound**：单次吸附 ≤ 6 个月（Q18 用户裁决；与 §6-2 的 `months:N` 上限同源）。
- **开关**：`settings.toml [time].snap_to_festival`（默认 `true`）。关闭 = 节日照常
  触发，但不推动剧情时间（此时允许出现"八月里的圣诞祝福"——这就是用户说的
  "无法调和的矛盾"的显式降级档）。
- **只触发一次/年**：因为吸附已经把 `①` 推到节日当天，同一节日在本世界线内**当年不会
  再撞**；跨年后 `fired` 键自然更新。

### 4.7 为什么不做"全年事件表"（记录一次被否掉的方案）

想过给每个世界预排一张"剧情日历"（到 12 月自动进圣诞篇）。**否掉**，因为：
玩家的真实互动节奏不可预测，预排表必然与实际游玩进度错位，最后还是要吸附——
**那不如一开始就只做吸附**。节日表只提供"由头"，节日本身仍由 LLM 现演。

### 4.8 与回退/平行世界的关系（② 不可回退 —— 为第四面墙留的地基）

- **② 现实日历是物理单调的**：回档不会让本机日期倒退。所以"回档之后又过了一次同一个
  圣诞"在架构上是**可能的**，不能靠数据禁用，只能**给叙事解释**。
- 这正是 `docs/archive/world_model_evolution.md` 阶段 15 的物理结论：
  **单体时间倒流 = 该角色局部熵减 = 在他人眼里就是失忆**（15.2）；
  "损"是相对 scope 的悬空引用数（15.3）。
- 架构上的落点：
  - `real_clock.rewind_count` 累加（回退/回档时引擎自增）
  - 重复触发的节日/生日在事件流里带 `rewind_count` → 渲染时角色口径可退化为
    **"好像过过一次…"既视感**（不撒谎、不解释、不惩罚）
  - 召回可对 `rewind_count` 一致的旧节点加权（"这段你也记得"）
- **完整设计另立文档**：`docs/DESIGN_FOURTH_WALL.md`（OS / Orwell'S 项目 —— 用户裁决
  Q19：第四面墙独立立项，creepiness **可关闭**、达阈值**不惩罚**）。

### 4.9 模糊时间措辞（`§3.8` 的输入）

`story_age = now_story_time − node.story_time`，走**槽位差**而非壁钟：

```
   同 phase        → "刚才"
   < 1 天          → "今天"
   1~6 天          → "昨天" / "N 天前"
   1~4 周          → "上周" / "N 周前"
   1~11 月         → "上个月" / "N 个月前"
   ≥ 1 年          → "去年" / "N 年前"（按 significance 调措辞）
   跨吸附点        → 用吸附后的 sim_days 算（否则会算出"三天前的去年圣诞"）
```

### 4.10 与现有字段的关系

- `segment_id` / `event_seq` ✅ 保留（工程溯源；游标是**语义**时间，两者并存）
- 现有节点的 `ts` 保留不动（③ 只做审计）
- **没有 `story_time` 的旧节点**（线上 13 条全部没有）：迁移时按 `event_seq` 单调
  **外插**到游标（Q8 倾向外插，不置 `null`——置 null 会让全部旧记忆退化成"很久以前"，
  相对顺序这个最值钱的信息就丢了）

## 5. 组合重组策略（两档，别一次全上）

### 5.1 现状：机制齐全，零调用，且溯源有缺陷

`revise.py` 的 `merge`/`contradict`/`accrue`/`create`/`link`/`unlink`/`resolve` ✅ 全实现，
测试全覆盖，**但零生产调用**（`apply_revision_package` 只出现在测试里）。
真机 `evolution.jsonl`：**6 条，全是 `add`**（haruka 4 + mutsuki 2）。

而 `_build_merged`（`revise.py:421`）的做法有一个**设计缺陷**：
merge 是**造新节点 + 删源节点**，`links/contradictions/event_seq` 取并集，
但**不记录"我从哪几条合并来"** —— 恰好违反 A-Mem 那条纪律
（"without versioned history this is hard to debug and can be unsafe"）。
### 5.2 轻档：无损聚合（放进 digest 常态）

| 动作 | 语义 | 引擎保证 |
|---|---|---|
| `accrue` ✅ 已有 | 同类经历并入既有认知 | 加边 + `occurrences` 计数 + `examples` 追加（≤3）；**不删不改原文** |
| `touch` ✅ 已有 | 纯印证 | 只加边 |

特点：**信息零损失**，可随时重建。这档没有争议，v3 直接启用（v2 只是没接入口）。

### 5.3 重档：深度重组（独立阶段，可撤销）—— **合并策略按 `nature` 分派**

这是 §2.5 第四轴的**用途所在**：`nature` 不是标签，而是**能不能合并的判据**。

| `nature` | 允不允许 merge | 理由 |
|---|---|---|
| `self_image` | **禁止 merge**（I8） | 角色内核。合并 = 抹掉人设张力（"依赖他" + "怕成为负担"必须能并存） |
| `other` | ✅ 允许 | 关于他人的判断会被反复观察，该收敛 |
| `relationship` | ✅ 允许，但**优先"过期退场"而非合并** | 约定会被履行/失效，是**时效**问题不是重复问题 |
| `pattern` | ✅ 优先 `accrue`（计数聚合） | "反复出现"本就该累积，不需要合成新句 |

| 动作 | 语义 | v3 新增纪律 |
|---|---|---|
| `merge` | 多条同 `nature`、同 `about` 的认知合成一条更宽的 | **产物记 `superseded_by`；源节点保留**（I11）；产物 `history` 合并源的历史；**`self_image` 一律拒绝** |
| `contradict` | 标注两条认知互斥 | 双向边；渲染时并列显示，**不自动选边**（让 LLM 在剧情里处理张力） |
| `generalize` | 由 N 条 episode 提升出**新** belief | 必须 ≥2 条支撑（对齐 I2） |
| `merge_entity` | 两个实体实为同一个 | **只做别名软合并**（§2.7 改进④）：别名并入 + `merged_into` 单向标记，**节点保留**、**不改写指向它的 belief** |

**触发时机**（v2 的 `PHASE_DEEP` 声明了但没注册动作）：
- **同 `about` + 同 `nature=other`** 的 belief 数超阈值（如 ≥4）→ 提议 merge
- **同 `about` 的实体重复**（LLM 提议新建时发现别名高度重合）→ 提议 `merge_entity`
- 语义碰撞持续判"同主题"但内容分歧（用 §6.3 的 relevance 分数分布触发）
- 每 N 次 digest 兜底一次

**成本控制**：对齐 AgentGal 的 step3 —— **只在超过阈值时才跑**，
而不是每次 digest 都做一遍全局重组。

### 5.4 撤销与审计

- `history` ✅ 已有：update 时追加 `{episode_id, content, ts}`
- v3 补：`superseded_by`（认知被取代）+ `merged_into`（实体被归并）
  + `evolution.jsonl` 记录 `merge`/`merge_entity` 的**源 id 列表**
- **不做 GC**：被取代的节点留在图里（可回放、可审计、可回滚），只是不再参与常规召回
  （`superseded_by` / `merged_into` 非空的节点权重 ×0.3，或直接从角色视图剔除、
  仅组织视图可见）

## 6. LLM 每一步动作（全链路重排）

### 6.1 v2 现状：两步挤在一轮里、动作只有三选一

| 步骤 | v2 实际做什么 | 问题 |
|---|---|---|
| Round A | 时间线 → episodes（`kind` 可出 episode/experience） | 缺时间/地点/在场；两种素材共用一段【MMT 专则】 |
| Round B | 逐条决策（add/touch/update）+ subject 纪律 + content 改写 + experience 判定 + 好感 + evidence | **一轮干六件事**；动作集缺链接/矛盾/组合 |

### 6.2 v3 动作表（每步：输入 / 输出 / 引擎校验 / 失败口径）

#### Step 0 — 时间推进（**新**，极轻）

| | |
|---|---|
| 触发 | 每次 digest 之前 |
| 输入 | 上一游标（槽位）+ 本段事件流（压缩）+ 上一段末尾 |
| 输出 | **粒度枚举**（§4.3），不是天数：`{"span": "same\|phase\|day\|days\|week\|weeks\|month\|months", "n": 3, "reason": "拯救猫咪大作战跨了三天"}` |
| 引擎校验 | `span` 必须 ∈ 枚举；`n` 为正整数且 `1 ≤ n ≤ 4`（`days` 可到 30）；整数化后**换算成 `sim_day` 增量**并**进位写槽位**；单次 ≤ 30 `sim_day`，超出夹取 + NOTE；非法 → 走默认 `phase` |
| 失败 | 默认 `span=phase`（**不是 0**——"紧接上一场"也至少推进半个时相，否则一天可以无限长） |

**为什么输出不是天数**（v3 初稿错了，见 §4.3）：天数既不准也不可校验，而枚举可兜底。
LLM 只需回答"这段戏横跨了多久"这个**叙事问题**，槽位算术全部由引擎做。

#### Step 1 — 经历记录员（原 Round A，改造）

| 引擎校验 | 必填字段齐全（**结构完整性逐条校验**，对齐 AgentGal）；`epistemic` 与 `observer` 配对；≤5 条 |
| 失败 | 整步跳过、水位不推进（宁缺勿错） |

我的论据错。**

#### Step 1.8 — 实体消解与登记（**新，实体层的入口**）

这是引入实体层后**新增的关键一步**，也是"四种写法"问题的根治点。

| | |
|---|---|
| 触发 | Step 1 之后（与 Step 1.5 可合并成一次调用） |
| 输入 | Step 1 的 episode（含 tags/narration）+ **已知实体清单**（渲染成 `x0001 [person] 老师（别名: sensei）`）+ 关系表（`interperson.json`） |
| 输出 | `{"entities": [{"ref": "x0001"} \| {"new": {"name": "春余", "etype": ["item"], "aliases": []}}], "links": [{"episode": "m0001", "about": ["x0001", "x0004"]}]}` |
| 引擎校验 | ① `ref` 必须存在于清单（**引用幻觉 → 该条作废**，与 Round B 的 id 纪律同源）② `new` 必须过 `etype ⊆ 词表`（I5）③ `new` 与既有实体**别名重合度超阈值 → 引擎改判为 `ref` 并建议 `merge_entity`**（防重复实体）④ 每条 episode 的 `about` 至少 1 个实体 |
| 失败 | 跳过本步 → `about` 留空（该 episode 不进实体车道，仍可被语义/词面通道召回到；**绝不阻断消化**） |

**为什么必须有这一步（而不是让 Round B 顺手写）**：
- **`about` 是归堆键，必须可信**。若交给 Round B（它同时在忙决策/改写/好感），
  就会重演 v2 的 `subject` 自由发挥。
- **实体创建要防重复**。引擎做别名重合度检查、强制走 `ref`，这是**构造性**防重；
  靠提示词"请复用已有实体"是劝不住的（v2 的实证）。
- **代价可控**：可与 Step 1.5 合并为一次调用，不额外增加轮次。

**`self` 与 `player` 不进 LLM 决策**：`x0000`（self）开局自动建、
`about=self` 由引擎按"这是角色自己的反应"判定；玩家实体开局自动建
（`ref=player`，`etype=[person]`，别名取玩家当前名字 + "老师"/"sensei"）。
LLM 只需要在清单里引用它们。

#### Step 3 — 边状态维护（**新**，仅当本段出现状态变化线索时跑）

| | |

`parse_round_b`），v3 改为**强提示**：仍标注"疑似同主题 + sim 分数"，但允许 LLM
`add` 并在 `note` 里说明理由。

**这条已用真机实验定案（2026-09-13，见 `docs/EXPERIMENT_CAND_HIGH.md`）**，
结论比"收窄范围"更硬：

1. **换 Qwen3-Embedding 是前提，不是优化。** nomic 下**主题无关**的经历 top1 可达
   `0.868`，而**真相关**的经历最低 `0.819` —— 无关 > 相关，**单阈值原理上不可分**。
   Qwen3 下有干净窗口：相关 `0.682~0.859` / 无关 `0.367~0.452` → **(0.452, 0.682)**。
2. **`0.50` 从未标定过**（标定时 embedding 服务没通）。Qwen3 下建议 `cand_high≈0.62`、
   `cand_med≈0.40`（旋钮已在 V3-0 落到 `settings.toml [recall]`）。
3. **但取消结构强制与阈值无关、且更根本**：语义相似度**无法区分**
   "同一件事"与"同一个人身上的不同侧面"（Qwen3 下同一实体的不同侧面落在 0.44~0.86）。
   把连续分数变成二元硬闸门，就会在"她讲的是老师"这种**域相同、事不同**的情形上误判。
   —— 这与 v3 引入第四轴（`nature`）是**同一个洞察的两处应用**。
4. **候选排序方向是对的**（Qwen3 下 haruka 4/4 的 top1 语义正确），
   所以分数**该作为给 LLM 的排序提示**，不该作为引擎的判定。

**另有两条附带发现（都写进实验档 §6）**：
- `cand_k=3` 会掩盖真相：`k=99` 下 4 episode × 4 belief = **16 个候选全部 > 0.73**
- `_round_b_material` 的 `c.id in local_of` 过滤**吞掉认知列表之外的候选** →
  `COGNITION_CAP=12` 之外的高相关认知**不但读不出，连组织也参与不了**（§3.1 的第二个后果）

### 6.4 标注层扩展：感知碎片 + 情绪强度（回应用户 f）

**用户 2026-09-13**：*"人在经历时会看到一些、听到一些，无意识决定了很多东西，
而不仅仅是复盘。要不要让 emo-LLM 标注一些关键词，模拟人无意识接受的产物，
然后用在 RAG 里？比如去杂草屋 llm 可以写一个看到了蓝天白云，
这样 rag 检索时就能想起来那天也是这样的好天气。"*

**采纳，且它顺手解决了另一件事**（时间感的载体，见下）。三条约束：

| 约束 | 为什么 |
|---|---|
| **必须稀疏**（每板 ≤2~3 个，禁止罗列） | 与 `place` 的"事件型稀疏锚点"同一个道理——罗列会让检索信号变成噪声 |
| **必须进 embedding 文本**（不只显示） | 否则它进不了 RAG 通道，只是装饰 |
| **只记具体可感之物** | 天气/光/声音/气味/温度/触感；**不记抽象判断**（那是 belief 的活） |

**不开新 lane**：`emotion` 那一路已经带人设卡 + 记录序列 + 词表，**加字段比加 lane 便宜**。
所以把**新产出**并进 **emo 标注的同一次调用**：

> ### ⚠️ 本节初稿的 `intensity` 产出**已撤回**（2026-09-13，见 §3.3.2）
>
> 初稿写 `"intensity": {"1": 0.2, "2": 0.8}`。**撤回**：**emo lane 结构上看不到基线**
> （它只吃一板 + 上一板 + 人设卡，`emo_text.py:186`），给不出"这个键对本角色算多强"。
> **强度从 `emotions.yml` 的作者注释派生**（查表，非评分）。
> **`percepts` 不受影响，保留**（它确实是"当时多看到/听到了什么"，
> 正是 emo lane 看得见的那部分）。

```jsonc
// 现在: {"labels": {"1": "nomal", "2": "smile"}}
// v3  : {"labels": {"1": "nomal", "2": "smile"},
//         "percepts": ["午后的阳光斜着照进来", "纸页的霉味"]}   // ★ 感知碎片（稀疏, ≤3）
//        ~~"intensity"~~  ← 已撤回（§3.3.2）：强度由引擎查作者注释表派生
```

写入位置：`episode` 记录的 `percepts: []`（**不进 belief**）。
`emo_span`/`emo_int` **不写入节点**——它们是**物化层**的派生量（§3.3）。

#### 6.4.1 ★ `nomal` 污染 —— **这一条的结论仍然成立，只是用它的地方变了**

> **2026-09-13 更新**：本小节原为"情绪强度怎么算"的口径裁决（Q29 激活比）。
> 现在**强度不走激活比了**（§3.3：`emo_int` = 作者注释查表，`emo_span` = 极差）。
> **但 `nomal` 的污染分析仍然有效且必须保留**——`emo_span` 的 val/min 计算
> 同样吃这个污染：**`nomal` 有 7.5% 是标注失败而不是"平静"**。

用户提议："**直接算 `nomal` 表情比率**"。**方向可行，但当前不能用**——`nomal`
**同时是失败回落值**，代码三处：

```python
core/bond/emotion_annotate.py:41   _DEFAULT_EMOTION = "nomal"
core/bond/emo_text.py:41           _DEFAULT_EMOTION = "nomal"
webgui/bond.py:2410                p["emotion"] = "nomal"     # 缺失即填（兜底）
```

**真机数据证实污染量级**（world1 事件流，2026-09-13 实测）：

| 角色 | 有标注的记录 | `nomal` 占比 |
|---|---|---|
| asagi_mutsuki | 53 | **0 条（0%）** |
| igusa_haruka | 40 | 3 条（**7.5%**） |

→ `nomal 比率` 度量的是**标注失败率**，不是"她有多冷静"。**两义混用则指标无意义。**

**替代口径（不碰兜底值，且不新拍阈值）**：用**词表注释**（作者已写好的语义）
把键分成平静/激活两组，算**激活比**：

| 组 | 键 | 依据（`emotions.yml` 注释原文） |
|---|---|---|
| **平静** | `nomal` / `respond` / `pensive` | 「正常态」/「相对比较认真的回复」/「回忆·沉睡」 |
| **激活** | `tease` / `laugh` / `embarrass` / `serious` / `outburst` / `shout` / `enraged` / `depressed` / `strive` / `expectant` … | 其余（带情绪倾向的） |

```
activation_ratio = 激活组 / (激活组 + 平静组)      # 按角色、按章、按窗口可算
```

**副产品（比强度更好用，但列后手）**：每角色有**独占情绪签名**（实测）：

```
mutsuki:  tease 35.8% / smile_2 18.9% / laugh 15.1% / smile 11.3%（玩味型）
haruka:   serious 17.5% / embarrassed 15% / expectant 12.5% / depressed 10% / strive 10%（认真/不安型）
```

可额外量"整板同键率"（现测 mutsuki 1/14、haruka 0/6——说明标注并不偷懒）。

> **⏳ 用户裁决（2026-09-13）：独占签名暂作后手，"先不是先"，计入文档。**
> 即：**记下来，不作为本阶段设计输入**；先走激活比/强度主线。

**★ 意外收益：它是"时间感"的第二种载体。**
天气/光/温度这类碎片，恰好就是**人感知时间推移的方式**——
"那时候还在下雪"比"x 周前"更像人的记忆。所以 §3.4 的模糊时间标签与
`percepts` 是**互补的两种时间表达**：一个是**相对距离**，一个是**环境指纹**。
`percepts` 也让 §3.7 的"随机旁路"更有价值——想起"那天的好天气"本身就是一次召回。

**成本**：并入现有调用 → **0 新增轮次**；只增输出 token（`emotion` 档位是 `off`/512，
需复核 512 是否够装 `labels + intensity + percepts`，不够就抬到 768——见 §8 待办）。

### 6.5 提示词装配的约束（与盒机制冲突的地方）

`render_character_view` ✅ 目前是 **Bond 开场一次注入、整章不变**（盒B"一次拼死、
逐字节稳定"）。召回一旦变成 query 驱动，就与这个约束冲突。三个选项（**待你拍板**）：

| 选项 | 做法 | 代价 |
|---|---|---|
| A | Bond 仍开场注入，但**开章 query 用触发语料**（chapter_title + 触发 reason + 首场 switch） | 章内不刷新，长章仍然陈旧；但零改动盒机制 |
| B | Bond **每板**刷新召回段，放在**盒外**的动态尾（注记位） | 破"盒逐字节稳定"的前缀缓存收益（§9 缓存会退化） |
| C | 折中：**开场注入 + 关键节点重召回**（换场 / 纪念 / 每 N 板） | 复杂度中等，缓存影响可控 |

我倾向 **C**（换场是天然的记忆检索时机，而且 Bond 已有 `switch` 记录作为触发点）。


### 8.1 §8-1 详注：`max_paragraph_chars` 为什么该删（真机实测 2026-09-13）

**它不是"控预算的保险"，是一块补丁**——诞生于"**怕出厂记忆挤占召回窗口**"的年代，
而那个设计已经作废（出厂 experience 直注、不进 wiki）。**补丁对象死了，补丁没了依据。**

**实测（world1 真机）**：

| 角色 | 非 marker 事件 | 全量 timeline | 板均正文 | 最长板 | 超 120 字的板 |
|---|---|---|---|---|---|
| asagi_mutsuki | 42 | 3129 字 | **73 字** | 199 字 | 2/14 |
| igusa_haruka | 21 | 1662 字 | **163 字** | 337 字 | 3/6 |

- **阈值卡在板均 73~163 字之上一点** → 它砍的不是异常长板，而是**把正常的板也砍掉一部分**
- **删掉后输入只涨 ×1.11 / ×1.50**（1500→2500 字量级）——**整条世界线的记忆还不到 2k token**，
  拿它担心 1M 上下文是拿补丁思维看新问题
- **它砍掉的正是全章情感落点**，实例（haruka 一章）：
  ```
  丢 358 字: …门口地砖缝里的这一种……基沃托斯到处都是，没有人拔它，它就一直在长。
  丢 268 字: 那份报告，会交到联邦理事会手里，对吗。 上面会写着这些草的名字……会一直留着…
  丢 121 字: 写下来，就是有人记得它们了。就算所有人都当没看见，也还有人在名单上找得到它们。
  ```
  同时也在砍 `老师: 自作自受了吧。` 这类**玩家裁决行**（`picked` 也是先拼进 `texts` 再一起砍的）

**落法**：直接删（不是放宽）。`max_paragraph_chars` 全库只有 4 处引用
（`renderer.py:261/308/309` + `tests/core/test_session.py:295`），零生产调用方传参。
**`verbatim` 语义不变**（它是"摘要里摘出的那一个关键短句"，本来就不要求全文记叙）——
这条修的是"引擎把它砍没了"，不是"要它记全文"。

**✅ 已落地（2026-09-13，独立提交，见 §9.3）**。落地后本函数 = **digest Round A 的
唯一输入**，因此"不截断"= **LLM 看得见完整情绪弧**——这正是**板指针**
（`event_seq`，§3.3.1）能成立的前置条件：**不删它，LLM 看到的时间线是残缺的，
板指针会永远指向前几条。**

## 11. 边界（v3 不做的事）

- **不做**跨世界线/跨角色的记忆合并（世界线隔离是硬语义，`DESIGN_BRAIN §1.4`）
- **不做**GC / 物理删除节点（append-only 精神；被取代者保留）
- **不做**在节点里存"情感数值"（好感仍是事件流派生，数值不进节点）
- **不做**把情绪塞进 embed 文本（实测空间塌陷 + 极性不可分，§2.3.1 ③ 撤回框；
  情绪走独立结构化通道 = §3.3 的 `emo_span`/`emo_int`）
- **不让** LLM 给情绪打绝对强度分（emo lane 看不到基线；强度从 `emotions.yml`
  **作者注释**派生。LLM 唯一的情绪相关输出 = **板指针** `event_seq`，§3.3.1）
- **不让**主 LLM 写 `id`/`story_time`/`occurrences`/`history`（引擎字段，防幻觉）
- **不引入**向量数据库依赖（当前是 JSONL + 进程内向量；要换后端只换 `embed_fn`，
  与 v2 预留接口一致）
- **不做**多角色的 NPC 记忆网络（那是 `core/DESIGN_MULTI_CHAR.md` 的线，v3 不碰）

### 11.1 时间项的边界（§4 专属）

- **不做**两钟同步：现实日历与剧情时间**永不试图对齐**，只做单向吸附（§4.1 红线 3）
- **不把**现实年份/日期喂给 LLM（Q22 倾向）——角色不该知道"2026"
- **不做**动态节日（农历 / 第 N 个周几）——表结构预留 `rule:`，**本阶段只落三行固定日期**（Q20）
- **不做**预排全年剧情日历（§4.7：与实际游玩进度必然错位，吸附已足够）
- **不在**节日触发时直接注入文案——引擎只落"由头"事件，文案永远由 LLM 现演（§4.5）
- **不实现**第四面墙 / OS（Orwell'S）——只留 `rewind_count` 接口（Q19，另立 `docs/DESIGN_FOURTH_WALL.md`）
