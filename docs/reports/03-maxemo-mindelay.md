## 0. 核心矛盾:

1.  **流式输出**和 **局部退火**
   - 你不能既要流式输出的速度，又要局部退火的兜底
2. **长篇输出** 和 **精度输出**
   - 你不能既要长篇输出的宽裕，又要精度输出的细度

在我们的项目中，我们要求AI在没输出一段对话的同时，附加一个[emotion]字段

这个[emotion]是直接对应差分渲染到屏幕上的，其变化细度直接决定了玩家的体验

而同样的，LLM的响应[delay]又是另一个决定玩家体验的问题

---

假如你做的是关注剧情的Visual Novel，那显然是[delay]更需要被重视，选择显而易见

但假如你做的是角色扮演，那么OOC会惩罚每一个不认真设计提示词的Coder

[emotion]要求的细度 和[delay]要求的速度，就是本项目XEND需求上的两朵乌云

---

## 1. 乘法原理:

那么既然是两两矛盾，我们最终的选择，其实就被框死在2x2里了(for now):

### 1.流式输出 + 精度输出
这些词怎么会组成一句话呢？

短输出让流式输出的优势完全无法发挥，总等待时间仍然是Time(TTFT x N)，这样的流式输出的优化度微乎其微，并不是一个优秀的组合

### 2.局部退火 + 长篇输出
孩子们，我在第一个token处出错了，看我退火，不好孩子们我又在第一个token处错了

长篇输出和局部退火本身的适配性没那么强，因为长篇输出一旦出来一个错触发了退火，等待时间是灾难性的，尤其是在一个语法出错率较高的RP的项目之中

### 3.流式输出 + 长篇输出
孩子们，我速度非常快。什么叫意大利面拌42号混凝土

体感速度最高的一集，但是问题是不兼顾RP，最多作为备选方案，高度取决于LLM的参数量

### 4.局部退火 + 精度输出
M...Y...N...A...N...E...I...S...F...L...A...S...H

输出精度最高的一集，但是问题是每一小段话都要等待，不过虽然如此，这也是一个备选方案

### JAILBREAK-并发修正法

```json
{
	"character": "igusa_haruka",
	"plot": {
		"paragraph0": {
			"text": "您好...老师...",
			"emotion": "nomal"
		},
		"paragraph1": {
			"text": "我想和您讨论一件...很微不足道的小事..."   -->   出现缺失emotion 
		},
		"paragraph~": {
			"text": "~",
			"emotion": "~"
		},
		"paragraphN": {
			"text": "感谢老师，我永远也不会忘记您的大恩大德的...".
			"emotion": "smile"
		},
	}
}
```

1. 流式解析json
2. 发现错误点，校验器写入语法错误
3. 直接把语法错误塞进payload并行让另一个LLM生成
这在一定程度上解决了二者的问题，虽然有些抽奖性质，因为另一个AI拿不到原始AI的输出作为输入，纠错能力必然大打折扣，但是它一定程度上确实解决了我们的问题。

### JAILBREAK-N x 1? 1 x N? M x N.

长篇输出和精度输出真的也是矛盾的吗？

显然，它们并不是二元正反关系，它们是一个区间的左右端点

我们完全可以控制AI一次性输出数段文字，并要求AI标注这几段，这是一个更为简单的调和输出。

例: 一次标注3段，出错概率大大减小

**并发退火 + 短篇输出**

## 4. One man's trash is another man's treasure

AI说可以两步走，先生成文案，然后逐句分析情感

请注意，这一切并不依赖导演，因为导演是需要和主LLM交互的

但是此处，这个第二步又像极了导演，因为它做到了一件事情，且做的比导演更好：它将两者的任务几乎完全解耦，只剩下一个时间上的先后关系

不过，在实测中，这个行为总耗时接近13s，虽然高度准确，但是速度仍然过慢，这个方法，真的也行不通吗

并不是，我们只差最后一块拼图了，准确来说，是两块

## 5. 流式异步加并发

在主LLM输出文案后，进行流式解析，与此同时，开一个异步线程，让并发LLM去解析主LLM的流解析结果，这样，两个LLM宏观上几乎是同时进行工作，而且还很节省token

以下是范例: 
```json
{
	"character": "igusa_haruka",
	"plot":
		{
			"text0": "您好...老师...",                          // --并发0: {emo: nomal}
			"text1": "我想和您讨论一件...很微不足道的小事...",    //  --并发1: {emo: timid}
			"text2": "就是，我喜欢您!",                         // --并发2: {emo: effort}
			"text~": "~",									   // --并发~: {emo: ~}
			"textN": "感谢老师，我永远也不会忘记您的大恩大德的..." // --并发n: {emo: giggle}
		}

}
```


```markdown
主 LLM 输出文案
   ↓ **流式解析**（边到边切）
   **异步线程**：把流解出来的句子喂给并发 LLM
   ↓
   两个 LLM 在宏观上**几乎同时工作**
```

这完美解决了上面的几乎所有问题，因为精度不仅由输出长短决定，它也由LLM所获取的任务单一性决定！

- 主 LLM 的任务是"写文章"——大任务，但是单一，出错几乎只是小的格式错误，是无法避免的，且可以由引擎处理并回灌错误
- 异步 LLM 的任务是"给这几句标情绪"——小任务且单一，它要是再错，立刻惩罚参数直接上调到114514

`LLM的任务可以难，但不可以乱。就像飞行员，你可以在飞机上装复杂的操纵系统让他巡航，但你不能一边让他握住前进拉杆一边打麻将`

甚至假如你真的不信任模型的输出，**并发修正**和**流并发解析**并不矛盾


## 5. 水到渠成：它后来长成了什么

上面那条推演停在"流解 + 异步"。真正落地之后，长出来的东西比当时设想的更彻底——
因为它把"并发"从一个技巧变成了**分层**。

记录流 v2 里，一条记录只允许长这样：

```jsonl
{"character": "haruka",   "text": "……老师，你、你来了。"}
{"character": "sensei",   "text": "是我来晚了。"}
{"character": "narrator", "text": "（她低下头。）"}
{"stage": "switch",   "text": "深夜的杂草屋"}
{"stage": "art",      "text": "她终于把话说出口的一刻：抬头、眼中有泪光"}
{"stage": "memorial", "text": "（她抬起头，朝我笑了一下。）"}
```

**没有 `emotion`，没有 `place`，没有 `image`。** 只有人话，加几个舞台标记。

四件"场景"全部由标注层读出来：

| 场景 | 谁做 | 何时 |
|---|---|---|
| **表情 / 情绪** | 记录级情绪标注：**一条记录一个键** | 本板闭合后 |
| **背景地点** | 句级锚点（稀疏的 `[{sentence, place}]`） | 同一时刻，另一条 lane |
| **背景变体** | 第二遍：地点定了，再挑这个地点的哪一张（时刻 / 天气 / 作者差分） | 地点确定后 |
| **纪念立绘** | 流式嗅探到 prompt 定稿即开生图线程 | 生成期 |



这就是"妙笔生花"的字面意思：**她只管把话写出来，画面自己长出来。**后端的FIFO异步线程永远是最坚实的后盾
