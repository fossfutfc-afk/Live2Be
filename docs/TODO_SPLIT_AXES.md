## 1. 顺序原则（四句）

1. **契约先行** —— 形状定死、守门能红，后面才敢动；
2. **从源头到下游** —— R0 判据 → 尾巴 → 段边界 → 召回（**倒着做等于给错的东西打补丁**）；
3. **每笔都要有一个真机数字做验收** —— 不然改完不知道好没好；
4. **零新边优先** —— `continues` 只记账；四道里前四道（含它）**能不加边就不加**。

## 3. 逐笔细化

### S1 · R0 判据：一件 = 一段

**改什么**（LLM 会看到的三处）：

1. `_DOMAIN_CONTRACT["bond"]` 尾巴那三行（**它是真机症状 A 的直接肇事者**）——
   今天明写「本段可能同时含 MomoTalk 聊天……**按 `mmt` 规则另行切件**……既不要并进章总结, 也不要漏切」；
2. `_DOMAIN_CONTRACT["mmt"]`「必须覆盖全部 —— **连闲聊也要给它自己的那一件**」+ 切分三条
   （「换人说话 / 换话题 / 换场景 = 新的一件」）；
3. `build_schema(PHASE_SPLIT)` 里那把**松尺子**（"三十条消息切成十五件"才算流水账 ⇒ 隐含许可 2:1）。

**还要动的两处**：

- ⭐ **示例**（示例才是形状的来源）：`digest_split.md` 的输出示范要**示范"一场多话题的戏 = 1 行"**；
- `MAX_SEGMENTS` **20 → 12** 收回（上限从来不只是上限，它是标尺）。

**守门（都要能红）**：① 契约里"一件 = 一段"那句在（删掉 ⇒ 红）② prompt 不许抄判据原文
（复用 `test_split_prompt_does_not_restate_the_schema_criteria` 的黑名单，把新词加进去）
③ `MAX_SEGMENTS == 12` ④ 示范里"多话题一场戏"只有一行。

**验收**：真机跑一段后用 §5 那张表对数字（「每段件数」「相邻相接率」）。

### S4 · 召回不半截（零新边）

**改什么**：召回命中一条 episode ⇒ ① 带上**它所在那一段**的全部（按时间拼）② 带上**同群**的其余条。
`continues` **只记账**：把"疑似被插曲打断的同一件事"记进日志（不写边）。

⚠️ ② 就是**给"群"补上它一直缺的消费者**（`PROCEED §2 #48`：群写侧有、读侧零）。

**守门**：两条（段拼接 · 群扩展）+ 一条断言「**没有新增 rel**」（防顺手把 `continues` 加上）。

**验收**：构造 store —— 命中 `e1` ⇒ 输出里出现同段/同群的其余条。

### ⏸ S6 · `continues` 边（待启用，**不要顺手做**）

它的定位与三个场子见规格 §4。**三条启用线**（出现任一条才开工）：

1. 真机仍有一段被切成多条（「相邻相接率」降不下来）；
2. **一段太长必须切**（一次来访几百条）—— 那时"两半"是被迫的；
3. 按段召回实测**段太大淹人** ⇒ 需要一个更窄的粒度。
