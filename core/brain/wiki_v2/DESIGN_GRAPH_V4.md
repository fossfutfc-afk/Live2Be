## 1. 三层 + 两个旁支

```
                ┌──────────────── entity ────────────────┐
                │ text(立场/成长基线) · state(物理状况句)  │
                │ name · aliases（消解的目标）            │
                └──┬────────────┬────────────┬───────────┘
          about ↑ │            │            │ ↑ about
                │ │            │            │ │
   belief（离散命题: 看法/规律/结论）    fact（她眼中的事实）
        ↑ supports          ↑ source
        │                   │
   episode（经历）──────────┘
        ↑ formed_by × N
   promise（未完成的事, 带状态机）──supports──→ belief
        └ from / to → entity（双方）
```

- **entity** —— 一个对象 + 角色对它的**立场**。⚠️ **不做 `etype`**（2026-09-21 用户裁决）：
  只保留 **`x0000` = self** 这个 id 约定（v3 §2.8）。原来的五类（`self/person/place/item/knowledge`）
  已被后来的裁决拆掉四类 —— `item` 与 `knowledge` 由 §3.1 判走（物品是 episode 的字段、新知识就是
  belief/fact）、`place` 挂起（§9-5）。**多一个枚举 = 多一个要维护、要裁决、要写进 prompt 的东西，
  而它今天不改任何行为。**
- **belief** —— 对某 entity 的**离散命题**，entity 的第一层辐射。
- **episode** —— 经历。支撑 belief；**也允许直连 entity**（没形成认知的经历也要有归属，
  否则按对象聚合会漏掉大半经历）。
- **fact**（旁支，仍在图内）—— **她眼中的事实**（可对可错）。不参与排序，走旁路。
- **promise**（旁支，仍在图内）—— 带状态机的"未完成的事"；可连**多段** episode（共有）。

## 2. 边（带类型，取代今天那根无类型的 `links`）

| 边 | 从 → 到 | 含义 |
|---|---|---|
| `about` | belief / fact / promise → entity | 归属（entity 车道的依据） |
| `about` | episode → entity | 经历归属（**没有认知也要连**） |
| `supports` | episode → belief · promise → belief | 支撑 |
| `formed_by` | promise → episode × N | 这条承诺是怎么一次次说定的（共有） |
| `contradicts` | 同层之间 | 矛盾（她后来发现不对） |
| `evolved_from` | belief → belief | 认知演化（新看法取代旧的） |
| `source` | fact → episode | 她怎么知道的 |
| `from` / `to` | promise → entity × 2 | 承诺双方 |

**归属**：`about` 边是归属的**唯一落地形式** —— **有边 = 归好了；没边 = 没归**。
⏸ 原"三态"设计（`about_state ∈ resolved/uncertain/none` **挂点上**、`uncertain` 进复查队列）
**2026-09-21 用户裁决"先不做，再考虑考虑"** ⇒ 从"定案"**退回未定**（§9-6）。
连带后果：`uncertain` 的条目暂时**没有落点**（队列是给它兜底的）—— 第 3 轮判不出就不建边，
也不追踪（待 §9-6 定）。

### 2.1 存储与索引（2026-09-21 定案）

**点边分离，两个文件**：

```
soul/wiki.jsonl     点 —— 一行一节点（**不动**，迁移面 = 0，grep 友好）
soul/edges.jsonl    边 —— 一行一条 {"rel","src","dst","ts"}
```

（代码里用 `src`/`dst`；上表的 `from`/`to` 是 rel 名，落到 JSON 键会撞 Python 关键字。）

**运行时 = dict 邻接索引**（纯 stdlib），载入时建三个：

```python
out:    dict[str, list[Edge]]   # src → edges    "我指向谁"
inc:    dict[str, list[Edge]]   # dst → edges    "谁指向我"
by_rel: dict[str, list[Edge]]   # rel → edges    "所有 about 边"
```

六类查询各一行（这也是"够不够用"的验收口径）：

| 查询 | 写法 |
|---|---|
| entity E 下的 beliefs | `[e.src for e in inc[E] if e.rel == "about" and kind(e.src) == "belief"]` |
| belief B 的支撑经历 | `[e.src for e in inc[B] if e.rel == "supports"]` |
| promise P 的共有经历 / 双方 | `[e.dst for e in out[P] if e.rel == "formed_by"]` / `rel in ("from","to")` |
| 1-hop 扩展（召回） | `out[n] + inc[n]` |
| **未归属清单** | **非 entity** 节点 − `{e.src for e in by_rel["about"]}`（复查队列直接用它） |
| 删节点 | 节点表删 + 边表过滤一遍 ⇒ **"悬空引用/双向一致"在构造上不可能存在** |

⚠️ **未归属清单要排掉 entity 自己**（G1 落地时复核出来）：`about` 边的方向是"节点 → entity"，
所以 entity **永远不会**是 `about` 的 `src` —— 不排的话每个 entity 都会冒充"未归属"。

**推断层的 `unknown`（G1 专有）**：今天那根无类型 `links` 判不出类型的对
（`belief`↔`belief` · `belief`↔`experience` · `episode`↔`episode`）发一条 `rel="unknown"` ——
**不猜**（`evolved_from` 的语义是"新看法取代旧的"，一条无向边说不出谁取代谁，猜错方向比不判贵），
但**也不丢弃**（丢了会让 1-hop 比今天的 `links` 更窄）。G3 落盘后写路径总是知道 rel
⇒ `stats()["unknown"]` 应当归零，**它就是那条验收线**。

**三条边界（写死，免得以后反复）**：

1. **运行时纯 stdlib**：`core/brain/wiki_v2` 现在没有第三方依赖（只有 `json`/`dataclasses`/`logging`），
   CLI/测试/实验脚本都能独立跑。**networkx 只留在 dev 侧**（`tools/wiki_viz.py` 已在这么做）；
   要图算法时用一行桥（`G.add_edges_from(iter_edges(store))`）在分析脚本里建图。
   ⇒ 触发条件：只有出现"我们写不动的算法"（最短路解释支撑链 / 社区发现做合并候选 / 中心性做召回加权）才评估升级。
2. **磁盘格式自持**：不用第三方序列化（nx 的 `node_link_data` 就是活例子——3.x 把 `links` 键改名成 `edges`）。
   我们的纪律是"**旧档宽容读、无迁移脚本**"，格式一旦外包，库的升级就变成我们的数据迁移。
3. **不做双写**：不搞"边表与节点内 `links` 并存一段时间"——那是第二个真源。数据 5 节点 / 消费者 12 文件
   ⇒ 一步到位比长期双真源干净。**G3 已按这条落地**：写路径只写边表，`links`/`contradictions`
   在点表里变成"**读得进、写不出**"（旧档自举还要读它，见 G3 行）。
4. **两个文件不是一次事务**（G3 加）：`save()` 是两次 `atomic_write_lines`，写序 = **先点后边**
   —— 点写成功而边写失败, 后果是"边表陈旧（少几条新边）", 记忆正文完好、可重算;
   反过来会留下一批悬空边。两条都只降级不损坏, 但前者更好收拾。
   一致性靠**读侧宽容**（悬空边保留, 由 `audit()` / `Graph.dangling()` 报），不靠事务。

**落地分步（叶子优先，每步一提交 + 全量 + B 层冒烟）**：

## 3. entity 载荷

```
entity
├── name / aliases      实体消解的目标（"老师 / sensei / 他" → 同一个 entity）
├── text                **立场 / 成长基线**（慢变: 只在确有成长时改）—— 原 `overview` 的语义
└── state               物理状况句清单（粘性: 换了发型 / 手上多了道划痕 / 今天戴了眼镜）
```

- ⭐ **`overview` 不落字段：它的语义由共用的 `text` 承担**（2026-09-21 用户裁决）。
  于是 entity **不需要新字段**，也**不必**把 `text` 从"共用字段"里降级出去。
- **两个载荷的分工是"立场 vs 物理"**：`text` = **立场/成长基线**（主观、慢变、只在确有成长时改）；
  `state` = **物理状况**（身体 / 外观 / 随身，客观、会变、会自愈）—— `state` **本来就是为物理状况
  设计的**，所以不需要再分一个 `body` 字段。这也把 entity 内部对齐到 §3.1 那条轴：
  `text` 属心智侧，`state` 属世界侧。
- **同块注入、不分家**：LLM 每次看到 entity 就知道"她/他当下是什么样" ⇒ **防前后矛盾**
  （这正是这一层存在的理由）。
- 写纪律：**只改变化的那一行，其余原样复制** —— diff 可读、改动可审、不会每次整体重写漂移。
- `self` entity 装角色自己（成长 + 身体）；其他 entity 装该对象（看法基线 + 相关状态）。
- "上次什么时候更新的"**不落字段**：从 `evolution.jsonl` 最后一条 entity 更新行推。

### 3.0 entity 的字段与初始化（2026-09-21 定案）

```python
# entity 节点（**定稿形状**）
id: str              # x0001（x0000 = self, 保留 0 号）
kind: str            # "entity"
name: str            # 主名字（"老师"）
aliases: list[str]   # 别名（消解的目标；**不做"自动累积"机制** —— 见下）
text: str            # 立场 / 成长基线（原 overview）
state: list[str]     # 物理状况句清单
event_seq: list[int] # 它从哪些事件里长出来的（溯源 + 车道温度）
ts: str              # 首次形成的时刻（"认识多久了" + §9-1 的陈旧判定）
```

**不要的字段**（都按用户裁决）：`etype`（改由 `x0000` 约定）· `significance`（entity 不是
"值得记的事"，常驻层排序用派生信号）· `observer` / `tags`（转述者与检索词对它无意义，它不进
语义召回）· `epistemic`（"见过 vs 只听说过"用 `text`/`state` 说得清，先别加第三个语义层）。

- **初始化就有两个 entity**（用户裁决）：**`self`** + **`sensei`**（老师/玩家）。
  后续考虑按"**熟知程度表**"增加（待议，见 §9-1）。
  ⚠️ 落地要定"谁在什么时候建" —— 纪律是**读路径不写盘**，所以候选：会话打开时幂等
  `ensure_entities()`（无则建、有则跳过）或第一次 digest 时建。**未定**。
  ⚠️ sensei 的名字是可配置的（玩家名在 GUI 里能改）⇒ `name` 取角色视角的"老师"，
  `aliases` 收 `sensei` / 玩家名 —— 玩家改名时怎么办**未定**。
- **`text` 的初值** = 建 entity 时写"她对他的初印象"一句；之后按 §8.3 只喂"旧基线 + 本轮新增"。
- **`new_entity` 准入**（用户裁决）：**必须给一句理由**（照 §8.1"判 add 要在 note 里说明理由"
  的先例）+ 那句自检题"**三个月后再提到，需要一致吗？**"
- **`aliases` 不做"自动累积"机制**：维护别名是**效率优化，不是能力**（候选表只有几十条，
  第 3 轮本来就能靠字面比对 + 读正文判）。⇒ 字段留着、初始化写死几个，第 3 轮**在它已经判定
  "hint 就是这个人"时顺手把 hint 写进去**（零额外成本、零新机制）—— 而不是专门造一条维护路径。

- ⭐ **两个载荷的分工是"立场 vs 物理"**（2026-09-21 用户正名）：`overview` = **立场/成长基线**
  （主观、慢变、只在确有成长时改）；`state` = **物理状况**（身体 / 外观 / 随身，客观、会变、
  会自愈）—— `state` **本来就是为物理状况设计的**，所以**不需要再分一个 `body` 字段**。
  这也顺手把 entity 内部对齐到 §3.1 那条轴：`overview` 属心智侧，`state` 属世界侧。

### 3.1 准入与解耦判据（2026-09-21 定案）

> 起因：**entity 会膨胀**。LLM 见到新名词就想给它一个身份（送一盆杂草 → 标一个 entity；
> 去一家饭馆 → 标一个 entity），只要不给准入条件，增长率就是 O(章节数)。
> 量化（用 §8.3 的两层算）：**身份表便宜**（100 条 ≈ 1000 字）、**载荷贵**（100 条 ≈ 1~2 万字，
> 而载荷是**每轮注入**的）⇒ 膨胀真正命中的是**载荷**，不是表长。

**第一步：分清两个 store。**

| | 装什么 | 特征 |
|---|---|---|
| **心智模型**（她脑中） | `episode` · `belief` · `entity.overview`（立场）· `fact`（**她眼中的**事实） | 主观、可错、**正文不可改**（"当时她怎么想的"） |
| **世界模型**（世上） | 时间 · 地点 · 物品 · 身体 · 好感数值 · 承诺（半） | 客观、可变、**引擎可独立维护** |

**RP 的丰富性来自两者之差**（她不知道的 / 记错的 / 以为的）—— §5 那句"fact 允许与 canon 冲突"
就是这条轴的一个特例。

**第二步：两问判据。**

```
① 真源在她脑外吗？   不在 → 就是记忆（belief / fact / episode），**别解耦**（新知识属于这档）
② 是"痕迹"还是"当前值"？
   · 痕迹（谁给的 / 哪来的, 可追加）→ **台账字段**, **可以不常驻**
   · 当前值（会变 / 会自愈）      → 留在 entity 的 `state`, **必须常驻**
```

⚠️ **"解耦"≠"搬出提示词"**：身体状态之所以不外置，就是因为**她不能下一场忘了自己手上有伤**
—— 而 `state` 已经在常驻层里了，搬出去只会多一个常驻块、或者漏掉。

| 对象 | ① 脑外真源 | ② 痕迹 | 结论 |
|---|---|---|---|
| `entity` | ✅ | — | **kind**（被 `about` 指着 + 有 overview/state 要维护） |
| `promise` | 半 | ✅ | **kind**（`formed_by` 指过来 + 状态机 + 进常驻层） |
| **物品** | ✅ | ✅ | **episode 上的字段 `items`**（见下） |
| 身体 / 外观 / 随身 | ✅ | ❌ 当前值 | entity 的 `state`（§3） |
| 新知识 / 能力 | ❌ | ❌ | **不解耦** —— 它们就是 belief / fact |
| `fact` | ❌（"她眼中的"） | — | ⏳ 未定（§9-2） |
| 地点 | ✅ | — | ⏳ 挂起（§9-5） |

**第三步：`items` 落在哪（定案）。**

```python
# episode 节点上多一个字段 —— **不是 kind、不是边、不是新文件**
items: list[str] = field(default_factory=list)     # ["一盆杂草", "锈饼干盒"]
```

- **谁写**：第 1 轮（和 episode 正文同批，它本来就在写这件事）—— **不新增轮次、不新增写者**。
- **为什么不做 kind**（判据的落点：**有没有别的节点要指向它 · 有没有状态要维护** —— 两问皆无）：
  没有节点要指它（归属仍指向会辐射的对象）、没有状态机、不进召回车道（episode 被召回时
  物品**跟着正文一起来**，比单独召回更好）。做成 kind = 纯付账不收货。
- **物品不是"被归属的对象"，而是"事件留下的痕迹"** ⇒ 它**不被 `about` 指向**；
  `about` 照旧指向会辐射的对象（老师 / `self`）。§2 的语义一个字都不用改。
- **不进常驻层**（用户 2026-09-21 暂定）：全量台账 100 件 × 30 字 ≈ 3000 字，每轮注入不值当。
  而"**她此刻手边有什么**"这个真正常驻的需求，由 `state`（物理状况，含随身）满足。
- 形状：数组元素 = **裸字符串**（与 `tags` 同款；需要注解时先写在 episode 正文里）。
- **物品再次出现**由 LLM 在正文里自己连（"那顶帽子" ↔ 某条 episode 的 `items`）——
  引擎不需要机械地知道它们是同一个东西（这与"不进常驻层"一致）。
- **副作用（很划算）**：物品不进 entity 表 ⇒ entity 只因人 / 地点增长（一章 0~1 个新人）
  ⇒ **`archive`（超 N 轮未标注就移出候选表）、"事件级 entity"、"改名 identity"三套机制都不需要了**。

## 4. 注入两档（本模型的核心分界）

| 档 | 内容 | 行为 |
|---|---|---|
| **常驻层** | `entity`（`overview` 立场 + `state` 物理）· `promise`（未兑现） | 每次注入，**与 query 无关** |
| **按需层** | `belief` · `episode` · `fact` · **`items` 台账** | 按 query / 按本轮涉及的 entity 取 |

判据（以后新增字段时复用）：**不常驻会出什么错？** —— 会自相矛盾、或会失约的，进常驻层。

## 5. fact（暂时）

- **entity 直取**：按 entity 键取出，不进语义排序、不做独立 kind —— 因为 fact 现在并不多。
- **生产者 = digest 第 1 轮**（与 episode / belief 同批产出，见 §8）。
- 语义是"**她眼中的**事实" ⇒ **允许与 `config/` 的 canon 冲突**（她可以是错的，冲突本身是线索）。
- 边界：canon（作者真相）永远在 config；fact（她眼中）在 wiki。
- ⏳ **"暂时"标记**：自由对话 / 多人会让它变多，届时再提升为独立旁路车道（§9）。

## 6. promise

- 图内**节点**，状态机：`open / kept / broken / superseded`。
- 边：`from`/`to`（双方）· `formed_by`（多段 episode，共有）· `supports`（承诺会长出认知）。
- **未兑现的永远进提示词**（query 无关）—— 她答应过的事，不该等被问到。
- 闭合**不需要新机制**：真源 append-only ⇒ "兑现/作废" = 追加一条状态事件、读侧算最新
  （与 `bond/story_pick` 完全同一模式，已有先例）。

## 7. 时间

- **记忆的时间锚 = 这段剧情落地时的现实时刻**（已有 `ts`）：VN 结束的那一刻，就是这剧情发生的日子。
- 剧情内部的"我们认识三个月了"是**叙事文本**，不落时间字段、也不与壁钟对齐。
- "时间加速"是背后的**物理层小解释**（角色不知道、玩家也不知道）。
- ⇒ **节点零时间字段**；"昨天 / 去年"由渲染层算。

## 8. digest 三轮（2026-09-21 定案）

> 起因：正文是自然语言（"老师 / sensei / 他"混用），而 `about` 要指向**唯一 entity**。
> 结论：**改 digest 的形状**——把"创作"与"判定"分到三轮里（同 2026-08-31 那条教训：
> 让主 LLM 逐句内联情绪 → 注意力分散、重试爆炸 ⇒ 后来拆成两遍式标注层）。

| 轮 | 读什么 | 写什么 | **禁止** |
|---|---|---|---|
| **1 产出** | 时间线（记录级带索引）· 人设锚点 · 视觉记忆 | `episode` / `belief` / `fact` 的**正文** + `aspect` + 情绪标量 + **`about_hint`**（自然名字："我在写谁"） | 引用任何现有节点 id · 判"这是不是新的" |
| **2 链接/裁剪** | 本轮新节点 · 现有认知（本地 id 渲染）· 引擎候选 | 边（`supports` / `contradicts` / `evolved_from`）· `update`（改写旧认知）· `merge` · 裁掉错边 | **新建节点**（add 只在第 1 轮） |
| **3 归属 + entity 维护** | 全量候选表（**只有身份**）· 命中集的**当前载荷** · 本轮新节点 | `about`（映射 hint→id）· `mentions` · `new_entity` 提案 · **重写 entity 载荷** | 改正文 · 合并节点 |

**顺序取 A（产出 → 链接 → 归属）**：合并的本判据是语义（"这两条是不是一回事"），
entity 只是加速与约束；且 A 保住了"**归属层可独立重跑而不动图**"这个值钱的性质。

### 8.1 两条纪律（不写死就会互相踩）

- **第 1 轮只 add**，一切"是否已存在 / 要不要合并"归第 2 轮。今天 Round B 同时干 add 与
  update，还得让模型在 note 里解释"为什么不是复用"——那是它最容易出错的地方。
- **entity 载荷的写者唯一 = 第 3 轮**（多处写会打架，同"谁有写权限"那条老教训）。

### 8.2 第 1 轮给 hint，不给 id（"表不进第 1 轮"）

`about_hint` = 自然名字（`老师`），**不落库**（三轮之间内存传参）。

理由：第 1 轮在写正文，那时它心里本来就有这个名字（零成本）；而"从候选里挑 id"是**闭集选择**，
会把 **entity 表搬进第 1 轮的 prompt**——表是会变的（新对象登记 / 别名增补），
而第 1 轮的 prompt 属于**稳定前缀**（吃上下文缓存），表一变前缀就变。

⇒ 分工一句话：**第 1 轮说"我在写谁"（名字），第 3 轮说"那对应表里的哪一个"（id）。**
第 3 轮拿 hint 做**映射**（不是推理）；hint 对不上或没给，才回落到读正文判。

### 8.3 载荷注入分两层

| 层 | 内容 | 规模 |
|---|---|---|
| **候选表**（全量，**不裁剪**） | 本地 id + 名字 + 类别（`e0001 老师（人）`） | 全部 entity（几十条；用户判断"40 个不构成注意力问题"） |
| **载荷区**（只给命中集） | 该 entity 的 `overview` + `state` | 通常 1–3 个 |

命中集由**确定性规则**算：`about_hint` ∪ `别名命中本轮正文`（不靠 LLM）。
⚠️ **改写基线只喂"旧基线 + 本轮新增"**，不喂该 entity 的全部 beliefs —— `overview` 是慢变量，
更新天然是增量的；喂全量会让成本与漂移都上来。触发也在此：**每轮命中集里问一次**，
水位不落字段（需要时从 `evolution.jsonl` 最后一条 entity 更新行推）。

### 8.4 归属三态 + 复查队列 —— ⏸ **2026-09-21 退回未定**

> 用户裁决：**"先不做这个，再考虑考虑"**（原话针对 `about_state` 字段）。下面的设计**保留作候选**，
> 但**不要照它落地**；待定项见 §9-6。

```
about_state      → resolved / uncertain / none   ← **点的属性**（不是边属性: uncertain 恰好意味着"还没有边"）
```

- **不阻塞**：`uncertain` 的**不落 `about` 边**、**不进 entity 车道**（免得污染"关于某人的看法"聚合），
  但仍进按需层普通召回——记忆不丢。
- **下一轮过目**：第 3 轮把队列里的条目 + **可能相关的新正文**一起过一遍；后续剧情
  往往自己给出答案（"他"后来被点名了）⇒ 多数条目第 2~3 轮就落地。
- **队列要能自终止**（默认值，可调）：每轮最多带 **N = 5** 条（最老优先）；连续 **K = 3** 轮
  仍不确定 → 停止复查，降级为"**永久未归属**"，只在人为重挂时处理。
  ⚠️ "复查了几轮"**不落字段**：从 `evolution.jsonl` 数（同 `history` 那次的口径——审计的事归审计日志）。
- 形状与 `BondStoryEngine._pending_feedback` 同款（本轮判不了 → 下一轮念一次 → 自清）。

### 8.5 讨论中改掉的两个口径

- ❌ "**不许猜**"红线 **降级为"可以猜，但错了要留痕"**。因为**正文与结构的寿命不同**：
  正文（`text` / `verbatim`）是 append-only 的记忆，改了等于篡改"当时她怎么想的"；
  而边 / `about` / entity 载荷是**派生的组织方式**（`wiki.jsonl` 本来就整写）⇒ 挂错按
  **可修的错**处理，甚至可以是"她的理解错误"这个叙事资产。前提只有一条：**看得见**
  （`evolution.jsonl` 留痕 + 未归属台账）。
- ❌ "候选裁剪（别名粗筛 + 向量 top-K）" **不做**——40 条不稀疏注意力。真正会膨胀的是
  "给每个 entity 附载荷"，那由 §8.3 的两层注入解决。

## 10. 已否决（别再提）

| 项 | 结论 | 理由 |
|---|---|---|
| **节点做成父类 / 子类** | ❌ **不做**（2026-09-21 用户裁决） | 改动面太大：要动 ~60 处分派点 + store + 一大批测试，而本仓**没有类型检查**（`isinstance` 与 `kind ==` 运行时等价），子类拿不到静态分派安全；收益主要是"字段归属与不变量有地方放"，那些可以用**表驱动**更便宜地拿到（见下） |
| **运行时用 networkx（或现成图 API）** | ❌ **不做**（2026-09-21） | nx 确实提供 `remove_node`/正反邻接/算法，但代价是：① **磁盘格式被它的 schema 绑住**（3.x 把 `node_link_data` 的 `links` 改名成 `edges`——我们的"旧档宽容读、无迁移脚本"纪律会被迫跟着迁移）② 运行时加依赖（`wiki_v2` 现在纯 stdlib）③ 原子写/宽容解析/旧档兼容仍得自己写，省不掉。**dev 侧照旧可用**（`tools/wiki_viz.py`）；要算法时一行桥建图 |

**替代方案（不在本稿内，需要时另立）**：保持一个 dataclass、按 `kind` 分派，但把
**"每个 kind 有哪些字段 / 哪些必填"收进一张表**，由表驱动 `to_dict` / `from_dict` / `validate`。
今天这件事散在**四份平行维护的清单**里（`KINDS` · `_REQUIRED` · `to_dict` 的字段元组 ·
`store._PREFIX`），删一个字段要改 5 处——2026-09-21 的化简里已经反复踩到。
⚠️ 成本提醒：这条替代方案本身也要 ~1 提交 + 契约夹具，**要动时先讨论**。
