## 1. 三层 + 两个旁支

```
                ┌──────────────── entity ────────────────┐
                │ text(立场/成长基线) · state(物理状况句)  │
                │ name · aliases（消解的目标）            │
                └──┬────────────┬────────────┬───────────┘
          about ↑ │            │            │ ↑ about
                │ │            │            │ │
   belief（离散命题: 看法/规律/结论）    fact（她眼中的事实）
        ↑ supports          ↑ source
        │                   │
   episode（经历）──────────┘
        ↑ formed_by × N
   promise（未完成的事, 带状态机）──supports──→ belief
        └ from / to → entity（双方）
```

- **entity** —— 一个对象 + 角色对它的**立场**。⚠️ **不做 `etype`**（2026-09-21 用户裁决）：
  只保留 **`x0000` = self** 这个 id 约定（v3 §2.8）。原来的五类（`self/person/place/item/knowledge`）
  已被后来的裁决拆掉四类 —— `item` 与 `knowledge` 由 §3.1 判走（物品是 episode 的字段、新知识就是
  belief/fact）、`place` 挂起（§9-5）。**多一个枚举 = 多一个要维护、要裁决、要写进 prompt 的东西，
  而它今天不改任何行为。**
- **belief** —— 对某 entity 的**离散命题**，entity 的第一层辐射。
- **episode** —— 经历。支撑 belief；**也允许直连 entity**（没形成认知的经历也要有归属，
  否则按对象聚合会漏掉大半经历）。
- **fact**（旁支，仍在图内）—— **她眼中的事实**（可对可错）。不参与排序，走旁路。
- **promise**（旁支，仍在图内）—— 带状态机的"未完成的事"；可连**多段** episode（共有）。

### 1.1 三种组织形式：**图 / 笔记 / 台账**（2026-09-23 讨论形成）

> 起因：`experience` / `promise` / `item` 反复定不了调。结论是**它们本来就不该进图** ——
> 它们的价值不在"邻接"，而在"**跨事件汇总 / 当前状态**"。用户原话：
> *"这些节点没有被定调，就是因为它们本身就游离在这个连接的体系之外或者连接方式极其特殊。"*

| 形式 | 装什么 | 价值来源 | 消费方式 | 今天 |
|---|---|---|---|---|
| **图**（`wiki.jsonl` + `edges.jsonl`） | **离散事实**：一次经历 / 一条看法 / 一个对象 | **邻接**（能沿着边走） | 引擎**常驻注入** + 她将来**主动 `recall`**（§11） | 已落地 |
| **笔记**（`notes.json`） | **跨事件汇总 / 当前状态**：还没做的事 · 他给我的东西 · 我们之间的老规矩 · 我最近在意的 | **内容 + 当下有效性** | **常驻**（小、有限） | §3.2 设计，未实现 |
| **台账**（`inventory`） | **当前持有**：她此刻拥有 / 带着什么 | 内容 + 来源 | **按需查**（`recall{scope:inventory}`） | **只留接口**（§3.3） |

**准入三问**（以后遇到新东西先问这三条，别再纠结十几轮）：

1. **引擎要不要处理它？** 要（去拆 / 改 / 淘汰）⇒ 必须**严格结构化**；不要（只搬运）⇒ 允许自然语言。
   ⚠️ 用户前提原话：*"能不让 LLM 做的前提是 note 里的内容 engine 都能正确处理。"*
2. **它靠邻接定义吗？** 靠（有别的节点要指向它 / 要按关系查）⇒ **图**；不靠 ⇒ 笔记或台账。
3. **它是痕迹、当前值，还是汇总？** 痕迹 ⇒ episode 字段；当前值 ⇒ 台账（或 entity 的 `state`）；汇总 ⇒ 笔记。

⚠️ **图的强项只有"从一点走到相邻点"**：没有 traverse 者时，图 ≈ **带 id 的列表**。
真机证据：`about` / `supports` 有数据但**零消费者**；`contradicts` 与 entity 载荷**从未进过任何 LLM 上下文**。
⇒ **边的存在理由 = 有一条能走的路**（§2.2）。

## 2. 边（带类型，取代今天那根无类型的 `links`）

> ⚠️ **2026-09-23 按"形状"重排过**（用户：*"这个边体系是不是有点混乱啊"*）——
> 平铺看不出重复，**按 `src → dst` 分组**才看得出"哪种形状有几条边、各自什么角色"。
> 自查结论：**8 条没有真重复**；当时新提的 `mentioned_in` / `ended_by` **撤回**
> （它把 `promise → episode` 从一个边裂成两个，而且分的是**时刻**不是**角色**）。

| 形状（src → dst） | 边 | 角色 / 含义 |
|---|---|---|
| X → entity | `about` | **归属** —— belief / fact / promise / episode 都能指（"有边 = 归好了"） |
| promise → entity × 2 | `from` / `to` | **承诺双方**（与"归属"正交的另一根轴） |
| episode → belief · promise → belief | `supports` | **支撑**（同一条边跨两个形状） |
| promise → episode × N | `formed_by` | ⭐ **这条约定的相关经历**（说定 + 后来谈到 / 兑现的那些） |
| 同层之间 | `contradicts` | **矛盾**（她后来发现不对） |
| 同层之间 | `evolved_from` | **新取代旧**（belief↔belief；promise 的"被取代"也走它） |
| fact → episode | `source` | 她怎么知道的 |

⚠️ **`formed_by` 的语义 2026-09-23 放宽**：原稿写"**怎么一次次说定的**" —— 但"哪条经历了结了它"
不需要在边上编码：**`state` 说结果（kept / broken / superseded），`ts` 说顺序**，按时间读
就是这条承诺的完整故事。⇒ 走法 = "**这条约定一路上的经历**"，**不再新增第二条 promise → episode 的边**。
⚠️ 形状名（`episode|belief` 这种）**不做**：① 有的形状本来就不止一条边（`promise → entity` 有
三种角色、同层有两条），形状名会逼出 `promise|entity:from` 这种更乱的写法
② **走法按"问题"走，不按"类型对"走**（§2.2）③ 模型将来**会看到**边名（`render_organize_view`
把类型印进组织轮输入，G3 特意改的）④ 真机 `edges.jsonl` 存的已经是这 8 个名字，改名 = 老档映射。

**归属**：`about` 边是归属的**唯一落地形式** —— **有边 = 归好了；没边 = 没归**。
⏸ 原"三态"设计（`about_state ∈ resolved/uncertain/none` **挂点上**、`uncertain` 进复查队列）
**2026-09-21 用户裁决"先不做，再考虑考虑"** ⇒ 从"定案"**退回未定**（§9-6）。
连带后果：`uncertain` 的条目暂时**没有落点**（队列是给它兜底的）—— 第 3 轮判不出就不建边，
也不追踪（待 §9-6 定）。

### 2.1 存储与索引（2026-09-21 定案）

**点边分离，两个文件**：

```
soul/wiki.jsonl     点 —— 一行一节点（**不动**，迁移面 = 0，grep 友好）
soul/edges.jsonl    边 —— 一行一条 {"rel","src","dst","ts"}
```

（代码里用 `src`/`dst`；上表的 `from`/`to` 是 rel 名，落到 JSON 键会撞 Python 关键字。）

**运行时 = dict 邻接索引**（纯 stdlib），载入时建三个：

```python
out:    dict[str, list[Edge]]   # src → edges    "我指向谁"
inc:    dict[str, list[Edge]]   # dst → edges    "谁指向我"
by_rel: dict[str, list[Edge]]   # rel → edges    "所有 about 边"
```

六类查询各一行（这也是"够不够用"的验收口径）：

| 查询 | 写法 |
|---|---|
| entity E 下的 beliefs | `[e.src for e in inc[E] if e.rel == "about" and kind(e.src) == "belief"]` |
| belief B 的支撑经历 | `[e.src for e in inc[B] if e.rel == "supports"]` |
| promise P 的共有经历 / 双方 | `[e.dst for e in out[P] if e.rel == "formed_by"]` / `rel in ("from","to")` |
| 1-hop 扩展（召回） | `out[n] + inc[n]` |
| **未归属清单** | **非 entity** 节点 − `{e.src for e in by_rel["about"]}`（复查队列直接用它） |
| 删节点 | 节点表删 + 边表过滤一遍 ⇒ **"悬空引用/双向一致"在构造上不可能存在** |

⚠️ **未归属清单要排掉 entity 自己**（G1 落地时复核出来）：`about` 边的方向是"节点 → entity"，
所以 entity **永远不会**是 `about` 的 `src` —— 不排的话每个 entity 都会冒充"未归属"。

**推断层的 `unknown`（G1 专有）**：今天那根无类型 `links` 判不出类型的对
（`belief`↔`belief` · `belief`↔`experience` · `episode`↔`episode`）发一条 `rel="unknown"` ——
**不猜**（`evolved_from` 的语义是"新看法取代旧的"，一条无向边说不出谁取代谁，猜错方向比不判贵），
但**也不丢弃**（丢了会让 1-hop 比今天的 `links` 更窄）。G3 落盘后写路径总是知道 rel
⇒ `stats()["unknown"]` 应当归零，**它就是那条验收线**。

**三条边界（写死，免得以后反复）**：

1. **运行时纯 stdlib**：`core/brain/wiki_v2` 现在没有第三方依赖（只有 `json`/`dataclasses`/`logging`），
   CLI/测试/实验脚本都能独立跑。**networkx 只留在 dev 侧**（`tools/wiki_viz.py` 已在这么做）；
   要图算法时用一行桥（`G.add_edges_from(iter_edges(store))`）在分析脚本里建图。
   ⇒ 触发条件：只有出现"我们写不动的算法"（最短路解释支撑链 / 社区发现做合并候选 / 中心性做召回加权）才评估升级。
2. **磁盘格式自持**：不用第三方序列化（nx 的 `node_link_data` 就是活例子——3.x 把 `links` 键改名成 `edges`）。
   我们的纪律是"**旧档宽容读、无迁移脚本**"，格式一旦外包，库的升级就变成我们的数据迁移。
3. **不做双写**：不搞"边表与节点内 `links` 并存一段时间"——那是第二个真源。数据 5 节点 / 消费者 12 文件
   ⇒ 一步到位比长期双真源干净。**G3 已按这条落地**：写路径只写边表，`links`/`contradictions`
   在点表里变成"**读得进、写不出**"（旧档自举还要读它，见 G3 行）。
4. **两个文件不是一次事务**（G3 加）：`save()` 是两次 `atomic_write_lines`，写序 = **先点后边**
   —— 点写成功而边写失败, 后果是"边表陈旧（少几条新边）", 记忆正文完好、可重算;
   反过来会留下一批悬空边。两条都只降级不损坏, 但前者更好收拾。
   一致性靠**读侧宽容**（悬空边保留, 由 `audit()` / `Graph.dangling()` 报），不靠事务。

**落地分步（叶子优先，每步一提交 + 全量 + B 层冒烟）**：

### 2.2 边的"走法"（2026-09-23 讨论形成）

**判据：一条边值不值钱，看它有没有一条能走的路。** 没有走法的边不是"零成本的常量"，
而是**会误导后来人的装饰**。

| 边 | 走法（谁能沿它走到哪） | 她因此能说出的话 |
|---|---|---|
| `about` | 对象 → 关于它的一切 | "关于老师的事，我记得的有…" |
| `supports` | 看法 → 它的证据（**可数**） | "我为什么这么觉得？因为那天…还有那次…" |
| `contradicts` ✅ **保留**（用户 2026-09-23） | 一条 → 与它冲突的另一条 | ⭐"**我上次说的跟这次不一样**" —— RP 里最精彩的瞬间 |
| `evolved_from` ✅ **保留**（同上） | 新看法 → 它取代的旧看法 | "我以前觉得…现在不这么想了" |
| `from` / `to` | **固化后的承诺** → 承诺双方（§6） | "关于某人的承诺，哪些做到了"（entity 车道） |
| `formed_by` | **固化后的承诺** → 它一路上的经历（§6；**从"说定"放宽成"相关"**） | "这条承诺是怎么说定的、后来怎么了"（走回 episode 看细节） |
| `source` | `fact` → 它的来源（**fact 未立项**） | —— |

⚠️ **8 条边一个都不删**（用户 2026-09-23 裁决：*"边不许删，还记得已完成 promise 固化吗"*）——
**走法不必"现在就有"，可以是"固化后出现"**（§6 的两段式就是例子）。

⇒ 两个推论：
- ⭐ **`degree`（被印证几次）不必预存** —— 沿 `supports` 数一数就知道（"能走出来的东西，不必先算好"；
  与 G4 删 `count` 同一思路）。**连带：`degree ≥ 2 浮现` 那套运行时门槛可以整块不做。**
- **引擎不该再把图压成列表**（`_bucket_view` 那套是"列表化"）。未来的引擎职责是**给图 + 给走法**。

## 3. entity 载荷

```
entity
├── name / aliases      实体消解的目标（"老师 / sensei / 他" → 同一个 entity）
├── text                **立场 / 成长基线**（慢变: 只在确有成长时改）—— 原 `overview` 的语义
└── state               物理状况句清单（粘性: 换了发型 / 手上多了道划痕 / 今天戴了眼镜）
```

- ⭐ **`overview` 不落字段：它的语义由共用的 `text` 承担**（2026-09-21 用户裁决）。
  于是 entity **不需要新字段**，也**不必**把 `text` 从"共用字段"里降级出去。
- **两个载荷的分工是"立场 vs 物理"**：`text` = **立场/成长基线**（主观、慢变、只在确有成长时改）；
  `state` = **物理状况**（身体 / 外观 / 随身，客观、会变、会自愈）—— `state` **本来就是为物理状况
  设计的**，所以不需要再分一个 `body` 字段。这也把 entity 内部对齐到 §3.1 那条轴：
  `text` 属心智侧，`state` 属世界侧。
- **同块注入、不分家**：LLM 每次看到 entity 就知道"她/他当下是什么样" ⇒ **防前后矛盾**
  （这正是这一层存在的理由）。
- 写纪律：**只改变化的那一行，其余原样复制** —— diff 可读、改动可审、不会每次整体重写漂移。
- `self` entity 装角色自己（成长 + 身体）；其他 entity 装该对象（看法基线 + 相关状态）。
- "上次什么时候更新的"**不落字段**：从 `evolution.jsonl` 最后一条 entity 更新行推。

### 3.1 准入与解耦判据（2026-09-21 定案）

> 起因：**entity 会膨胀**。LLM 见到新名词就想给它一个身份（送一盆杂草 → 标一个 entity；
> 去一家饭馆 → 标一个 entity），只要不给准入条件，增长率就是 O(章节数)。
> 量化（用 §8.3 的两层算）：**身份表便宜**（100 条 ≈ 1000 字）、**载荷贵**（100 条 ≈ 1~2 万字，
> 而载荷是**每轮注入**的）⇒ 膨胀真正命中的是**载荷**，不是表长。

**第一步：分清两个 store。**

| | 装什么 | 特征 |
|---|---|---|
| **心智模型**（她脑中） | `episode` · `belief` · `entity.overview`（立场）· `fact`（**她眼中的**事实） | 主观、可错、**正文不可改**（"当时她怎么想的"） |
| **世界模型**（世上） | 时间 · 地点 · 物品 · 身体 · 好感数值 · 承诺（半） | 客观、可变、**引擎可独立维护** |

**RP 的丰富性来自两者之差**（她不知道的 / 记错的 / 以为的）—— §5 那句"fact 允许与 canon 冲突"
就是这条轴的一个特例。

**第二步：两问判据。**

```
① 真源在她脑外吗？   不在 → 就是记忆（belief / fact / episode），**别解耦**（新知识属于这档）
② 是"痕迹"还是"当前值"？
   · 痕迹（谁给的 / 哪来的, 可追加）→ **台账字段**, **可以不常驻**
   · 当前值（会变 / 会自愈）      → 留在 entity 的 `state`, **必须常驻**
```

⚠️ **"解耦"≠"搬出提示词"**：身体状态之所以不外置，就是因为**她不能下一场忘了自己手上有伤**
—— 而 `state` 已经在常驻层里了，搬出去只会多一个常驻块、或者漏掉。

| 对象 | ① 脑外真源 | ② 痕迹 | 结论 |
|---|---|---|---|
| `entity` | ✅ | — | **kind**（被 `about` 指着 + 有 overview/state 要维护） |
| `promise` | 半 | ✅ | **kind**（`formed_by` 指过来 + 状态机 + 进常驻层） |
| **物品** | ✅ | ✅ | **episode 上的字段 `items`**（见下） |
| 身体 / 外观 / 随身 | ✅ | ❌ 当前值 | entity 的 `state`（§3） |
| 新知识 / 能力 | ❌ | ❌ | **不解耦** —— 它们就是 belief / fact |
| `fact` | ❌（"她眼中的"） | — | ⏳ 未定（§9-2） |
| 地点 | ✅ | — | ⏳ 挂起（§9-5） |

**第三步：`items` 落在哪（定案）。**

```python
# episode 节点上多一个字段 —— **不是 kind、不是边、不是新文件**
items: list[str] = field(default_factory=list)     # ["一盆杂草", "锈饼干盒"]
```

- **谁写**：第 1 轮（和 episode 正文同批，它本来就在写这件事）—— **不新增轮次、不新增写者**。
- **为什么不做 kind**（判据的落点：**有没有别的节点要指向它 · 有没有状态要维护** —— 两问皆无）：
  没有节点要指它（归属仍指向会辐射的对象）、没有状态机、不进召回车道（episode 被召回时
  物品**跟着正文一起来**，比单独召回更好）。做成 kind = 纯付账不收货。
- **物品不是"被归属的对象"，而是"事件留下的痕迹"** ⇒ 它**不被 `about` 指向**；
  `about` 照旧指向会辐射的对象（老师 / `self`）。§2 的语义一个字都不用改。
- **不进常驻层**（用户 2026-09-21 暂定）：全量台账 100 件 × 30 字 ≈ 3000 字，每轮注入不值当。
  而"**她此刻手边有什么**"这个真正常驻的需求，由 `state`（物理状况，含随身）满足。
- 形状：数组元素 = **裸字符串**（与 `tags` 同款；需要注解时先写在 episode 正文里）。
- **物品再次出现**由 LLM 在正文里自己连（"那顶帽子" ↔ 某条 episode 的 `items`）——
  引擎不需要机械地知道它们是同一个东西（这与"不进常驻层"一致）。
- **副作用（很划算）**：物品不进 entity 表 ⇒ entity 只因人 / 地点增长（一章 0~1 个新人）
  ⇒ **`archive`（超 N 轮未标注就移出候选表）、"事件级 entity"、"改名 identity"三套机制都不需要了**。

### 3.2 note（随身笔记）—— 2026-09-23 讨论定形，**未实现**

> 定位：**她的随身工作台**。不是记忆（不改写历史）、不是人设（不装设定）、
> 不是图的镜像（只装**她自己挑过**的 —— 精选，不是全量）。

**三条已定（用户认可）**：

1. ✅ **独立成块，单向引用，绝不穿插。** 一旦写成"依附于对应 episode"的穿插形式，
   主 LLM 会**一头雾水**：一瞥即"我现在的工作集"这个性质被毁掉；而且待办是**关于未来**的，
   挂在哪条 episode 上都是错的。`refs` 是**引用**，不是父子。
2. ✅ **真源 = 事件流（append-only 的操作），`notes.json` = 折叠出来的派生缓存**
   （带 `up_to_seq`；不存在就现折；可随时重建）。⇒ **并发安全**（主 LLM 与 digest 同时写**不丢更新**）、
   **可回放**、**与水位同频**。操作事件用 `type:"note"`，**不进 LLM 上下文历史**（同 `affection` 的处理）。
3. ✅ **不加 tick 动作。** "完成判定"是**判定**不是创作 ⇒ 收口归 digest；主 LLM 只有一个
   **可选顺手字段**（"这轮恰好做了笔记上的某件事"）；**过期由全景轮淘汰**（核对图里已有 ⇒ `retire`）。
   ⚠️ 前提 = 准入三问第 1 条（字段必须按"引擎要不要处理"分，见下）。
4. ⭐ ✅ **`close` 是"结清"，不是"划掉"**（2026-09-23 用户裁决追加）—— 见下面的两段式。

⭐⭐ **承诺的两段式之二：`close`（结清）→ `retire`（退场）**

> 起因（用户）：*"note 注入块不可立刻少 —— 这段时间里这个记忆既不存在于 note 里，
> 也不存在于 graph 里，上下文也可能未覆盖，这就有问题了。"*

**根因**：原稿把"**结清**"（判定"这条不再开着了"）和"**退场**"（"图里已经有它了，
本子上可以划掉"）当成了**一件事**，而它们是**不同的人在不同时刻**做的 ——
合成一步，中间必然有真空。而 `promise` 是**唯一"note 是它唯一落脚点"**的东西
（episode/belief 的底料本来就在图里；`habits`/`on_mind` 是概括，丢了不伤事实），
**上下文窗口（120 单元滚动）从来不是保证** ⇒ 一删就可能三处全无。

| 操作 | 谁写 | 语义 | 注入块 |
|---|---|---|---|
| `add {text, refs, due?}` | 当场（主 LLM 输出字段；bond 侧由 **R4 收口**兜底，§8） | 加一条 | 显示 |
| **`close {id, state, reason}`** | **当场**（主 LLM 的 `note_close` 字段）或 **R4 收口** | **结清** | ⭐ **照旧显示**，尾巴 = `← 已兑现（理由）` / `← 没做到（理由）` / `← 被新的取代了（理由）` |
| **`retire {id}`** | **固化那一批**（digest 事务 `ok` 之后由引擎补写） | **退场**（图里已经有了） | 消失 |

- ⭐ **不变量：一条承诺在任何时刻至少在一个可见面上** —— 开着 / 已结清 ⇒ **在 note**；
  已固化 ⇒ **在图**。**永不在两者之外。**
- **附带的结构红利**：*"结清未退场"的条目天然就是收口的待办队列* ——
  不必另造队列，note 自己就是（`text` + `refs` + `reason` 全在手上，连"关掉的这条写的
  是什么"都不用回放）。
- ⚠️ **先固化、后退场**（顺序是正确性）：`events.jsonl` append-only，**不随 digest 的
  `clone_state` 回滚**（快照只含点表 + 边表）。所以 `retire` 必须由引擎在**事务成功之后**
  补写 —— 与好感事件同一个模式（`digest` 只返回决定，事件由引擎在 `ok` 后落）。
- ⚠️ **`retire` 只对已结清的条目生效**：退场一条还开着的承诺 = 把它从唯一落脚点删掉
  （图里根本没有它），正是两段式要堵的洞。
- ⚠️ **已结清的不再覆盖**：块里印着 `id`，若二次 `close` 能改写 `reason`，就是给
  "拿幻觉理由覆盖真实理由"开后门 ⇒ 第二次只告警（幂等 = 忽略）。还开着的那条照旧覆盖。
- ⭐ **`state` 说结果，`ts` 说顺序**（2026-09-23）：`state ∈ {kept, broken, superseded}`
  既进 `note/close` 事件、也进图里那个节点的 `state`。**渲染按 state 分三种尾巴**
  （`已兑现` / `没做到` / `被新的取代了`）—— 于是早先那个**中性词"已结清"退休**
  （它当初存在只是因为不知道 state）。
  ⚠️ `broken` 的措辞**放宽成"没成"**：**失约 + 她自己作废**都算它（不加第 4 态 —— 状态越少，
  模型判得越准）。
- **渲染**：开着的排在已结清**前面**（这个块第一句要回答"我手上还开着什么"）；
  不必分区抬头（局部标记比全局分区更抗误读：分区容易被当成第二份待办清单）。
- **兜底**：digest 一直没跑到 ⇒ 结清条目会一直挂着（`check()` 在积压超过
  `MAX_CLOSED_PENDING=3` 时报一句）。

**文件格式**：`soul/notes.json`（**JSON 单文件**：引擎要局部改 + 校验 + diff；jsonl 是"流"，note 是"一个对象"；
md 引擎拆不动；yaml 我们踩过解析坑）。
⚠️ **存的那份 ≠ 看的那份**：**存 JSON，注入时由引擎渲染成中文小节**（同 `wiki.jsonl` + `render_character_view`）。

**字段按"引擎要不要处理"二分**：

| 类 | 槽 | 装什么 | 更新模型 | 引擎职责 |
|---|---|---|---|---|
| **A 操作式** | **`promise`** | 还没做的事（约定 / 承诺） | **增量操作**：`add` · **`close` 结清** · **`retire` 退场**（两段式，见上） | 折叠 · 幂等 · 去重 · 淘汰 · **分配 `id`** |
| **B 快照式** | **`habits`** | **我们之间的惯例 / 他的习惯**（**跨段才看得见**的重复） | **全景轮整段替换** | **只校验 `refs` + 渲染** |
| **B 快照式** | `on_mind` | 我最近在意的（**一段散文**，她的口吻） | 全景轮整段替换 | 只搬运 |

⚠️ **两条改名**（用户 2026-09-23）：`todos` → **`promise`**（与"固化后的 promise"语义连贯）；
`rituals` → **`habits`**（用户原话：*"礼节也太正式了"*）。

⚠️ **note 里一个字都不写物品**（用户裁决）—— 物品三件事各归各位：
痕迹 → `episode.items`；当前持有 → `inventory`（§3.3）；**情感意义 → 就在那条 episode 的正文里**
（她将来 `recall` 捞得到）。**没有 `gifts` 槽**（本节早先的提案已撤）。

条目结构（A/B 共用）：`{"id", "text", "refs": [...], "since"}`；`promise` 另有可选 `due`，
以及**结清三字段** `closed_at` / `reason` / `state`（`closed_at` 非空 = 已结清）。
**`text` 写名词短语（≤20 字），不写陈述句** —— 避免与 episode 的叙述竞争
（"周六模型店" ≠ "我们约好周六去模型店"）。⇒ 从根上防止"两处写同一件事，LLM 晕掉"。
⚠️ `due` **只存不渲染**（印成日期会诱使她"数日子"，与 `worldtime.age` 那条"绝不输出精确值"冲突）。

**四条不变量**：
① 每项**至少一个 `refs`，且指向现存节点**（悬空 → 记账告警，不阻断；照 `store.audit()` 的做法）
② `promise` 的键 = **`id`**（不是文本 ⇒ 幂等 / 去重 / `close` / `retire` 都精确；防"主 LLM 加一条、digest 又推一条"）
③ 上限 `promise ≤5 / habits ≤5 / on_mind ≤1 段` —— **只算还开着的**，且**超限只告警不截断**（取舍交全景轮）
④ ⭐ **至少一个可见面**：一条承诺任何时刻要么在 note（开着 / 已结清），要么在图（已固化），**永不在两者之外**

**注入版式**（固定位置、固定标题、**不进按时间排序的记忆流** —— 它是当前值，不是事件）：

```
【你自己记的备忘录】（你自己随手记下的, 不是别人给你的任务; 括号里是编号, 指回你记忆里的那件事）
  · 你自己记下的约定
    n3 周六模型店 (m0009)  ← 记于 3 天前
    n2 还他笔记 (m0011)  ← 记于 昨天
    n1 买花 (m0014)  ← 已兑现（送出去了）
  · 你们之间的惯例
    n7 他买东西时总先问我想要哪个 (m0005, m0010)
  · 最近在想
    我不想再只是隔着玻璃看
```

⚠️ **剥离结构化痕迹**（2026-09-23 用户裁决：*"注入的时候记得要剥离 json 等结构，更符合自然语言，
且告诉 LLM 这是什么"*）：**存 JSON，看中文**。注入块里**不许出现** JSON、键名（`promise`/`habits`/
`on_mind`）、波括号 —— **字段名是引擎的词汇，不是她的**。
⚠️ **标题必须说清这是什么**：她是这份备忘的主人（**不是系统派的任务** —— 同一个 system 里还住着
规则书与 task 卡，不说清就会被读成"引擎要她做的事"）+ 括号里是编号。**小节抬头也是自然语言**
（约定 / 惯例 / 最近在想），且**空槽不印**（常驻预算是硬约束）。
⚠️ **`id` 必须渲染出来**（否则她只能靠文本匹配去 tick ⇒ 不可靠）。
⚠️ **开着的排在已结清的前面**；**结清行的尾巴 = 那个 `state` 对应的说法 + 理由**
（`已兑现` / `没做到` / `被新的取代了` —— 不能用光板的"已完成"，它对失约是假话，见两段式）。
⚠️ **频次不进这一块**（既有纪律：**数值不直接喂 LLM**，防讨好/数值化）—— 要不要说"好多次/每次都"由 writer 决定。

**拼接位置（两处注入点, 2026-09-23 落地）**：出厂背景 → wiki 视图 → **笔记块** → 时间注记。
两处 = `load_brain_segment`（bond 开场, `webgui.bond` / `apps.vn_cli` 共用）与
`MmtEngine._inject_brain`（MMT: digest 完成 / resume / 开会话）。⚠️ 两块**同源同频**,
都在这两个时刻重建; **写完一条 note 之后必须重建**（`_brain_injection` 是缓存的串）。

**写者分工（同一段只有一个写者）**：**加** = 当场（MMT 主 LLM 的可选字段 / bond 侧由 **R4** 兜底）·
**结清** = 当场（`note_close`）或 **R4 收口**（§8，它读本段时间线 + 还开着的约定）· **退场** = **固化那一批**
（图侧接住之后）· **归纳（B 类整体重写）** = 全景轮（§8.6）。

### 3.3 台账 `inventory` —— 2026-09-23：**独立成系统，暂时不做，接口不删**

用户原话：*"inventory 作为一个独立系统，**再再再独立**，给 LLM 一个 `inspect_inventory` 即可；
inventory 只需要内容 + 简要来源说明 + 指向。"* ⇒ 它**不进图、不做 kind、不被 `about` 指向**。

**为什么必须独立**（§3.1 那笔账的另一半）：全量台账 100 件 ≈ 3000 字，**每轮注入不值当** ⇒
它该有一个**按需查**的家，而不是"删掉"或"塞进常驻层"。

**三层分工（别抢同一个职责）**：

| 层 | 装什么 | 落点 |
|---|---|---|
| **痕迹**（append-only） | 这条经历里她**得到 / 失去了**什么 | `episode.items`（**保留** —— 它是 inventory 的取材处，不再提"删"） |
| **当前持有**（会变） | **她此刻拥有 / 带着什么** | **`inventory`（本节，独立系统）** |
| 情感意义 | "他给我的东西"为什么特别 | **不单独存** —— 就在那条 episode 的正文里（她将来 `recall` 捞得到；**note 里也不写物品**，§3.2） |

条目结构（与 note 同构）：`{"id","text","from","src","since"}` —— `from` = 简要来源说明（"老师给的"），
`src` = 指向（那条 episode ⇒ 想细节就走图）。

⚠️ **待裁**：`entity.state` 里的"**随身**"要不要移交给 `inventory`？（§3.1 当年把"随身"给了 `state`，
理由是她不能忘了自己手上有伤。）**不移交 ⇒ 两处会抢同一个职责。**

**预留（不实现）**：`recall` 的 `scope` 枚举**一次开全** `{memory, note, inventory}`，
inventory 分支先返回空 —— 省掉将来改 spec 触发的**前缀缓存重建**（§11）。

## 4. 注入两档（本模型的核心分界）

| 档 | 内容 | 行为 |
|---|---|---|
| **常驻层** | `entity`（`overview` 立场 + `state` 物理）· `promise`（未兑现） | 每次注入，**与 query 无关** |
| **按需层** | `belief` · `episode` · `fact` · **`items` 台账** | 按 query / 按本轮涉及的 entity 取 |

判据（以后新增字段时复用）：**不常驻会出什么错？** —— 会自相矛盾、或会失约的，进常驻层。

⚠️ **"谁发起"是另一条轴**（2026-09-23 澄清：**与上面这档不矛盾**）：
**常驻层 = 引擎注入（她不用查）· 按需层 = 她主动 `recall`**（MMT 有 `function_call`，见 §11）。
⇒ 引擎那套"相关性排序 + 注入"（`recall_subgraph` / `compose` / `channels`，今天生产**零调用**）
将来的身份是**查询后端**（她调用的那个工具的实现），**不是**"引擎自动注入的机制"。
判据不变，但**按需层可以无限大**（她自己查），**常驻层的预算是硬约束**（每轮都进 prompt）。
⇒ note（§3.2）与 entity 载荷属常驻；episode / belief / fact / inventory 属按需。

## 5. fact（暂时）

- **entity 直取**：按 entity 键取出，不进语义排序、不做独立 kind —— 因为 fact 现在并不多。
- **生产者 = digest 第 1 轮**（与 episode / belief 同批产出，见 §8）。
- 语义是"**她眼中的**事实" ⇒ **允许与 `config/` 的 canon 冲突**（她可以是错的，冲突本身是线索）。
- 边界：canon（作者真相）永远在 config；fact（她眼中）在 wiki。
- ⏳ **"暂时"标记**：自由对话 / 多人会让它变多，届时再提升为独立旁路车道（§9）。

## 6. promise（**两段式**，2026-09-23 定形）

> ⭐ **开放期在 note，闭合时固化进图**（用户：*"还记得已完成 promise 固化吗"*）。
> 于是 `promise` 有两种存在形态，**同名不同处**：note 里的是"活的"，图里的是"归档的"。
> ⚠️ note 侧自己也是两段式（**`close` 结清 → `retire` 退场**，§3.2）：**固化成功之前，
> 那条一直留在 notes 的块里** —— 否则就会出现"note 里没了、图里也还没有"的真空。

| 阶段 | 住哪 | 形态 | 维护 |
|---|---|---|---|
| **开放期**（未兑现 / 未失约） | **note 的 `promise` 槽**（§3.2） | 一行条目（`id` / `text` / `due` / `refs`），**轻、可覆盖** | 加 = 当场（主 LLM 的可选字段）+ **R4 收口**兜底（bond 侧没有 function_call） |
| **闭合期**（已兑现 / 已失约 / 被取代） | **图** | `promise` 节点 + `state ∈ {kept, broken, superseded}` | 固化那一次写死，之后 append-only |

**固化时落什么**（这就是那四条边的走法 —— 全部保留、**一条都不删**）：

| 边 | 从 → 到 | 谁给 | 固化后能回答 |
|---|---|---|---|
| `from` / `to` | 承诺 → entity ×2 | 引擎（默认 `self` ↔ `sensei`） | "**关于某人的承诺**，哪些做到了 / 哪些没做到" |
| `formed_by` | 承诺 → episode × N | 引擎：note 条目的 `refs` **∪ 本段新增的 episode** | "**这条约定一路上的经历**"（走回 episode 看细节） |
| `supports` | 承诺 → belief | **R2**（链接轮） | "承诺长出了认知"（如"他答应的事都做到了"） |
| `evolved_from` | 承诺 → 旧承诺 | **R2**（被取代时） | "这条是新定的一条，把旧的盖过去了" |
| `about` | 承诺 → entity | **R3**（归属轮） | 走 entity 车道找"关于他的所有承诺" |

⭐ **"哪条经历了结了它"不需要在边上编码**（2026-09-23）：**`state` 说结果，`ts` 说顺序**
—— 按时间读 `formed_by` 的那串 episode，就是这条承诺的完整故事。当初拟的
`ended_by` / `mentioned_by` **都不加**（理由见 §2 的开头）。
⇒ **"万一不是 end"这个问题因此消失**：LLM 只判"这条还开着吗"（`kept`/`broken`/`superseded` + 理由），
**"跟哪条经历有关"由引擎确定性连接**（本段新增的 episode），LLM 没有判错的机会。

⚠️ **为什么两段而不是一段**：开放期的承诺**变化频繁**（随时兑现/失约）+ **必须常驻**（她不该忘），
适合 note 的覆盖式维护；而已闭合的承诺是**历史**，该进图被 traverse（永久、可查、可溯源）。
⇒ 这也顺手回答了"promise 的状态机放哪"：**它不需要一个活的状态机** —— "开着"就是 note 里有一行，
"闭合"就是从 note 移出 + 图里多一个节点（`state` 只写一次）。

⚠️ **固化的时序（顺序是正确性，2026-09-23 定）**：全部发生在**同一批 digest**里 ——
`R4 收口 → 引擎物化 promise 节点 → R2 写它的 supports/evolved_from → R3 写它的 about
→ 提交 → 引擎补 note 事件（add/close）→ 补 retire`。
**批失败 = 整批回滚**（含 R4 的判定）⇒ 那条约定原样开着，下次再来，不需要自愈机制。
⏳ **待裁**：`from`/`to` 只支持"我 ↔ 老师"；**第三方承诺**（"我答应了阿露"）怎么办 —— §9。

## 7. 时间

- **记忆的时间锚 = 这段剧情落地时的现实时刻**（已有 `ts`）：VN 结束的那一刻，就是这剧情发生的日子。
- 剧情内部的"我们认识三个月了"是**叙事文本**，不落时间字段、也不与壁钟对齐。
- "时间加速"是背后的**物理层小解释**（角色不知道、玩家也不知道）。
- ⇒ **节点零时间字段**；"昨天 / 去年"由渲染层算。
- ⛔ **2026-09-23 撤回一条提案**：曾提议给记忆加"**剧情时间**"字段（从文本抽 `M月D日` + 时段）。
  **不做** —— 用户提醒：**现实时间 = 剧情时间**（本节第一句早就定了）。而且真机旧档里还留着那套尸骨：
  `mutsuki` 的 5 条 `story_time`（`sim_day` = 0/15/30/45/60，**每章正好 +15**）= 当年被"累加"污染的假日历，
  也正是 2026-09-17 删掉它的原因。**"轮椅"（模糊时间短语）照旧** —— `render_relative` 现成，
  它本来就在按 `ts` 算，缺的从来不是"剧情时间"。
- ⚠️ **但"时间轴紊乱"的真实形状仍未解**（属链路第 ④ 步，"现实时间=剧情时间"不解决它们）：
  ① **同一批消化 = 同一个 `ts`** ⇒ 十几条记忆共享一天，**无法表达先后**
  ② **消化延迟 ⇒ `ts` 偏移**（事件发生日 ≠ 消化日）
  ③ 时间短语与 `significance` 耦合（`render_relative(age, significance)`）是有意还是巧合
  ④ ⭐ **"演化"的时间怎么表达**：`evolved_from` 边（已定要）/ 行内 `history`（AgentGal）/ 边带有效期（Graphiti，§12）

## 8. digest 每段四步（三轮 + **R4 收口**；2026-09-21 定案，2026-09-23 加 R4）

> 起因：正文是自然语言（"老师 / sensei / 他"混用），而 `about` 要指向**唯一 entity**。
> 结论：**改 digest 的形状**——把"创作"与"判定"分到三轮里（同 2026-08-31 那条教训：
> 让主 LLM 逐句内联情绪 → 注意力分散、重试爆炸 ⇒ 后来拆成两遍式标注层）。

| 轮 | 读什么 | 写什么 | **禁止** |
|---|---|---|---|
| **1 产出** | 时间线（记录级带索引）· 人设锚点 · 视觉记忆 | `episode` / `belief` / `fact` 的**正文** + `aspect` + 情绪标量 + **`about_hint`**（自然名字："我在写谁"） | 引用任何现有节点 id · 判"这是不是新的" |
| **4 收口**（promise 记账，窄） | **note 里还开着的约定**（≤5 条，带编号）+ **本段新增的 episode**（真 id） | `add {text, refs, due?}` · `close {id, state, reason}` | 改正文 · 碰 `habits`/`on_mind` · 指"是哪条经历"（那是引擎的活，见下） |
| **2 链接/裁剪** | 本轮新节点（**含 R4 物化的 promise 节点**）· 现有认知（本地 id 渲染）· 引擎候选 | 边（`supports` / `contradicts` / `evolved_from`）· `update`（改写旧认知）· `merge` · 裁掉错边 | **新建节点**（add 只在第 1 轮 / R4） |
| **3 归属 + entity 维护** | 全量候选表（**只有身份**）· 命中集的**当前载荷** · 本轮新节点（**含 promise 节点**） | `about`（映射 hint→id）· `mentions` · `new_entity` 提案 · **重写 entity 载荷** | 改正文 · 合并节点 |

⭐ **批内顺序 = `R1 → R4 → R2 → R3`**（2026-09-23 用户：*"R4 在 R3 前会不会更好？"* —— 对，
而且必须更早）。理由只有一条：**promise 节点需要的边由后面两轮写**（`supports`/`evolved_from` 是 R2、
`about` 是 R3）⇒ 节点**必须先就位**，否则 R2/R3 根本看不到它，它就"永远没边、永远没归属"
（§9-12 ⑤ 那条"漏一批且永久补不回"的同款错误）。
⚠️ 连带要改一处：`revise._ATTACHABLE` 现在只允许 `episode` / `belief` / `experience`
—— **要把 `promise` 加进去**，否则 R3 想归属它会当场被行级违约打回。
⚠️ **命名轴别混**：**轮次 = `R1`/`R2`/`R3`/`R4`**（本文用这套）；**实施节点 = `D0`/`D1`/`D2a`/`D2b`/`D3a`**
（落地顺序那套）—— §9-12 ⑧ 里那句"顺序 D4 → D3"说的是**后者**（先把 belief 产出搬到 R1，再接第 3 轮），
**与 R4 无关**。
⚠️ **失败 = 整批回滚（含 R4 的判定）** ⇒ 那条约定原样开着，下次再来；不需要任何自愈机制。

⚠️ `mentions` **暂不实现**（2026-09-23 用户: *"先留着, 不碍事"*）—— 这个词留在表里是
记号不是待办: 要落它得先有 rel（§2 的八种里没有）与消费者, 现在两样都没有。

**顺序取 A（产出 → 链接 → 归属）**：合并的本判据是语义（"这两条是不是一回事"），
entity 只是加速与约束；且 A 保住了"**归属层可独立重跑而不动图**"这个值钱的性质。
（R4 插在 R1 与 R2 之间，不改这条骨架。）

⏳ **"note 跟 VN 并发"——不做**（2026-09-23 用户裁定：*"就是顺序 digest 即可，原来时序"*）。
四条事实决定了它值不值：

1. VN 里的注入段是**开场构造、整章固定** ⇒ 章内更新 note，**VN 自己看不见**（除非重建章内 system = 打掉前缀缓存）。
2. **中断（未完成）的章不触发 digest**（触发点是 `if completed`）⇒ 那章里做的约定在 MMT 侧看不到，直到章真正结束。
3. 章进行中的板**不在真源里**（B0 整章暂存）⇒ 章内跑要读 **overlay**（`replay_attempts` 就在这坑里摔过）。
4. VN 是**玩家盯着等**的路径（每板一次生成）⇒ 再发一次 long-thinking 调用抢同一份配额，最坏是拖慢玩家正在等的那一板。

⇒ 收益只剩"中断章里的约定也能记"，代价是 overlay + 配额竞争 + 一个回溯语义。**不做。**
⚠️ **接受下来的限制**（真机 `vn_abandon` 存量 0 ⇒ 这是默认情形）：**"中断后既没续完、也没被废弃"
的章里做过的约定不会被记录** —— 与现状一致（那种章本来就不进记忆）。真机上若出现"玩家这么做、
而她在 MMT 里明显该记得"，再回来看。
⭐ 顺带**消掉一处复杂度**：章内不落 note 事件 ⇒ **"废弃回溯"整个不存在** —— note 事件只在 digest
时落（= 章已结束之后），永远不会落在章的 seq 区间里，也就没有"折进来了又要撤回"。

### 8.1 两条纪律（不写死就会互相踩）

- **第 1 轮只 add**，一切"是否已存在 / 要不要合并"归第 2 轮。今天 Round B 同时干 add 与
  update，还得让模型在 note 里解释"为什么不是复用"——那是它最容易出错的地方。
- **entity 载荷的写者唯一 = 第 3 轮**（多处写会打架，同"谁有写权限"那条老教训）。

### 8.2 第 1 轮给 hint，不给 id（"表不进第 1 轮"）

`about_hint` = 自然名字（`老师`），**不落库**（三轮之间内存传参）。

理由：第 1 轮在写正文，那时它心里本来就有这个名字（零成本）；而"从候选里挑 id"是**闭集选择**，
会把 **entity 表搬进第 1 轮的 prompt**——表是会变的（新对象登记 / 别名增补），
而第 1 轮的 prompt 属于**稳定前缀**（吃上下文缓存），表一变前缀就变。

⇒ 分工一句话：**第 1 轮说"我在写谁"（名字），第 3 轮说"那对应表里的哪一个"（id）。**
第 3 轮拿 hint 做**映射**（不是推理）；hint 对不上或没给，才回落到读正文判。

### 8.3 载荷注入分两层

| 层 | 内容 | 规模 |
|---|---|---|
| **候选表**（全量，**不裁剪**） | 本地 id + 名字 + 别名（`c0001 老师（sensei/阿宅）`）—— **只有身份，不印类别** | 全部 entity（几十条；用户判断"40 个不构成注意力问题"） |
| **载荷区**（只给命中集） | 该 entity 的 `text`（立场） + `state`（物理状况） | 通常 1–3 个 |

⚠️ **不印类别**（2026-09-23 用户裁决）: `etype` 已裁决不做（§3.0）⇒ 旧稿那个
"（人）"**没有字段来源**, 印了就是编。本地 id 前缀 = `c`（真 id 是 `x`, 且 `x0000`/`x0001`
是保留号 ⇒ 必须分得开）, 映射交执行器（同 Round B 的 `u0001` + `id_map`）。

命中集由**确定性规则**算：`about_hint` ∪ `别名命中本轮正文`（不靠 LLM）。
⚠️ 扫正文的称呼**要求 ≥2 字**（`entities.MIN_HIT_LEN`）—— 中文没有词边界, 若别名里
混进"他/她/它"这类单字, 几乎**每一段正文都会命中所有人**; 而 hint 是模型自己写的称呼,
走精确相等, **不受这条限制**。
⚠️ **改写基线只喂"旧基线 + 本轮新增"**，不喂该 entity 的全部 beliefs —— `overview` 是慢变量，
更新天然是增量的；喂全量会让成本与漂移都上来。触发也在此：**每轮命中集里问一次**，
水位不落字段（需要时从 `evolution.jsonl` 最后一条 entity 更新行推）。

### 8.4 归属三态 + 复查队列 —— ⏸ **2026-09-21 退回未定**

> 用户裁决：**"先不做这个，再考虑考虑"**（原话针对 `about_state` 字段）。下面的设计**保留作候选**，
> 但**不要照它落地**；待定项见 §9-6。

```
about_state      → resolved / uncertain / none   ← **点的属性**（不是边属性: uncertain 恰好意味着"还没有边"）
```

- **不阻塞**：`uncertain` 的**不落 `about` 边**、**不进 entity 车道**（免得污染"关于某人的看法"聚合），
  但仍进按需层普通召回——记忆不丢。
- **下一轮过目**：第 3 轮把队列里的条目 + **可能相关的新正文**一起过一遍；后续剧情
  往往自己给出答案（"他"后来被点名了）⇒ 多数条目第 2~3 轮就落地。
- **队列要能自终止**（默认值，可调）：每轮最多带 **N = 5** 条（最老优先）；连续 **K = 3** 轮
  仍不确定 → 停止复查，降级为"**永久未归属**"，只在人为重挂时处理。
  ⚠️ "复查了几轮"**不落字段**：从 `evolution.jsonl` 数（同 `history` 那次的口径——审计的事归审计日志）。
- 形状与 `BondStoryEngine._pending_feedback` 同款（本轮判不了 → 下一轮念一次 → 自清）。

### 8.5 讨论中改掉的两个口径

- ❌ "**不许猜**"红线 **降级为"可以猜，但错了要留痕"**。因为**正文与结构的寿命不同**：
  正文（`text` / `verbatim`）是 append-only 的记忆，改了等于篡改"当时她怎么想的"；
  而边 / `about` / entity 载荷是**派生的组织方式**（`wiki.jsonl` 本来就整写）⇒ 挂错按
  **可修的错**处理，甚至可以是"她的理解错误"这个叙事资产。前提只有一条：**看得见**
  （`evolution.jsonl` 留痕 + 未归属台账）。
- ❌ "候选裁剪（别名粗筛 + 向量 top-K）" **不做**——40 条不稀疏注意力。真正会膨胀的是
  "给每个 entity 附载荷"，那由 §8.3 的两层注入解决。

### 8.6 全景轮：**写卡**（低频，不属于每段）

> **不是**"每段都跑"的常规轮，而是**低频 · 全景 · 遍历后**的一次整理。
> 用户原话：*"LLM 在遍历 wiki 后，要不要给自己写一个记忆卡？"*
> ⇒ **2026-09-23 定名：它只干一件事 —— 写卡。**

⭐ **它不碰图、也不碰 A 类槽**（产出只有 `habits` / `on_mind` 两个 B 类快照槽）⇒
**不进 digest 事务、不需要 `clone_state` 快照、失败也不带走整轮 digest**
（原稿那句"同一份快照 + 同一次 `save` + 同一个水位提交"是把它误当成了写图的一轮）。
⚠️ **promise 的结清/固化不在它这儿**（2026-09-23 撤回我早先"全景轮顺手结清"的说法）——
设计稿 §3.2 的写者分工本来就写着"**收口 = digest**"，那件事归 **R4**（§8）。

| | 每段（§8） | **全景轮** |
|---|---|---|
| 频率 | bond 闭环 / MMT 每 25 轮 | **低频**（每 N 段，N=10 默认；章闭环也算 —— 待裁 §9-9 的余项） |
| 视野 | 本段窗口 | **全量**（= 上次那张卡 + 本轮新增 + 按锚点找到的旧经历） |
| 职责 | 产出 / 收口 / 链接 / 归属 | **写 note 的 B 类两槽**（`habits` / `on_mind` **整体重写**）+ **淘汰**（重写时不写回来 ⇒ 不需要任何"过期标志"） |
| 纪律 | — | ⭐ **只归类、不创作**：每条结论**必须带实例 id**（`refs`）；**禁止产出无实例支撑的内容**；**不许写抽象类别词** —— 用户要求的"极其严苛"靠这条保证，不靠模型自觉 |
| 成本 | 4 次调用 | 1 次（且低频） |

⭐⭐ **输入一张卡，输出一张卡**（2026-09-23 定形，三块）：

```
【你上次给自己写的卡】
  · 惯例
    他买东西时总先问我想要哪个（m0005, m0010）
  · 最近在想
    我不想再只是隔着玻璃看（m0009）

【这次新消化的经历】
  m0011 … / m0012 … / m0013 …

【可能相关的旧经历】（按**字面**找到的, 不一定是同一件事 —— 你自己判）
  m0009（与 m0011 同 tag: 纸兔子, 与 m0013 同 tag: 纸兔子）我把老师带到我路过很多年的那家模型店…
```

**输出契约（2 键 2 字段，一种行形状）**：

```json
{"habits": [
   {"text": "他买东西时总先问我想要哪个", "refs": ["m0005", "m0010"]},
   {"text": "周四晚上会发晚安", "refs": ["m0012", "m0013"]}],
 "on_mind": {"text": "我不想再只是隔着玻璃看", "refs": ["m0009"]}}
```

- ⭐ **`on_mind` 与 habit 条目同形状**（只是"只有一条"）⇒ 解析器一个分支。
- ⭐ **契约里没有 `id`**：延续的判据只有"**照抄上一版的原文措辞**"，两套身份声明只会打架。
- ⭐ **两个键都必须在**（`habits` 可为 `[]`、`on_mind` 可为 `null`）；**缺键 = 形状错 → 拒 + 反馈重试**
  ⇒ "缺键 vs 空值"这条语义规则整条消失，且失败是安全的（老卡原样留着）。
- ⚠️ **缺了的东西 = 淘汰**（设计稿原话"重写时不写进去"，所以空数组合法）；
  引擎侧只加两行**可见性**：`旧 N 条 → 新 M 条且 M < N` ⇒ 记账；`新空旧非空` ⇒ WARNING（不阻断）。
- ⚠️ **`refs` 是纪律的脊梁**（每条结论都要能指回经历）；**幻觉 id** ⇒ 剔掉那条 ref，
  剔完没 refs 的条目**整条丢** + 记账（不拒整包：形状错才拒，"看错了世界"重试大概率还是错）。
- ⚠️ **"惯例"至少两个实例**（`refs ≥2`）：prompt 硬要求，引擎**只记账不硬拒**
  （拒了会把内容一起丢掉）。

#### `habits` 的取料机制（v3，2026-09-23 定案）

> 演进史（都是被否掉的中间方案，别再回头）：`pattern_hint`（第 1 轮**判不了"类"**）→
> `degree ≥ 2 浮现`（门槛挂在 kind 上是**死穴**：出生时恒为 1）→ 字面锚点聚类（我为了**不引入
> 嵌入**而造的一整套补丁：锚点五类 + 停用表 + 覆盖率过滤）→ ❌ **全部作废**。

| 步 | 做什么 | LLM |
|---|---|---|
| 1 | 新 episode 落库 → **嵌入**（**低频轮现算**，不落盘、不引入向量库 —— 见下） | ❌ 引擎 |
| 2 | ⭐ **"同类" = 近邻查询**（不是"维护出来的概念"）：每条新 episode 查 top-k 相似，**跨全时段** ⇒ **不需要"最近 N 段"那个旋钮** | ❌ 引擎 |
| 3 | **LLM 判定**：这几条是不是**同一件事**（严苛三判据：① 同一个具体细节 ② 人设卡里没有 ③ 不是抽象类别词）+ 写一句惯例，**必须带 `refs`** | ✅ 全景轮 |
| 4 | **频次**：**只对 LLM 确认过同类的实例计数**（⚠️ 不能拿 sim 阈值直接数 —— 我们自己的注释写过：*"sim 高不等于同主题，同一个人的经历天然都像"*）；⚠️ **不每轮注入数字**（既有纪律：数值不直接喂 LLM），要说"好多次/每次都"由 writer 决定 | ❌ 引擎 |
| 5 | 注入：`habits` 段 + **按时间排序的记忆流**（第 ⑤ 步"注入时间重排"） | — |

**输入池 = 向量全量近邻 ∪ 上一版 `habits`**（递归，学 BaiShou 的金字塔：新东西靠近邻发现，
长周期靠上一版承载 —— 不再延续的自然淡出，**不需要过期机制**）。

⚠️ **不引入向量库**（用户 2026-09-23 裁决）：habits 是**低频**任务 ⇒ 现算嵌入完全够用
（百来条短文秒级），并保住 `recall.py` 那条"**embedding 派生不落盘 ⇒ 内容改动零漂移**"的纪律；
**回合内 `recall` 的嵌入缓存**留到第 ⑥ 步再定（AgentGal 用 sqlite-vec、BaiShou 用 `memory_embeddings` 表）。
⚠️ **降级路径**：embedder 未就绪（`_get_embed_fn()` → None）时退化成**字面锚点**（同一 `tag` /
`items` / `place` 的**值相同**）—— 那套补丁不作废，它降级成后备（`recommend_candidates` 已有同款先例）。
⚠️ 它**依赖 R1**（要读 R1 刚产出的 episode ⇒ 不能与 R1 并行）。

#### ✅ 取料已落地（2026-09-23）—— `wiki_v2/panorama.py`

`build_input(store, note_state, *, new_ids, embed_fn=None)` → `PanoramaInput`（纯函数、零 IO、零 LLM）。
**判断全交给那一次调用，本模块只负责"把料摆到她面前"**。

✅ **代码已对齐**（2026-09-23 同一节点）：`PanoramaInput` 只留 **三块**（上次的卡 / 本轮新增 /
候选池）· **索引默认关**（`DEFAULT_INDEX_CAP = 0`）· **`worth_running` 只看"有没有新材料"**
（"待结清"不再是理由 —— 那不是这一轮的活）· 卡上**不印编号也不印时间**（`_card_line` 与注入块的
`render_item` 故意不同）· `render()` 的 `now` 参数**删掉**（卡不印时间 ⇒ 它成了死旋钮，
不留 —— 同"不留死旋钮"那条纪律）。

**四条落地时定的纪律**（都是"不写死就会出错"的那种）：

1. ⭐ **候选必须如实标注来源**（`与 m0013 同 tag: 纸兔子`）—— 她看得见"这两条只是共享一个
   泛词"才拒得掉；**引擎替她过滤 = 引擎做判定**（越界）。
2. ⭐ **锚点排序 = 稀有度（DF 小 = 具体）→ 命中数（几条新经历连上它）→ 显著性**，
   且**每个锚点封顶** `cap_per_anchor=3` —— 否则"约定"这类泛词会把池子冲爆（长世界必然）。
3. ⚠️ **`verbatim` 共词不做锚点**：真机实测前两字 `那个` 命中 3 条，纯噪音。
   `emo_shape` 也不做（召回侧信号，绝不进 LLM 上下文）。
4. ⚠️ **`worth_running`**：有**新材料**才值得花那一次调用（重写空转没意义；
   **时机**是另一回事，由触发频率决定）。

**真机事实（2026-09-23 实测，world1/igusa_haruka 11 条 episode）**：
- ⚠️ **本机 embedding 服务未起**（`[embed].base_url = :1235`，`health()=False`）⇒
  **今天的主力是字面锚点**，语义近邻那条路接口就位但跑不到。
- 可用的锚点：`tags` **11/11 条都有**（28 个值，≥2 次的有 6 个：约定×4 / 笔记×4 / 夏莱×3 /
  **纸兔子×3** / 大扫除×2 / 模型店×2）· `items` 只 1 条 · `place` 只 4 条 · `place_raw` 无重复值。
- 取料演练真的连上了：`纸兔子` 把 m0009 抬给 m0011/m0013，`夏莱` 把 m0005/m0006 抬给 m0012。
  ⇒ **具体名词（人设给不出来的那种）正是锚点最灵的地方** —— 与"物品/具体名词才是记忆的意义"那条一致。
- ⚠️ 稀疏档（`asagi_mutsuki` 2 条 episode）**候选池为空**：没有共享锚点就是没有 —— 这是如实结果，
  不是 bug（此时 `worth_running` 仍可能为真：待结清那一路）。

**还没做的**：调用侧（`llm/prompts/panorama.md` 的任务与严苛三判据 + 输出契约 + `digest.panorama`
标签 + 解析/执行器 + 触发频率）· §8.6 表的第 4 步"频次统计"（倾向**不做**：数字不注入、
今天零消费者 —— 该不该说"好多次"由 writer 决定）。

## 10. 已否决（别再提）

| 项 | 结论 | 理由 |
|---|---|---|
| **节点做成父类 / 子类** | ❌ **不做**（2026-09-21 用户裁决） | 改动面太大：要动 ~60 处分派点 + store + 一大批测试，而本仓**没有类型检查**（`isinstance` 与 `kind ==` 运行时等价），子类拿不到静态分派安全；收益主要是"字段归属与不变量有地方放"，那些可以用**表驱动**更便宜地拿到（见下） |
| **运行时用 networkx（或现成图 API）** | ❌ **不做**（2026-09-21） | nx 确实提供 `remove_node`/正反邻接/算法，但代价是：① **磁盘格式被它的 schema 绑住**（3.x 把 `node_link_data` 的 `links` 改名成 `edges`——我们的"旧档宽容读、无迁移脚本"纪律会被迫跟着迁移）② 运行时加依赖（`wiki_v2` 现在纯 stdlib）③ 原子写/宽容解析/旧档兼容仍得自己写，省不掉。**dev 侧照旧可用**（`tools/wiki_viz.py`）；要算法时一行桥建图 |

**替代方案（不在本稿内，需要时另立）**：保持一个 dataclass、按 `kind` 分派，但把
**"每个 kind 有哪些字段 / 哪些必填"收进一张表**，由表驱动 `to_dict` / `from_dict` / `validate`。
今天这件事散在**四份平行维护的清单**里（`KINDS` · `_REQUIRED` · `to_dict` 的字段元组 ·
`store._PREFIX`），删一个字段要改 5 处——2026-09-21 的化简里已经反复踩到。
⚠️ 成本提醒：这条替代方案本身也要 ~1 提交 + 契约夹具，**要动时先讨论**。

## 11. 能力面：MMT 的 `function_call`（2026-09-23 用户交底）

**MMT 的消息流协议（JSON）本来就是为 `function_call` 准备的** —— 除了现有的
`mmt_send_media` / `mmt_inspect_character` / `mmt_trigger_bond_story`，将来还有 **"回忆"**：
她可以 `grep "keyword"` 或 `inject all` 来保证**本轮**记得该记得的东西。
⚠️ **bond 里没有 `function_call`**（VN 的契约是记录流）⇒ bond 侧的"记忆动作"只能靠 digest 事后做。

**因此图的价值重新定位**：图不是"给引擎分桶注入"用的，而是"**给她自己查**"的库。
`about` / `supports` / `contradicts` / `evolved_from` 是**查询索引与走法**（§2.2）。

**动作面（2026-09-23 定，调研依据 → §12）**：

| 动作 | 状态 |
|---|---|
| `mmt_chat`（隐含）· `mmt_send_media` · `mmt_inspect_character` · `mmt_trigger_bond_story` | 现有 **4** |
| ⭐ **`mmt_recall {scope, query}`** | **计划新增 1 个**（合计 5）：`scope ∈ {memory, note, inventory}` **一次开全**（inventory 分支先返回空，§3.3）；`query` = 关键词 / 空（全部或最近） |

**加动作的判据四条**（以后先过这四条）：
① **数同类**：同族操作 ≥3 ⇒ **合并**成一个动作 + 参数
② **划边界**：两个动作若模型可能分不清 ⇒ 改描述或合并（⚠️ **重叠比数量更致命**）
③ **看意图**：动作名要**意图形状**（`schedule_event`），不要 **API 形状**（`create_event`）
④ **一次开全**：spec 进 system（逐字节稳定、吃缓存）⇒ **每次加动作 = 废一次前缀缓存**

**"动作 vs 输出字段"的判据**（这条把 note 的增删从动作面里救了出来）：

> **"我需要它才能说下一句" → 动作；"我说完了顺手记一笔" → 输出字段。**

⇒ `recall` / `inventory` 查询 = 动作；`note_add` / **`note_close`** / `drop_item` = **输出字段**（不占动作位）。
⚠️ **`note_close` 的形状与 R4 的 `close` 行同构**（`{id, state, reason}`）—— 同一件事只有一个契约，
别长成两套；当场多半是 `kept`，但"这轮发现去不成了"也可以是 `broken`（判据同 §8 的 R4）。
⚠️ **`retire` 不是她的输出字段** —— 它是引擎在固化成功之后落的机械确认（§3.2），模型不该碰。
⚠️ 动作面**按真机需求长，不按设计完整性长** ⇒ `inspect_inventory` / `drop_item` **先不做**。

**对 `agent_turn` 的工程要求（未实现）**：
- **轮内多步**：现在是"一次调用 → 解析 → 执行动作（副作用）→ 结束"，而回忆是**回合内**的：
  `call → 工具结果回灌 → 再 call` ⇒ 需要 **loop + 步数预算**（防她反复查不停）
- 结果**只能往尾部插**（不动 system / history 前缀，否则打掉前缀缓存）
- **回忆动作要落事件流**（否则回放丢了"她当时想起了什么"，且 0-LLM 回放重建不出来）
- `window_messages` / `render_events` 要**认 tool 消息**（"live 与 resume 同形"那条纪律要扩到它）

### 12.1 ⭐ BaiShou 的设计哲学（原文摘录 —— 对"重复 / 时间 / 沉淀"三件事的启示）

> 出处：其 README「设计哲学：为什么不是『只靠 RAG』？」一节（2026-09-23 拉取）。
> 原话四条：

1. **我想让所有人都掌握自己的记忆**（Markdown，不是黑盒）。
2. **它太像「查字典」了**：RAG 把记忆切碎了存起来，需要时再查 —— 对查资料有用，但对人太生硬，**丢失了上下文语境**。
3. **它没有「时间感」**：记忆不是散落在地上的碎片，而是**一条流动的河**。昨天的事和去年的事，对人的意义完全不同。
4. **它不懂「权重」：拥抱冗余，哪怕这看起来很笨。** 你在日记里写了十次「我爱你」，RAG 可能会去重，
   但白守会把它们**都留下来** —— 因为每一次的语境都不同，**重复的频率本身就是羁绊的厚度**。
   （另："白守不做冷冰冰的数据库，它是你的「**外部海马体**」……随着时间推移，把**短期记忆慢慢沉淀为长期记忆**"）

**机制**：层级化总结（日记 → 周记 → 月报 → 季报 → 年鉴）+ **生成时注入"本期之前"的共同回忆**
（`untilExclusive: periodStart` ⇒ 总结是**递归**的）+ 注入时**按日期排序**拼成一整段"共同回忆"。
⚠️ 它的 **Agent 有日记读写工具**（可读写日记 / 搜历史）⇒ **BaiShou 是"有工具"那一派，AgentGal 是"无工具"那一派**；我们走的是前者（§11）。

**三条直接落到我们设计上的启示**：

| 启示 | 落到哪 |
|---|---|
| **不做去重压缩** —— "同类"不是要维护的概念，而是**一次近邻查询**；实例**一条都不删** | `habits` 取料机制 **v3**（§8.6） |
| **时间感 = 一条流动的河** —— 我们的注入是**分桶**的（同一天的事散在不同桶里，先后全丢） | **第 ⑤ 步（注入提示词时间重排）**：按时间排、每条带日期标签 |
| **金字塔 = 递归** —— 周记读日记、月报读周记 | `habits` 的输入 = **近邻 ∪ 上一版 `habits`**（不再需要"最近 N 段"窗口） |

⚠️ 它第 2 条对我们的批评**一半成立**：我们的图**也是"碎片 + 查询"**（只是比 RAG 多了可 traverse 的边）。
补齐靠两样 —— **注入层排成"一条河"**（第 ⑤ 步）+ **note 常驻**（她随身带着的当下）。
⇒ 一句话：**图管"可查的细节"，河管"时间感"，note 管"此刻"。**
